# NEXUS v0.2 Implementation Plan: the MESH runtime adapter

> **For agentic workers:** execute task by task, in order. Steps use checkbox (`- [ ]`) syntax. Each task ends green (`pnpm typecheck && pnpm test`) before the next starts.

**Status:** approved (F-A and F-B included) and executed on `nexus-v0.2`. The text below is the plan as approved. §0 records the U1–U4 verification that the approved spec required first. §1 lists two findings the spec didn't anticipate. F-A, a gap in NEXUS core, needs your decision before Task 2. F-B is a minor stale test.

**Spec:** `docs/superpowers/specs/2026-09-26-nexus-v0.2-mesh-adapter-design.md` (approved, revision 3). This plan executes it. Where the plan and the spec disagree, the spec wins, and the disagreement is a bug in the plan.

**Goal:** a NEXUS application in Node drives MESH v0.5 end to end (spec §1), proven by spec tests 1–9.

**Tech stack:** TypeScript 5.9 (strict, NodeNext, `exactOptionalPropertyTypes`), Effect 3.22, Vitest 2.1, pnpm 10, `@valancex/mesh-runtime@0.5.0` (dependency), `@valancex/mesh-compiler@0.5.0` (devDependency, test fixture only).

## Global constraints

- **Architecture is frozen.** The plan adds no separate MESH package, no optional peer dependency, no `@valancex/nexus/mesh` subpath, no PORT or browser rendering, no runtime MPRX compilation, no hot reload, no composite events, and no abstraction the spec doesn't name.
- **M1–M4 are normative** (spec §5.2). Every task that touches `src/mesh/` re-reads them.
  - M1: `dispatch` passes the caller's exact `Render` to the runtime.
  - M2: no registry or cache of renders.
  - M3: explicit `commands` entries only, looked up with `Object.hasOwn`.
  - M4: `src/mesh/` imports `@valancex/mesh-runtime` and NEXUS primitives, never the compiler.
- **One adapter file:** `src/mesh/index.ts`, exported from the package root as `Mesh`. Core modules (`src/<primitive>/`) never import it (test 9).
- **Relative imports use `.js` extensions** (NodeNext), as in v0.1.
- **Effect conventions follow the existing code:** `Effect.Do` pipelines rather than `Effect.gen` in `src/`, `_tag`ged plain-object errors, and rejections from the runtime as defects via `Effect.promise`.

### U4 in detail

**What happens at import.** `import "@valancex/mesh-runtime"` evaluates four small ES modules: `index.js`, `engine.js`, `encode.js` and `version.js`, about 22 KB of JS in total. Top-level work is limited to a `Symbol`, a `TextEncoder`/`TextDecoder` pair, a resolved `Promise` (the call queue) and class definitions. The package also declares `"sideEffects": false`.

**What is deferred.** `engine.js`'s `current()` reads `mesh-runtime.wasm` (604,443 bytes) with a dynamic `import("node:fs/promises")`, then runs `WebAssembly.compile` and `instantiate`, and does all of this only inside the first `render`/`dispatch`. It caches the compiled module and instance at module level, and re-instantiates only after a call fails.

**Measured:**

- **strace** of a process that only imports the built `@valancex/nexus` root (with a `Mesh` re-export): 0 opens of `mesh-runtime.wasm`. The only files opened from the package are the four JS files and `package.json`. With one render added, there's 1 open.
- **Import with the `.wasm` file deleted:** importing the NEXUS root still succeeds. The first `render` then rejects with `Error: ENOENT`. That's decisive: import doesn't touch the wasm.
- **Cost:**
  - `@valancex/mesh-runtime` on its own: median **4.2 ms** to import (15 cold processes).
  - The NEXUS package root, 30 interleaved cold processes each: without `Mesh` the median is 320.1 ms (p10 302.4, p90 355.9); with `Mesh` the median is 331.4 ms (p10 318.3, p90 369.5). That's roughly +11 ms, inside the run-to-run spread, and dominated by `effect`.
  - RSS at import: no measurable difference (median 45.9 MB vs 45.8 MB).
  - The first render costs a median **22 ms** (wasm read, compile and instantiate). Later renders cost about 3 ms. Only apps that actually render pay this.

**Conclusion.** The import-time cost isn't material, and it doesn't change the packaging decision. `@valancex/mesh-runtime` stays a regular dependency as approved (spec §5.4).

### Incidental observations (no spec change needed, recorded for the docs task)

- **O1: F9 is slightly incomplete.** A missing or unreadable `.wasm` rejects with a plain `Error` (for example `ENOENT`), not only with `TypeError`, `MeshVersionError` or `MeshInternalError`. The adapter treats every rejection as a defect (`Effect.promise`), so behavior is unaffected. Task 6 adds a one-line erratum to spec F9.
- **O2: snapshot exactness applies to records, not to the top level.** An unknown **top-level** snapshot key is accepted: `{...first.json, extra: 1}` renders fine. Nested record values are exact: `first.selectedUserId` gives `runtime-unknown-field`. Tests 6 and 8 already leak into `first`, so they're correct as specified. The slice's scope selector still omits `selectedUserId` (spec §7), but only because that's the right projection, not because MESH would reject it.
- **O3: the runtime keeps process-wide state of its own.** That's one cached wasm instance and a call queue that serializes every `render`/`dispatch` in call order. This is MESH's internal state, not the adapter's, so M2 is unaffected. It's also why `renders` stays in commit order even under concurrent calls.

## 1. Finding that needs a decision before Task 2

**F-A: `State.changes` doesn't complete when its scope closes, which contradicts `docs/primitives/state.md`.**

`state.md` says: "a `StateHandle` lives as long as the `Scope` it was created in… and its `changes` stream completes when that scope closes". `src/state/index.ts` registers no finalizer. `changes` is `Stream.drop(ref.changes, 1)` over a `SubscriptionRef`, and it never ends. No existing test covers this.

Probe (in the scratchpad clone):

| Case | Today | With the fix below |
|---|---|---|
| A: state in its own scope, `changes` drained in a daemon fiber, scope closed | still running after 300 ms | ends with `Success` |
| C: state created in the app's runtime scope; `Stream.mapEffect(selector.changes, …)` forked via `Runtime.runFork(running.runtime, …)`; one commit; `Application.shutdown` | still running | ends with `Success`, having collected exactly the one element |
| B: state in the *test's* scope; `Application.shutdown` | still running | still running. That's correct: the app doesn't own that state. |

**Impact.** Spec test 7 ("after `Application.shutdown`, a `renders` subscription started in the app's scope has ended without error") and spec §5.3 ("when that scope closes… the underlying state stream completes and `renders` ends with it") both rely on the documented contract. As the code stands, test 7 would hang. The adapter design itself is unaffected: `renders` is still just `Stream.mapEffect(scope.changes, render)`.

**Proposed resolution (Task 2): a bug fix to NEXUS core, not a redesign.** Make `State.create` honor its documented contract. Add a `Deferred` that a scope finalizer completes, and end `changes` with `Stream.interruptWhenDeferred`. That's three lines in `src/state/index.ts`, no API change, and a new test in `tests/state.test.ts`. In the probe, all 11 existing test files stayed green with the fix. Test 7 then creates the slice's `Team` state in the application's runtime scope (`Scope.extend(State.create(...), running.runtime.scope)`), which the spec's words "started in the app's scope" already describe.

**Alternatives, not recommended:**

- (b) Weaken test 7 to "the consumer fiber is interrupted", run with `Effect.forkScoped` in a scope the test closes. That tests Effect's scoping, not NEXUS's lifecycle, and it leaves the `state.md` bug in place.
- (c) Have the adapter add its own completion signal. That violates spec §5.3 ("the adapter adds no scope of its own") and is exactly the kind of lifecycle §5.1 forbids.

**Needs your approval:** Task 2 changes a v0.1 core primitive, so it's outside `src/mesh/`. It changes no API, and it makes the code match what the docs already promise.

**F-B (minor): an existing guard test becomes stale.** `tests/vertical-slice.test.ts`'s second test ("has no import of any mesh or port package anywhere under `src/` or `examples/`") greps for `@valence/(mesh|port)` and for `from "(../)*(mesh|port)/`. It would stay green in v0.2, but only because the regex spells the old `@valence` scope, while its *name* asserts something v0.2 deliberately changes. Spec §2.1 also says that "nothing else in the repo names the package", which this regex contradicts. Task 5 narrows the test to what's still true (no PORT import anywhere; no MESH import in `examples/`) under the new scope, and leaves `src/` MESH imports to test 9. The first vertical-slice test is untouched.

## 4. Risks

- **Flaky ordering in tests 5, 7 and 8.** The `renders` subscription must attach before the commit. As in `vertical-slice.test.ts`, a 1 ms sleep after the fork is the existing convention. Test 8 uses bounded polling for its assertions rather than fixed sleeps. If attachment proves racy, the fix is to fork with `Effect.forkScoped` inside the running runtime and yield once, not to change the adapter.
- **Handler-id drift.** Handler ids aren't hard-coded, so a fixture refresh can't silently break tests 2–8.
- **`Schema.optional` and exact records.** If Effect's decode ever materialized `avatar: undefined`, MESH would reject Grace. Test 1's parity check would catch that immediately.
