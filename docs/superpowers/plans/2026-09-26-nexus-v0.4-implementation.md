## The public model

This is the complete public surface of `src/semantic/index.ts`. Nothing else is exported: no helper, constant, utility type or re-export. Internal helpers are module-private (not `export`ed). Task 2 pins the runtime exports as exactly `["analyze"]`, and Task 11's parity test pins the exported names. The comments map it to the outline's working terms.

```ts
// C2: provenance. Offsets are UTF-16 code units, zero-based, half-open (P4).
export interface Span {
  readonly source: string;   // opaque source identity; non-empty (D6 case 3)
  readonly start: number;    // finite, not -0 (D6 case 3)
  readonly end: number;      // finite, not -0, and end >= start (D6 case 3)
}

// C4: one occurrence in the target-requirements fact
export interface Requirement {
  readonly capability: string;        // target capability id; non-empty (D6 case 4)
  readonly provenance?: Span;
}

// C3/C4: the one v0.4 semantic property
export interface TargetRequirements {
  readonly completeness: "complete" | "partial";
  readonly capabilities: ReadonlyArray<Requirement>;
}

// C1: the semantic declaration (exactly these parts; D5)
export interface Declaration {
  readonly id: string;                          // semantic identity (D4)
  readonly name?: string;                       // display name; never identity
  readonly provenance?: Span;
  readonly requirements?: TargetRequirements;   // absent = unknown (I14)
}

// C4: the target profile (explicit input; D8)
export interface TargetProfile {
  readonly name: string;
  readonly provenance?: Span;
  readonly provided: ReadonlyArray<string>;
  readonly notProvided: ReadonlyArray<string>;
}

export type Property = "target-requirements";        // C3: the v0.4 property set
export type RequiredFact = "target-compatibility";   // C5: the only fact that can be required

// C7 input: the analysis context
export interface AnalysisContext {
  readonly declarations: ReadonlyArray<Declaration>;
  readonly profile: TargetProfile;
  readonly require?: ReadonlyArray<RequiredFact>;
}

// C4: the verdict, with its cause. It carries every fact a diagnostic asserts (C5).
export type Verdict =
  | { readonly _tag: "Compatible" }
  | { readonly _tag: "Incompatible"; readonly notProvided: ReadonlyArray<string> }
  | { readonly _tag: "Undetermined"; readonly cause: "operation"; readonly requirements: "undeclared" | "partial" }
  | { readonly _tag: "Undetermined"; readonly cause: "target"; readonly undecided: ReadonlyArray<string> };

// C5: derived from the verdict, one to one
export type Classification = "supported" | "opaque" | "incompatible";

// C7: one entry per declaration
export interface OperationResult {
  readonly id: string;
  readonly known: ReadonlyArray<Property>;
  readonly verdict: Verdict;
  readonly classification: Classification;
}

// C6
export type DiagnosticCode =
  | "nexus-incompatible-target-capability"
  | "nexus-opaque-operation"
  | "nexus-undetermined-target-capability";
export type Severity = "warning" | "error";
export type Location =
  | { readonly _tag: "Span"; readonly span: Span }
  | { readonly _tag: "Unlocated" };
export interface RelatedSpan { readonly span: Span; readonly label: string }
export interface Diagnostic {
  readonly code: DiagnosticCode;
  readonly severity: Severity;
  readonly message: string;
  readonly location: Location;       // primary location, or explicitly unlocated (C2)
  readonly subject: string;          // the operation's semantic identity
  readonly related: ReadonlyArray<RelatedSpan>;
  readonly notes: ReadonlyArray<string>;
}

// D6: a malformed context. Not a diagnostic.
export type RejectionReason =
  | "duplicate-identity"     // D6 case 1
  | "missing-identity"       // D6 case 2
  | "invalid-span"           // D6 case 3: a non-finite or -0 offset, end < start, or an empty source
  | "empty-capability"       // D6 case 4
  | "conflicting-decision";  // D6 case 5
export interface RejectionIssue {
  readonly reason: RejectionReason;
  readonly path: ReadonlyArray<string | number>;
}

// C7 output: exactly one of these
export type AnalysisOutcome =
  | {
      readonly _tag: "Analyzed";
      readonly properties: ReadonlyArray<Property>;     // always ["target-requirements"]
      readonly required: ReadonlyArray<RequiredFact>;   // [] or ["target-compatibility"]
      readonly profile: string;                         // the profile's name
      readonly operations: ReadonlyArray<OperationResult>;
      readonly diagnostics: ReadonlyArray<Diagnostic>;
    }
  | { readonly _tag: "Rejected"; readonly issues: ReadonlyArray<RejectionIssue> };

export const analyze: (context: AnalysisContext) => AnalysisOutcome;
```

**Why each output field exists.** Every field traces to the outline:
- `properties`, `required` and `profile` are C7's "the property set considered, the required facts, the profile's name".
- `id`, `known`, `verdict` and `classification` are C7's per-declaration entry.
- The diagnostic's fields are C6's seven parts.
- `related` and `notes` are always present, possibly empty, so a consumer never distinguishes "absent" from "empty".
- The output has **no optional fields**, so no output key is ever `undefined`.

**Why the verdict sits next to the classification.** C7 requires both. The classification is a one-to-one summary. The verdict is the structured cause:
- for *incompatible*, which ids are not provided;
- for *opaque* with an operation-side cause, whether the requirements are undeclared or partial;
- for *opaque* with a target-side cause, which ids the profile leaves undecided.

No consumer has to parse a message (C5: "the result is authoritative").

**Deliberately absent:**
- predefined capability ids or profiles (D8);
- any field about what a consumer should do (C6, L3);
- fixes (D12);
- inputs, outputs, effects, determinism, cacheability or relationships (C3, D5);
- any link to `Capability`, `Environment` or `Command` (I15, D7);
- display names in the output: they appear only inside messages (C1: "human-readable messages; never identity").

### Requirement semantics (C3, C4, P7)

- **Absent `requirements`:** the property is unknown. `known` is `[]`.
- **Present `requirements`:** the property is known, and `known` is `["target-requirements"]`. `completeness` is C4's completeness statement. It has exactly these two values, and it is not an extension point:
  - `"complete"`: the operation requires exactly the distinct ids listed, and no others;
  - `"partial"`: it requires at least the distinct ids listed, possibly others.
- **The outline's "set", and this array.** `capabilities` is a list of *occurrences*. The outline's "set of target capability identifiers" is the set of **distinct** `capability` values in it. Order and repetition carry no semantic meaning. They matter only in two places:
  - the order of ids in the verdict: distinct ids, in order of first occurrence;
  - the order of related spans: every occurrence, in list order.
- **Empty lists:**
  - an empty complete list is the known fact "requires nothing". It is `Compatible` whatever the profile, and distinct from an absent property.
  - an empty partial list is known, but states only "at least nothing". It is `Undetermined` with an operation-side `"partial"` cause, like any partial set without a not-provided id.
- **Duplicates** are valid input:
  - compatibility is evaluated on the distinct ids;
  - each distinct id appears once in `notProvided` or `undecided`;
  - duplicates never add a verdict, a classification or a diagnostic;
  - every occurrence's provenance stays available. Where C6 requires related spans for requirements (the error, and the target-side warning), each occurrence with provenance contributes one related span, in list order.

  No other de-duplication exists.
- **Provenance** attaches per occurrence (`Requirement.provenance`), per declaration and per profile. These are the three sites C2 names. The requirements fact as a whole has no provenance, because C2 names no such site.

## The algorithm

`AnalysisContext → rejection → per declaration: known, verdict, classification, emission, location, related spans, message and notes → outcome`. Rejection runs first. A rejected context gets no further analysis.

### Rejection (D6, exactly five cases)

The whole context is traversed in this fixed order, collecting issues:
1. for each declaration `i`, in order:
   1. its identity;
   2. its `provenance`;
   3. each requirement `j`, in order: its `capability`, then its `provenance`;
2. the profile's `provenance`;
3. each `provided` entry, in order;
4. each `notProvided` entry, in order;
5. the conflicts.

If any issue is found, the outcome is `{ _tag: "Rejected", issues }` with every issue in that order. Otherwise analysis proceeds.

| D6 case | `reason` | Detected when | `path` |
|---|---|---|---|
| 2 | `missing-identity` | `id` is absent or `""` | `["declarations", i, "id"]` |
| 1 | `duplicate-identity` | a non-empty `id` equals an earlier declaration's `id` | `["declarations", i, "id"]`, for every later occurrence |
| 3 | `invalid-span` | a span has a `start` or `end` that isn't a finite number (`NaN`, `Infinity`, `-Infinity`) or is `-0`, or has `end < start`, or has `source === ""`. One issue per span, however many of these hold. | the span's path: `["declarations", i, "provenance"]`, `["declarations", i, "requirements", "capabilities", j, "provenance"]` or `["profile", "provenance"]` |
| 4 | `empty-capability` | a requirement's `capability`, or an entry of `provided` or `notProvided`, is `""` | `[…, "capability"]`, `["profile", "provided", k]` or `["profile", "notProvided", k]` |
| 5 | `conflicting-decision` | a non-empty id appears in both `provided` and `notProvided` | `["profile", "notProvided", k]`, where `k` is that id's first index in `notProvided`; one issue per distinct id, in order of `k` |

A missing identity takes no part in the duplicate check, and an empty id is reported only as `empty-capability`, never as a conflict.

**Nothing else is rejected** (D6: "Everything else is well-formed"). These are all well-formed:
- no declarations;
- a declaration with no facts;
- an empty complete list, or an empty partial list;
- duplicate ids in one requirement list;
- an id repeated within `provided`, or within `notProvided`;
- a profile deciding nothing, or empty `provided` and `notProvided` arrays;
- undecided ids, and unknown or unused capability ids;
- an empty display name, or an empty profile name;
- absent optional fields;
- a point span (`start === end`);
- a span with finite negative or fractional offsets, or offsets beyond the source's length, where `end ≥ start` and neither offset is `-0`. D6 decides this: none of these is among its five cases. They are passed through unchanged, and they are JSON-safe.

**The implementation condition for D6 case 3** is exactly this: a span is invalid when `!Number.isFinite(start) || !Number.isFinite(end) || Object.is(start, -0) || Object.is(end, -0) || end < start || source === ""`. It has no other numeric check. `Number.isFinite` and `Object.is` are applied to values read from the modeled fields, and invoke nothing from the input. Every span that reaches analysis therefore survives a JSON round trip unchanged (I13), and I17's exact pass-through holds.

### Analysis of one well-formed declaration

1. **`known`**: `["target-requirements"]` exactly when `requirements` is present, else `[]`.
2. **Verdict** (C4). Let `ids` be the distinct required ids, in order of first occurrence. The first matching step applies:
   1. requirements present, and some id in `notProvided` → `Incompatible`, with `notProvided` listing those ids in `ids` order;
   2. requirements absent → `Undetermined`, `cause: "operation"`, `requirements: "undeclared"`;
   3. `completeness: "partial"` → `Undetermined`, `cause: "operation"`, `requirements: "partial"`;
   4. some id in neither list → `Undetermined`, `cause: "target"`, with `undecided` listing those ids in `ids` order;
   5. `completeness: "complete"`, and every id in `provided` (vacuously true for an empty list) → `Compatible`.

   The five steps are exhaustive. Anything reaching step 5 is complete, and has no not-provided and no undecided id. They are also mutually exclusive, because the first match wins.
   - Step 1 precedes step 3, so a partial set with a not-provided id is incompatible (DoD 4).
   - Steps 2–3 precede step 4, because C4 says "if both apply, the cause is operation-side".
   - Only step 1 yields `Incompatible`, and only with a declared requirement explicitly marked not provided (I16). Missing information can never reach it (I12).
3. **Classification** (C5): `Compatible` → `supported`; `Undetermined` → `opaque`; `Incompatible` → `incompatible`.
4. **Emission** (C5 rules 1–4). "Required" means `require` contains `"target-compatibility"`.

   | Classification | Nothing required | Required |
   |---|---|---|
   | `incompatible` | one `nexus-incompatible-target-capability`, `error` | the same |
   | `supported` | none | none |
   | `opaque`, operation cause | none | one `nexus-opaque-operation`, `warning` |
   | `opaque`, target cause | none | one `nexus-undetermined-target-capability`, `warning` |

   Each operation therefore has exactly one classification and at most one diagnostic.
5. **Location**: if the declaration has `provenance`, `{ _tag: "Span", span: copy(provenance) }`; otherwise `{ _tag: "Unlocated" }`. The location is never borrowed from a requirement or the profile (I17).
6. **Related spans** (C6's table):
   - **error:** for each occurrence `j`, in list order, whose id is not provided and that has provenance: `{ span: copy, label: "requirement declared here" }`. Then, if the profile has provenance: `{ span: copy, label: "target profile declared here" }`.
   - **target-side warning:** for each occurrence, in list order, whose id is undecided and that has provenance: `{ span: copy, label: "requirement declared here" }`.
   - **operation-side warning:** `[]`.
7. **Message and notes.**
   - `label` below is the declaration's `name` when present and non-empty, else its `id`.
   - `<ids>` is the verdict's id list, each id in double quotes, joined by `", "`.
   - Caller strings are inserted verbatim. NEXUS adds no markup, escape sequences, excerpts, line numbers or colours (I13).
   - The wording is not normative and never asserted (C6: messages may change). The content of the notes is required (C6's "notes must state").

   | Code | Message | Notes |
   |---|---|---|
   | `nexus-incompatible-target-capability` | `Operation "<label>" requires target capabilities that target profile "<profile>" does not provide.` | `Not provided by target profile "<profile>": <ids>.` |
   | `nexus-opaque-operation` | `NEXUS cannot establish target compatibility for operation "<label>".` | `Its target requirements are undeclared.` or `Its target requirements are declared as partial.`; then `The operation still executes normally.` |
   | `nexus-undetermined-target-capability` | `NEXUS cannot establish target compatibility for operation "<label>" against target profile "<profile>".` | `Not decided by target profile "<profile>": <ids>.` |

   Messages and notes state findings, never consumer actions (C6: "Meaning, not action"). No template says to reject, refuse, block, fix or display anything.
8. **Outcome:**

   ```ts
   { _tag: "Analyzed", properties: ["target-requirements"], required, profile: profile.name, operations, diagnostics }
   ```

   `required` is `["target-compatibility"]` if `require` contains it, else `[]`. `operations` has one entry per declaration, in order. `diagnostics` follows declaration order.

### Exhaustive case table

The table covers one declaration. Declarations are independent: an operation's result depends only on its own declaration, the profile and `require`, never on other declarations, their order, or how many there are. "Distinct ids" are after de-duplication, so duplicates behave exactly like one occurrence here. "Diagnostic" is the one emitted with `target-compatibility` absent / present.

| Requirements | Distinct ids vs profile | Verdict | Classification | Diagnostic (not required / required) |
|---|---|---|---|---|
| absent | — (the profile is irrelevant) | Undetermined, operation, `undeclared` | opaque | none / `nexus-opaque-operation` warning |
| complete, 0 ids | — | Compatible | supported | none / none |
| complete, ≥ 1 id | all provided | Compatible | supported | none / none |
| complete, ≥ 1 id | none not provided, ≥ 1 undecided | Undetermined, target, `undecided` | opaque | none / `nexus-undetermined-target-capability` warning |
| complete, ≥ 1 id | ≥ 1 not provided (with any others) | Incompatible, `notProvided` | incompatible | `nexus-incompatible-target-capability` error / the same |
| partial, 0 ids | — | Undetermined, operation, `partial` | opaque | none / `nexus-opaque-operation` warning |
| partial, ≥ 1 id | none not provided (the rest provided or undecided) | Undetermined, operation, `partial` | opaque | none / `nexus-opaque-operation` warning |
| partial, ≥ 1 id | ≥ 1 not provided (with any others) | Incompatible, `notProvided` | incompatible | `nexus-incompatible-target-capability` error / the same |

Every well-formed declaration matches exactly one row. An `error` appears only in the two rows where a declared requirement is explicitly not provided (I16). No row turns missing or undecided information into `incompatible` or `error` (I12).

## Implementation discipline: exactly what the analysis reads and writes

This makes I11 and C7's purity concrete. It is a coding rule, tested by Tasks 8 and 9, not a sandbox.

**Reads.** The analysis reads only these fields, by plain property access:

| From | Fields |
|---|---|
| the context | `declarations`, `profile`, `require` |
| each declaration | `id`, `name`, `provenance`, `requirements` |
| a requirements fact | `completeness`, `capabilities` |
| each requirement | `capability`, `provenance` |
| the profile | `name`, `provenance`, `provided`, `notProvided` |
| each span | `source`, `start`, `end` |
| each modeled array (`declarations`, `capabilities`, `provided`, `notProvided`, `require`) | `length`, and indices `0 … length − 1` |

Presence of an optional field is tested with `!== undefined`, never with `in` or `hasOwnProperty`.

**Writes.**
- The analysis never writes to, defines on, deletes from or reorders any input object or array.
- The outcome contains only the public model's fields, built from fresh object and array literals.
- Every output span is a new `{ source, start, end }`, copied field by field.
- Output never aliases input.

**Coding rules in `src/semantic/`.** These rules guide the implementer. The tests check their observable effects (Tasks 8 and 9), not the coding style, except for the ambient channels C7 names (clock, environment, file, network), which Task 9 also scans for statically, because Node's global types make them usable without an import. Forbidden:
- calling, constructing or awaiting any value taken from the input;
- iterating a caller array with `for…of`, spread, destructuring, `Array.from`, or any array method (`map`, `filter`, `some`, `includes`, `indexOf`, `sort`, `forEach`, …). Caller arrays are walked only with an indexed `for` loop over `length`.
- over caller objects: `Object.keys`, `Object.values`, `Object.entries`, `Object.assign`, `Reflect.*`, `in` or `hasOwnProperty`, or spreading them;
- `JSON.*` and `structuredClone`;
- `async`, `await` and `Promise`;
- `process`, `globalThis`, `Date`, `Math.random`, `performance`, timers, `fetch`, `require(`, triple-slash references, and any module-level `let` or mutable module-level collection.

Internal working collections, such as a private `Set` of profile ids built by indexed reads, are allowed. The analysis creates them per call, never exposes them, and never stores caller objects in them, only caller strings.

**Not a goal:** defending against accessor properties or `Proxy`s on the modeled fields themselves. Reading a modeled field is part of the contract, and any getter on it is the caller's code, not the operation's implementation. The reference page says so. The tests pin that nothing *beyond* the modeled fields is touched, and that nothing is written.

## Risks (plan-level; the outline's R1–R6 still apply)

- **Structural typing** can't reject a matching-shape class instance, or a variable with extra properties (Task 10). Tasks 8 and 9 cover that at runtime.
- **Type tests can pass vacuously.** Task 10's breaks show that they fail when the model is widened.
- **The static scan (Task 9) is text-based.** It can false-positive on a word in a comment. The rule is to reword the comment, never to weaken the scan.
- **Accessors on modeled fields** run the caller's code when read. That is inside the contract and documented, not defended against.
- **Caller strings in messages.** A display name, id or profile name is inserted verbatim, so a caller could put an escape sequence in its own name. I13 forbids NEXUS from adding escape sequences or markup. It doesn't make NEXUS sanitize caller data, and v0.4 doesn't.

### Open point O1: `Capability` is structurally a `Declaration`

- `Capability<Shape>` is `{ readonly id: string; readonly tag: … }`. `Declaration` requires only `id: string`, and its other parts are optional. TypeScript is structural, so a `Capability` value is assignable to `Declaration`, and a `Capability[]` to `AnalysisContext["declarations"]`.
- DoD 12 asks for "a type-level test [showing] that the semantic model accepts no `Capability`, `CapabilityResolution` or `EnvironmentShape`". `CapabilityResolution` and `EnvironmentShape` have no `id`, and are rejected, as tested. `Capability` can't be rejected under the model as D5 fixes it.
- **Runtime behaviour is unaffected.** Passed as a declaration, a `Capability` is read only through the declaration fields (`id`, `name`, `provenance`, `requirements`); the proxy test proves analysis reads nothing else. So it is analyzed as an operation with unknown requirements: opaque. Its `tag` is never read, and nothing is resolved (I15 holds at runtime).
- **What would close it,** for the outline's owner:
  - **(a)** Add a type-only guard to `Declaration`, `readonly tag?: never`. This changes D5's "exactly these parts" and C1's table, so it needs an outline amendment.
  - **(b)** Amend DoD 12's type-level clause to cover what TypeScript can express: no `Capability`, `CapabilityResolution` or `EnvironmentShape` type appears in, or is required by, the model. The runtime and I15 guarantees stay as they are.
- The plan recommends **(b)**: it keeps the plain model unchanged, and the runtime guarantee is already proven. Nothing else depends on the choice.
