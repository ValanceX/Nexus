- **Plain data everywhere** (C1, I13, I18). - **Rejection is not a diagnostic** (D6, C7). Throughout the plan:

  | Input | Outcome |
  |---|---|
  | malformed context (one of D6's five cases) | `Rejected`, with rejection issues; no operation results, no diagnostics |
  | well-formed, insufficient semantic information | `Analyzed`; the operation is *opaque*, and a `warning` exists only if `target-compatibility` is required (C5) |
  | well-formed, established incompatibility | `Analyzed`; the operation is *incompatible*, with exactly one `error` |

- **Tests assert on data, never on message text** (DoD 7): codes, severities, subjects, locations, spans, verdicts and classifications. `message` and each note are asserted only to be non-empty strings.
- **Conventions:** `.js` extensions on relative imports; no `any`; `_tag`ged plain-object unions; no Effect in the module (D11).

## The public model

The complete public surface of `src/semantic/index.ts`. Nothing else is exported. The outline's working terms map as commented.

```ts
// C2: provenance. Offsets are UTF-16 code units, zero-based, half-open (P4).
export interface Span {
  readonly source: string;   // opaque source identity; non-empty
  readonly start: number;
  readonly end: number;
}

// C4: one entry of the target-requirements fact
export interface Requirement {
  readonly capability: string;        // target capability id; non-empty
  readonly provenance?: Span;
}

// C3/C4: the one v0.4 semantic property
export interface TargetRequirements {
  readonly completeness: "complete" | "partial";
  readonly capabilities: ReadonlyArray<Requirement>;
}

// C1: the semantic declaration (exactly these parts; D5)
export interface Declaration {
  readonly id: string;                          // semantic identity (D4)
  readonly name?: string;                       // display name; never identity
  readonly provenance?: Span;
  readonly requirements?: TargetRequirements;   // absent = unknown (I14)
}

// C4: the target profile (explicit input; D8)
export interface TargetProfile {
  readonly name: string;
  readonly provenance?: Span;
  readonly provided: ReadonlyArray<string>;
  readonly notProvided: ReadonlyArray<string>;
}

export type Property = "target-requirements";        // C3: the v0.4 property set
export type RequiredFact = "target-compatibility";   // C5: the only fact that can be required

// C7 input: the analysis context
export interface AnalysisContext {
  readonly declarations: ReadonlyArray<Declaration>;
  readonly profile: TargetProfile;
  readonly require?: ReadonlyArray<RequiredFact>;
}

// C4: the verdict, with its cause. It carries every fact a diagnostic asserts (C5).
export type Verdict =
  | { readonly _tag: "Compatible" }
  | { readonly _tag: "Incompatible"; readonly notProvided: ReadonlyArray<string> }
  | { readonly _tag: "Undetermined"; readonly cause: "operation"; readonly requirements: "undeclared" | "partial" }
  | { readonly _tag: "Undetermined"; readonly cause: "target"; readonly undecided: ReadonlyArray<string> };

// C5: derived from the verdict, one to one
export type Classification = "supported" | "opaque" | "incompatible";

// C7: one entry per declaration
export interface OperationResult {
  readonly id: string;
  readonly known: ReadonlyArray<Property>;
  readonly verdict: Verdict;
  readonly classification: Classification;
}

// C6
export type DiagnosticCode =
  | "nexus-incompatible-target-capability"
  | "nexus-opaque-operation"
  | "nexus-undetermined-target-capability";
export type Severity = "warning" | "error";
export type Location =
  | { readonly _tag: "Span"; readonly span: Span }
  | { readonly _tag: "Unlocated" };
export interface RelatedSpan { readonly span: Span; readonly label: string }
export interface Diagnostic {
  readonly code: DiagnosticCode;
  readonly severity: Severity;
  readonly message: string;
  readonly location: Location;       // primary location, or explicitly unlocated (C2)
  readonly subject: string;          // the operation's semantic identity
  readonly related: ReadonlyArray<RelatedSpan>;
  readonly notes: ReadonlyArray<string>;
}

// D6: a malformed context. Not a diagnostic.
export type RejectionReason =
  | "duplicate-identity"     // D6 case 1
  | "missing-identity"       // D6 case 2
  | "invalid-span"           // D6 case 3: end < start, or an empty source
  | "empty-capability"       // D6 case 4
  | "conflicting-decision";  // D6 case 5
export interface RejectionIssue {
  readonly reason: RejectionReason;
  readonly path: ReadonlyArray<string | number>;
}

// C7 output: exactly one of these
export type AnalysisOutcome =
  | {
      readonly _tag: "Analyzed";
      readonly properties: ReadonlyArray<Property>;     // always ["target-requirements"]
      readonly required: ReadonlyArray<RequiredFact>;   // [] or ["target-compatibility"]
      readonly profile: string;                         // the profile's name
      readonly operations: ReadonlyArray<OperationResult>;
      readonly diagnostics: ReadonlyArray<Diagnostic>;
    }
  | { readonly _tag: "Rejected"; readonly issues: ReadonlyArray<RejectionIssue> };

export const analyze: (context: AnalysisContext) => AnalysisOutcome;
```

**Why the result keeps the verdict next to the classification.** C7 requires each entry to carry the "verdict with cause" and the classification. The classification is a one-to-one summary. The verdict is the structured cause a consumer reads: which ids are not provided (incompatible), whether requirements are undeclared or partial (opaque, operation-side), or which ids the profile leaves undecided (opaque, target-side). No consumer ever has to parse a message (C5: "the result is authoritative").

**Deliberately absent from the model:** predefined capability ids or profiles (D8); any field about what a consumer should do (C6, L3); fixes (D12); inputs, outputs, effects, determinism, cacheability or relationships (C3, D5); any link to `Capability`, `Environment` or `Command` (I15, D7).

### Duplicate requirements (P7)

- Duplicate target capability ids within one requirement set are **valid input**.
- Compatibility is evaluated against the **distinct** ids. `notProvided` and `undecided` in the verdict list each distinct id once, in order of first occurrence.
- Duplicates never create extra findings. An operation still has one verdict, one classification and at most one diagnostic.
- Every occurrence's provenance stays available. Where C6 requires related spans for a requirement (the error, and the target-side warning), each occurrence that carries provenance contributes one related span, in original declaration order.

## The algorithm

Rejection comes first. For a context that isn't rejected, each declaration is analyzed in order.

### Rejection (D6, exactly five cases)

The whole context is checked. If any issue is found, the outcome is `Rejected` with every issue, in input order, and nothing is analyzed.

| D6 case | `reason` | Detected when | `path` |
|---|---|---|---|
| 1 | `duplicate-identity` | a declaration's `id` equals an earlier declaration's `id` | the later declaration: `["declarations", i, "id"]` |
| 2 | `missing-identity` | a declaration's `id` isn't a non-empty string | `["declarations", i, "id"]` |
| 3 | `invalid-span` | a declaration's, a requirement's or the profile's span has `end < start` or an empty `source` | the span's path, e.g. `["declarations", i, "requirements", "capabilities", j, "provenance"]` |
| 4 | `empty-capability` | a requirement's `capability`, or an entry of `provided` or `notProvided`, is `""` | that entry's path |
| 5 | `conflicting-decision` | an id appears in both `provided` and `notProvided` | the first `notProvided` index of that id, reported once per id |

Nothing else is rejected. In particular these are well-formed: no declarations; a declaration with no facts; an empty complete set; duplicate ids in one requirement set; an id repeated within `provided` (or within `notProvided`); a profile deciding nothing; an empty display name; an empty profile name; an empty span; unknown or unused capability ids. (See "Open points" for offsets that are negative, fractional or `NaN`.)

### Analysis of one well-formed declaration

1. **`known`** is `["target-requirements"]` exactly when `requirements` is present, else `[]`.
2. **Verdict** (C4). Let `ids` be the distinct required ids, in order of first occurrence:
   1. requirements present, and some id is in `notProvided` → `Incompatible`, listing those ids;
   2. otherwise, requirements absent → `Undetermined`, `cause: "operation"`, `requirements: "undeclared"`;
   3. otherwise, `completeness: "partial"` → `Undetermined`, `cause: "operation"`, `requirements: "partial"`;
   4. otherwise, some id is in neither list → `Undetermined`, `cause: "target"`, listing those ids;
   5. otherwise → `Compatible` (including the empty complete set).

   Step 1 first: a partial set with a not-provided id is incompatible (DoD 4). Steps 2–3 before step 4: "if both apply, the cause is operation-side" (C4).
3. **Classification**: `Compatible` → `supported`; `Undetermined` → `opaque`; `Incompatible` → `incompatible` (C5).
4. **Emission** (C5 rules 1–4):
   - `incompatible` → one `nexus-incompatible-target-capability`, `error`, whatever is required;
   - `supported` → none;
   - `opaque` and `target-compatibility` required → one `warning`: `nexus-opaque-operation` for an operation-side cause, `nexus-undetermined-target-capability` for a target-side cause;
   - `opaque` and nothing required → none.
5. **Location**: `{ _tag: "Span", span }` with a fresh copy of the declaration's provenance if it has one; otherwise `{ _tag: "Unlocated" }`. Never a borrowed span (I17).
6. **Related spans** (C6's table):
   - error: each not-provided requirement occurrence with provenance, labelled `"requirement declared here"`, then the profile's provenance, if any, labelled `"target profile declared here"`;
   - target-side warning: each undecided requirement occurrence with provenance, labelled `"requirement declared here"`;
   - operation-side warning: none.
7. **Notes** state C6's "notes must state" column, built only from the verdict and the profile's name: the capability ids and the profile's name (error); whether requirements are undeclared or partial, and that the operation still executes normally (operation-side warning); the capability ids and that the profile doesn't decide them (target-side warning). Notes and messages state findings, never consumer actions (C6: "Meaning, not action").

Diagnostics follow declaration order (C6).

## Implementation discipline: exactly what the analysis reads and writes

This makes I11 and C7's purity concrete. It is a coding rule with tests (Tasks 8–9), not a sandbox.

**Reads.** The analysis reads only these fields, by plain property access:

| From | Fields |
|---|---|
| the context | `declarations`, `profile`, `require` |
| each declaration | `id`, `name`, `provenance`, `requirements` |
| a requirements fact | `completeness`, `capabilities` |
| each requirement | `capability`, `provenance` |
| the profile | `name`, `provenance`, `provided`, `notProvided` |
| each span | `source`, `start`, `end` |
| each modeled array (`declarations`, `capabilities`, `provided`, `notProvided`, `require`) | `length`, and indices `0 … length − 1` |

**Writes.** The outcome consists only of the fields in the public model, built from fresh object and array literals. Every output span is a new `{ source, start, end }` copied field by field. Optional parts are omitted, never set to `undefined`. Output never aliases input.

**Forbidden in `src/semantic/`:**
- calling, constructing or awaiting any value that came from the input;
- iterating caller arrays with `for…of`, spread, destructuring, `Array.from`, or any array method (`map`, `filter`, `some`, `includes`, `indexOf`, `forEach`, …); caller arrays are walked only with an indexed `for` loop over `length`;
- `Object.keys`, `Object.values`, `Object.entries`, `Object.assign`, `Reflect.*`, `in` or `hasOwnProperty` over caller objects, or spreading them;
- `JSON.*`, `structuredClone`, `String(x)` or template interpolation of non-string caller values (ids and names are read as the strings the types say they are);
- `async`, `await`, `Promise`;
- `process`, `globalThis`, `Date`, `Math.random`, `performance`, timers, and any module-level mutable state.

Internal working collections (for example a private `Set` of profile ids built by indexed reads) are fine: they are created by the analysis, never exposed, and never hold caller objects beyond their string values.

**Not a goal:** defending against accessor properties or `Proxy` objects on the modeled fields themselves. Reading a modeled field is part of the contract; any getter on it is the caller's code, not the operation's implementation. The reference page says so. What the tests pin is that nothing *beyond* the modeled fields is touched.

- **Exactly three codes, two severities:** across the matrix, the set of codes seen is exactly the three, and of severities exactly `warning` and `error`.
- **Error only with proof** (I12): `error` appears only for incompatible operations; `warning` only for opaque ones.
- **At most one per operation,** duplicates included: an incompatible `["fs", "fs"]` gives one error.
- **Order:** diagnostics follow declaration order; reordering the declarations reorders the diagnostics and nothing else.
- **Stable structured code:** each diagnostic's `code` is one of the three literals; its `subject` equals the operation's `id`; joining diagnostics to `operations` by `subject` succeeds for every diagnostic.
- **Primary location:** a declaration with a span → `location.span` deep-equals it; without one → `location` is exactly `{ _tag: "Unlocated" }`, `subject` is still set, and the diagnostic is otherwise complete (a valid diagnostic).
- **Related spans:**
  - error: each not-provided occurrence's span, in declaration order (both occurrences of a duplicated `fs` with spans), then the profile's span; occurrences without provenance contribute nothing; no profile span → none for it;
  - target-side warning: each undecided occurrence's span, in order;
  - operation-side warning: `related` is `[]`.
- **No fabricated span** (I17): the set of spans in all diagnostics, compared by value, is a subset of the spans in the input; an unlocated declaration's diagnostic never carries the profile's or a requirement's span as its location.
- **Findings, not actions** (C6): each diagnostic's own keys are exactly `code`, `severity`, `message`, `location`, `subject`, `related`, `notes`; `message` is a non-empty string; `notes` is a non-empty array of non-empty strings for every code. No test asserts message wording.

**Change:** emission, location, related spans, messages and notes as in "The algorithm".

### Task 8: Freshness, JSON compatibility, determinism and UTF-16 spans (I13, I17; DoD 6, 7)

**Files:** `tests/semantic.test.ts`. Tests only; a `src/` change happens only if a test exposes a bug.

**Tests:**
- **Fresh spans:** for every span in an outcome (locations and related spans), the output span is `!==` the input span it came from, and `Object.keys` of it (in the test, not the analysis) is exactly `["source", "start", "end"]`.
- **No forged properties:** an input span carrying extra properties (`label`, `excerpt`, a function `toJSON`, a nested object) yields an output span with only `source`, `start`, `end`, and the function was never called.
- **No aliasing:** after analysis, mutate every caller-owned input object and array (spans' offsets, requirement arrays, profile arrays, declaration ids). The outcome deep-equals a `structuredClone` taken before the mutation.
- **JSON-compatible plain data:** every outcome produced in `tests/semantic.test.ts` (collected through a shared helper) is `toStrictEqual` to `JSON.parse(JSON.stringify(outcome))`; that proves no `undefined`-valued keys, functions, class instances or non-JSON values.
- **Determinism:** two equal contexts, built separately, give deeply equal outcomes; analyzing the same context twice gives deeply equal outcomes.
- **Two throwaway renderers,** local to the test (R1; not deliverables, not a CLI format): a plain-text one (`"<source>:<start>-<end> <severity> <code>"`, or `"<subject> (no source span) <severity> <code>"`) and a structured one (an array of `{ code, severity, subject, where }`). Both render the full Task 7 matrix, and afterwards the diagnostics deep-equal a clone taken before rendering.
- **UTF-16 code units, observably** (P4): the test holds source text `const e = "😀"; fs();`. `😀` is one Unicode scalar value, one grapheme cluster and two UTF-16 code units. A requirement's span is written for `fs()` as UTF-16 offsets (`text.indexOf("fs()")`, and `+ 4`). The test asserts:
  - the analysis returns that span unchanged in the error's related spans;
  - `text.slice(start, end) === "fs()"`, the mapping the reference page documents;
  - the code-point offset (`[...text.slice(0, start)].length`) is one less than `start`, so a consumer counting scalar values or graphemes would land one position off. The documented contract is therefore observable, not incidental.

  The analysis itself never interprets offsets beyond D6's `end < start` check; this test pins the contract the reference page states and the provenance pass-through (I17).

### Task 9: Purity, non-invocation and execution independence (I11, I12, I15, I16, I19; D3, D10, D15; DoD 3, 9, 10, 11, 12, 13, 15)

**Files:** new `tests/semantic-isolation.test.ts`. Tests only; a `src/` change happens only if a test exposes a bug.

**Tests:**
- **Reads only the modeled fields** (V3): the context, every declaration, requirements fact, requirement, span and the profile are wrapped in recording `Proxy`s; every modeled array too. ### Task 10: Compile-time public-boundary tests (C1, I13, I15, I18; DoD 10, 11, 12 type parts)

## Risks (plan-level; the outline's R1–R6 still apply)

- **Structural typing** can't reject a matching-shape class instance or a variable with extra properties (Task 10). Covered at runtime by Tasks 8 and 9.
- **Type tests can pass vacuously.** Task 10's bite check shows they fail when the model is widened.
- **The static scan (Task 9) is text-based.** It can false-positive on a word in a comment; the rule is to reword the comment, not to weaken the scan.
- **Accessors on modeled fields** run the caller's code when read. That is inside the contract and documented, not defended against.

## Open points

These don't block Tasks 0–12, and the plan doesn't decide them. Each is recorded so the outline's owner can settle it, possibly by amending the outline.

1. **Offsets that aren't non-negative integers.** D6 case 3 rejects only `end < start` and an empty source. A span with a negative, fractional or `NaN` offset is therefore well-formed as written (and `NaN < NaN` is false, so a `NaN` span passes). The plan implements D6 exactly and adds no category. If the outline is amended, the change is one more condition under `invalid-span` and one more Task 3 test.
2. **Input that violates the public types at runtime.** C7 promises a total function "over well-formed input", and D6 lists what's malformed. Neither says what happens when a JavaScript caller passes a value the TypeScript types exclude (for example `declarations: 5`, or a number where an id string belongs, beyond D6 case 2). The plan treats such input as outside the contract: the analysis still never invokes or iterates it (Task 9's rules hold), but whether it returns, throws or rejects is not specified or tested.

The earlier draft's open points on UTF-16 (P4), duplicates (P7), empty names and the page location (P8) are settled by the review and by D6's exhaustiveness.
