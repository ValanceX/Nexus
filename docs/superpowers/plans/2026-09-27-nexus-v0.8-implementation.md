# NEXUS v0.8 Application Semantics Implementation Plan

**Status:** Approved and executed (2026-09-27). The v0.8.0 release commit is made, with no tag, pending the final implementation review. See "As built".

**Goal:** Establish the v0.8 application-semantics contract (outline Revision 2: C24–C28, D56–D67, I39–I43) with **no change to `src/`**. The deliverables are test tooling and documentation only:
- requirements are owned by execution units, meaning the start unit and admitted units (D57);
- each unit is described by one standalone `Semantic.Declaration` (D56, D62);
- application necessity is the start unit's requirement (C27);
- the application requirement set and application classification are the C26 aggregation, computed only by test tooling (D61, D66);
- a declaration identifies a unit only within its context. Any mapping to a NEXUS primitive identity is the producer's, outside the contract (D65, Revision 2);
- a context contains the units its producer has chosen to describe, and is never implied to be complete (D59, Revision 2; O13 deferred);
- runtime behavior is unchanged (I37, I39, I43, D67).

**Spec:** `docs/superpowers/specs/2026-09-27-nexus-v0.8-outline.md`, Revision 2. **The outline wins wherever the two disagree**, except for the ordering of test tasks, which follows the review decision (see "Contradictions", item 1). Evidence: `docs/architecture/2026-09-27-application-semantics-audit.md` (ASA).

**Baseline:** `main` at `eafe012` (v0.7.0), plus the audit and outline commits on `claude/nexus-v0.8-semantics-audit-crhmzp`. That is **366 tests in 26 files**.

**Tech stack:** TypeScript 5.6 (strict), Effect 3.22, Vitest 2, pnpm 10.

## Four concepts that stay separate

Every test and every document in this plan must keep these apart:

```text
start-unit necessity          the start unit's declared requirement: the application can't start without it     (C27)
        ≠
application requirement set   the C26 union over the units the context describes: some unit can't work without it (C26)
        ≠
runtime capability resolution what the platform Layer built: Available / Unavailable, for one start              (D36, I36)
        ≠
static compatibility verdict  Semantic.analyze over declarations × a platform statement                          (C4, C20)
```

- A static *incompatible* verdict must never alter runtime behavior: start, admission, resolution or the unit's own execution (I37).
- A unit requirement must never become an application start requirement merely because the unit belongs to the application (I41).
- No code path in NEXUS connects the four. The only links are ones a test (or a future consumer) writes explicitly.

## Global constraints

- **No `src/` change.** `git diff eafe012 -- src` must be empty at every commit. **`src/semantic` in particular is never modified in a commit.**
- **No existing test is modified or deleted.** New tests go in one new file, `tests/application-semantics.test.ts`.
- **Test tooling is local.** The C26 aggregation helper is a non-exported function inside the new test file.
  - It is not a new module under `tests/`, so no new architecture block is needed.
  - It is not in `src/` and not in `dist/`.
  - It imports nothing but the public namespaces the test file already uses.
- **The new test file imports only `effect`, `vitest` and `src/` modules.** It imports no Node builtin, MESH package or PORT package.
- **Forbidden, in tests as in `src/`:**
  - requirement fields, metadata bags, decorators or annotations on any primitive, definition, `Layer` or start option;
  - registries or unit inventories;
  - automatic discovery;
  - source, type or runtime-derived requirement capture;
  - enforcement or gating, at start or at dispatch;
  - aggregate exports;
  - containment or inheritance;
  - capability provenance;
  - PORT or MESH integration.
- **O11–O14 are not solved.** No test anticipates them. In particular, no test treats a context as complete (O13) or introduces a start-unit kind (O12).
- **No unit-id convention (D65).** Test declaration ids are deliberately *not* equal to the `Command.name` or `Application.name` of the code they describe, wherever both appear in one test. The test data then can't read as establishing a join.
- **The final tree carries none of the deliberate breaks.** Breaks are applied to the working tree only, never committed, and reverted with `git checkout`.
- **Commits:** one per task, with the repository's trailers. No commit uses a model identifier.

### Task 2. Characterizations (outline tests 2 and 5, plus D62)

Create `tests/application-semantics.test.ts` with a first `describe` block, *"Application semantics: characterizations (v0.8)"*. It pins existing behavior only.

Shared fixtures, at the top of the file:
- two capability contracts, `Network = Capability.define("acme.network")` and `Storage = Capability.define("acme.storage")`;
- a `UserRepository` service with two implementations:
  - `Http`, which captures the `Environment` at build and `require`s `Network` in its method;
  - `InMemory`, which requires nothing;
- one `Command`, `listUsers`, calling the service;
- a `statement(provided, notProvided)` helper, as in `capability-model.test.ts`;
- a `requires(...)` helper building `complete` `TargetRequirements`.

Tests:
1. **The same `Command` value behaves differently under two compositions** (Y3, I42). The platform supplies no `Network`:
   - under `Http`, `Command.invoke(listUsers, {})` fails with `CapabilityUnavailableError`;
   - under `InMemory`, it succeeds.
2. **Two compositions are two contexts** (C24). The `Http` context declares the unit with `complete [Network.id]`, and the `InMemory` context with `complete []`. Against `statement([], [Network.id])` they give *incompatible* and *supported*. Re-running test 1's behavior after both analyses gives identical results.
3. **Overlapping units are accepted and undetected** (C25, Y2). A unit `whole` (`complete [Storage.id]`) and a unit `list` (`complete [Network.id]`) against `statement([Storage.id], [Network.id])`:
   - the outcome is `Analyzed`, with no rejection;
   - `whole` is supported and `list` is incompatible;
   - the outcome has no field relating the two.
4. **One unit, one declaration** (D62, C9). Two declarations with the same `id` in one context give `Rejected` with `duplicate-identity` at the second.

Verification: `pnpm test`, with 366 + 4 passing. `pnpm typecheck` clean. Commit: *"test: v0.8 application-semantics characterizations"*.

### Task 3. The aggregation, in local test tooling (outline test 3; C26)

Add a local, non-exported helper `aggregate(outcome, declarations)`. It returns plain data, `{ capabilities, occurrences, completeness, classification }`, computed **only** from:
- the public `Analyzed` outcome, for classifications;
- the plain-data declarations the test itself wrote, for requirement occurrences.

It reads no runtime value. Its rules are C26's, verbatim:
- `capabilities`: the distinct ids, in first-occurrence order (declaration order, then capability order);
- `occurrences`: every occurrence as `{ unit, capability, provenance }`, in the same order;
- `completeness`: `complete` exactly when every declaration has `complete` requirements, otherwise `partial`. An undeclared unit counts as partial-empty;
- `classification`: incompatible over opaque over supported. Empty is `supported`.

It produces no verdict cause (C26, "Verdict cause").

A second `describe` block, *"Application semantics: the aggregation algebra (v0.8 C26)"*:
1. **Exhaustive equivalence** (Y1). Over 0–3 units, the 9 requirement states over `{a, b}`, and the 9 profiles: `aggregate(...).classification` equals the classification `Semantic.analyze` gives one declaration carrying the union. Assert **7,380** cases and zero mismatches.
2. **Counter-check.** Treating an undeclared unit as *absent* in the union gives `opaque`, while `aggregate` gives `incompatible`, for `[{ id: "u0" }, { id: "u1", complete [a] }]` against `notProvided: [a]`. This pins the partial-empty rule.
3. **Order.** Three units requiring `[b]`, `[a, b]` and `[c, a]` give `capabilities` `["b", "a", "c"]`.
4. **Cross-unit duplicates keep every occurrence**, each attributed to its unit and carrying its span, in order.
5. **Partial opens.** One `partial` unit makes `completeness` `partial` and the classification `opaque`. With another unit incompatible it is `incompatible` (C4 step 1 first).
6. **Empty context.** Zero units give `capabilities: []`, `completeness: "complete"`, and `supported` (vacuous; relative to the context).

Verification: all pass, and typecheck is clean. Commit: *"test: v0.8 aggregation algebra as local test tooling"*.

### Task 4. Lifecycle and unit characterization (outline tests 1 and 4; C27, I41)

A third `describe` block, *"Application semantics: units in the lifecycle (v0.8 C27)"*. Every test starts a real application on `Capability.EnvironmentLive(...)`.

1. **The start unit's requirement is start necessity** (Y5). A `runtime` layer whose implementation `require`s `Storage` *while building*, on a platform without `Storage`:
   - `start` fails with `ServiceGraphFailed`;
   - no `RunningApplication` is returned.
2. **An admitted unit's requirement is only that unit's** (Y5). `runtime: Layer.empty`. A command that `require`s `Storage`, and a second command that requires nothing, on the same platform:
   - the application is `Running`;
   - the first command fails with `CapabilityUnavailableError`;
   - the second succeeds;
   - the status is still `Running` afterwards.
3. **An incompatible admitted unit doesn't make the application necessity incompatible** (C27, I41). The context has:
   - a start unit declared `complete []`;
   - admitted unit `save`, `complete [Storage.id]`;
   - admitted unit `list`, `complete []`.

   Against `statement([], [Storage.id])`:
   - the start unit is `supported`, and `save` is `incompatible`;
   - `aggregate(...).classification` is `incompatible`, and its `capabilities` are `[Storage.id]`;
   - starting on a platform matching the statement (no `Storage`) succeeds, and `list` runs;
   - the start unit's declared requirements (necessity) don't include `Storage.id`. The union does. The two are asserted unequal.
4. **The requirement set ≠ runtime resolution ≠ verdict.** In the same application, `Capability.resolve(Storage)` is exactly the Layer's `Unavailable`. The analysis outcome is `toStrictEqual` before and after starting.

Verification: all pass. Commit: *"test: v0.8 units in the lifecycle"*.

### Task 5. Independence and no-attachment (outline tests 6 and 7; I36, I37, I39, I43, D67)

A fourth `describe` block, *"Application semantics: independence and no attachment (v0.8)"*.

No attachment (I39):
1. `Object.keys(Command.define("x", Schema.Number, h))` is exactly `["name", "input", "handler"]`.
2. `Object.keys(Application.define(definition))` is exactly `["definition"]`, and `.definition` is the passed object itself, unchanged. `define` adds nothing.
3. **Type test:** `expectTypeOf<Application.ApplicationDefinition<never>>()` equals `{ readonly name: string; readonly runtime: Layer.Layer<never, unknown, Application.ApplicationAmbient> }`. Like the D42 test, this bites under `pnpm typecheck`, not under vitest.

Independence (I36, I37, I43):

4–9. For each application classification (supported, opaque, incompatible), with a three-unit context, × the platform Layer supplying `Storage` `Available` or `Unavailable` (6 cases):
   - `start` reaches `Running`;
   - `resolve(Storage)` is exactly the Layer's resolution;
   - `require(Storage)` succeeds exactly when the Layer supplies it;
   - the analysis outcome is unchanged by starting.

10. **A static incompatibility doesn't alter the unit's own runtime behavior.** Unit `save` is *incompatible* against `statement([], [Storage.id])`. On a platform that *does* supply `Storage`, `save` runs and succeeds, returning the implementation's value.

Verification: `pnpm typecheck` clean, `pnpm test` all pass, `pnpm build` clean, and `git diff eafe012 -- src` empty. Commit: *"test: v0.8 independence and no attachment"*.

## Contradictions between the approved outline and this plan

Found while writing the plan. None changes an approved decision. Each is resolved as stated, and awaits the reviewer's confirmation.

1. **Task order.** Outline §22 puts the lifecycle test (outline test 1) with the characterizations. It puts test 4 (no inheritance of necessity) with independence. The review requires: characterizations → aggregation → lifecycle/unit → independence and no-attachment. **Resolved in favor of the review.** Outline tests 2 and 5 are Task 2, test 3 is Task 3, tests 1 and 4 are Task 4, and tests 6 and 7 are Task 5. No test is added or dropped.
2. **The `ApplicationDefinition` break is caught by typecheck, not vitest.** Outline §T lists it as caught by "test 6 (type test)". Vitest doesn't type-check, as in v0.6 and v0.7 (B6 there). **Resolved:** B3's gate is `pnpm typecheck`, which is part of Task 9's gate and of CI.
3. **The outline's "Semantic gains any overlap or containment rejection" break would require editing `src/semantic`.** Every other break touches `src/` only in the working tree, and is never committed, as in v0.7. But the review's constraint "Do not modify `src/semantic`" is unqualified. **Resolved conservatively:** that break is not applied (Task 6), and Task 2 test 3 still pins the behavior. If the reviewer confirms that working-tree-only breaks in `src/semantic` are acceptable, it can be added as B10.
4. **Outline §T mentions "the existing `StartOptions` test is unchanged".** This plan adds no new `StartOptions` assertion, and relies on `tests/platform.test.ts:88` as is. There is no conflict. It is noted only because §T lists it under test 6.
5. **Outline §T test 7 ("independence … for an application context with several units")** doesn't fix the number of cases. This plan uses 3 classifications × 2 Layer states, mirroring v0.7. There is no conflict.

No contradiction was found with the approved core direction, with D65 as revised, or with the "not an inventory" revision.
