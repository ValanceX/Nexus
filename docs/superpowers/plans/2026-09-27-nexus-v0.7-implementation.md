# NEXUS v0.7 Platform Capability Model Implementation Plan

**Status:** Executed (2026-09-27). Awaiting the release decision. The outline was approved with one clarification to C21, applied here (below).

**Goal:** Establish the platform capability model defined in the v0.7 outline with **no change to `src/`**:
- the platform binding (D44), where a semantic capability identifier is `Capability.id` verbatim;
- a requirement means necessity (D46);
- a platform provision is a platform-authored claim (D47);
- the claim is checked against the `Layer` only by test tooling (C21);
- runtime behavior is unchanged (D49, D55).

**Spec:** `docs/superpowers/specs/2026-09-27-nexus-v0.7-outline.md`. The outline wins wherever the two disagree. Evidence: `docs/architecture/2026-09-27-capability-model-audit.md`.

**Tech stack:** TypeScript 5.6 (strict), Effect 3.22, Vitest 2, pnpm 10.

## Approval clarification: C21 is test infrastructure only

The conformance helper (`tests/platform/conformance.ts`) is not any of these:
- a public NEXUS API;
- a runtime capability validator;
- a Semantic API;
- an `Application.start` option;
- a platform registry;
- runtime introspection;
- profile generation;
- runtime gating.

It tests a platform author's claim against the actual `Layer`, and nothing else.

```text
STATIC CLAIM                                   TEST-TIME CONFORMANCE
platform provision statement                   platform Layer
          │                                          │
          ▼                                          ▼
     Semantic.analyze                          Application.start
          │                                          │
          ▼                                          ▼
       verdict                                  Environment
                                                     │
                                                     ▼
                                            conformance helper
                                                     │
                                                     ▼
                                   does runtime behavior agree with the statement?
```

No runtime path connects a Semantic verdict to application startup or execution.

The three provision states:

| State | Meaning |
|---|---|
| `provided` | the platform promises that every start makes this capability `Available` |
| `notProvided` | the platform promises that this capability is not `Available` through this platform's `Environment`. It is a promise, not "no implementation happens to exist today" |
| neither | undecided, conditional or not claimed: permissions, optional hardware, remote state, user configuration, or any other runtime condition, unless the platform can make a stronger claim |

The conformance helper reports every `provided` id that doesn't resolve `Available`, and every `notProvided` id that doesn't resolve `Unavailable`. It never reports an undecided id.

**Deviations from the outline's §T.**
- The characterizations are in their own file, `tests/capability-characterization.test.ts`, not in `capability-model.test.ts`, so that Task 2 could be reviewed on its own.
