# NEXUS v0.2: the MESH runtime adapter

*Design spec, 2026-09-26. Status: awaiting review.*

## 1. Goal

v0.2 is done when a NEXUS application, in Node, drives MESH v0.5 end to end, and tests prove it:

```text
NEXUS State ─▶ Selector ─▶ snapshot ─▶ mesh-runtime render() ─▶ Render (tree)
                                                                   │  user event
NEXUS Command.invoke ◀─ adapter's command table ◀─ intent ◀─ dispatch(that Render, handler, payload)
```

**The acceptance boundary is that slice running, not "the adapter compiles".** §7 lists the tests that have to pass. Each of them runs the published `@valancex/mesh-runtime@0.5.0` against MESH's own `examples/slice` program.

## 2. Scope

In:

1. Rename `@valence/nexus` to `@valancex/nexus`. This covers `package.json`, `README.md` and `docs/ARCHITECTURE.md`. Nothing else in the repo names the package.
2. Update the architecture for MESH v0.5 (§4). The "Semantic IR" model is gone: MESH produces templates, render trees and command intents.
3. Add the adapter, `src/mesh/`, exported as `Mesh` (§5).
4. Add the Node vertical-slice acceptance tests, plus lifecycle and error tests (§7).
5. Add basic CI. That's one GitHub Actions workflow that runs `pnpm typecheck`, `pnpm test` and `pnpm build` on Node 22 and 24.

Out: npm publishing, PORT, a browser or any renderer, compiling MPRX at runtime, programs that change while the app runs (hot reload), and composite events. The last is a limitation of MESH v0.5.

## 3. Facts about MESH v0.5 this design relies on

The design treats these as facts, because they were verified against the **published** tarballs `@valancex/mesh-runtime@0.5.0` and `@valancex/mesh-compiler@0.5.0`. Some were checked in the `.d.ts` files. Others were checked by a throwaway Node probe that ran the tarballs against `mesh/examples/slice`. None of them comes from the old NEXUS design.

| # | Fact | How verified |
|---|---|---|
| F1 | `render({program: {root, templates: string[]}, model: string, snapshot: Record<string, unknown>}): Promise<{render} \| {diagnostics}>` | `dist/engine.d.ts` |
| F2 | `dispatch(render: Render, handler: string, payload?: unknown): Promise<{intent} \| {diagnostics}>` | `dist/engine.d.ts` |
| F3 | `Render` is a class with only `readonly tree: RenderTree` public, and its tree is frozen | `.d.ts`; probe: `Object.isFrozen(tree)` |
| F4 | The snapshot is encoded when `render()` is called. Mutating the object afterwards doesn't change what that render dispatches | probe: a mutation after render; dispatch still gives "Ada Lovelace" |
| F5 | `dispatch` evaluates against the render's own snapshot. On the slice: dispatching the first render after a newer one gives "Ada Lovelace", and the newer render gives "Ada King" | probe |
| F6 | Handler ids are equal across renders of one program, so a mispaired dispatch gives no error | probe |
| F7 | The first render's tree is byte-equal to MESH's committed `expected/first.tree.json` | probe |
| F8 | Errors in the inputs come back as diagnostics, never rejections: an extra record field gives `runtime-unknown-field`; a wrong payload `runtime-value-mismatch`; a missing payload `runtime-missing-value`; an unknown handler `runtime-handler-other-program`. | F9 | The promises reject only with a `TypeError` (a Render the package didn't make, or a snapshot that isn't a plain object; the probe tried both), `MeshVersionError` or `MeshInternalError` | probe; `.d.ts` classes |

| F13 | `compile()` returns `{diagnostics, template?}`. A program's template is `JSON.stringify(template)`, and the model is the manifest's text | compiler `dist/engine.d.ts` |

**Assumptions still unverified. The plan's first task verifies them before anything is built on them:**

- **U1.** `@valancex/mesh-runtime` loads under **vitest**. Vite's module transform could break F11's `import.meta.url` wasm lookup. If it does, the fallback is `server.deps.external` for the package, or an explicit `init(readFileSync(...))` in test setup. The adapter itself doesn't change.
- **U2.** The package resolves under pnpm's strict `node_modules` layout, with NodeNext types. The probe imported the dist files by path, not by package name.
- **U3.** The `RenderTree` and `CommandIntent` types are exported from the package root. `index.d.ts` re-exports `types.js`, but that's only read, not yet compiled against.

**Old NEXUS assumptions that v0.2 drops:**

- §15 said "MESH reads state, evaluates selectors, invokes commands, observes changes". The direction is the other way. MESH never calls NEXUS: the NEXUS adapter is MESH's *host*, which gives MESH a snapshot and gets an intent back.
- §16 and §24 said "PORT sees the MESH Semantic IR". PORT sees a **render tree**: only primitive components, final values, text, keys and handler ids.
- MESH didn't turn out to be a "UI-facing API" of NEXUS with its own reactive binding model. Reactivity stays in NEXUS (`Selector.changes`). MESH is a pure function of (program, snapshot).

## 4. Architecture doc changes

- **§15, retitled "MESH host adapter".** The adapter feeds a snapshot from one selector into `render()`. It maps intents to Commands through an explicit table. The table is the only way MPRX reaches behavior, which keeps "MPRX can't call arbitrary Effect" (the existing rule list stays). NEXUS depends on `@valancex/mesh-runtime` only, never on the compiler at runtime, per MESH invariant I15.
- **§16.** "Semantic IR" becomes "render tree". PORT still depends on neither NEXUS nor the adapter. Whoever composes the app hands PORT trees and routes PORT's events back to `dispatch`.
- **§17.** Add `src/mesh/` to the layout.
- **§24.** Replace the diagram's "Semantic IR (render-only)" with "render tree". Add the v0.2 done-criteria, i.e. this spec's §1.
- **§26.** Add decision 7, "Semantic IR replaced by MESH v0.5 templates, render trees and command intents", which supersedes decision 4's wording but not its rule.
- **README.** Fix the package name, replace the "Semantic IR" sentence, and update Status to v0.2.

## 5. The adapter: `src/mesh/index.ts`

One file, exported as `Mesh`. It keeps no state and holds no resources: the caller holds renders, so it has nothing to scope or release.

```ts
export interface Program {
  readonly root: string;
  readonly templates: ReadonlyArray<string>; // template-v1 JSON text, compiled at build time
  readonly model: string;                    // the manifest's text
}

// An intent's arguments to a NEXUS command's effect, e.g. Mesh.bind(selectUser, ([user]) => ({ userId: ... })).
export type Binding<E, R> = (args: ReadonlyArray<IntentArgument>) => Effect.Effect<unknown, E, R>;
export const bind: <I, O, E, R>(command: Command<I, O, E, R>, toInput: (args: ReadonlyArray<IntentArgument>) => unknown) => Binding<E | CommandValidationError, R>;

export interface Host<E, R> {
  readonly render: Effect.Effect<Render, MeshDiagnostics>;            // renders the scope selector's current value
  readonly renders: Stream.Stream<Render, MeshDiagnostics>;           // one render per future scope commit
  readonly dispatch: (render: Render, handler: string, payload?: unknown) => Effect.Effect<Dispatched, MeshDiagnostics | UnmappedCommand | E, R>;
}
export const host: <E, R>(options: {
  readonly program: Program;
  readonly scope: SelectorHandle<Record<string, unknown>>;            // already shaped to the manifest (records are exact)
  readonly commands: Readonly<Record<string, Binding<E, R>>>;         // key: "component/name"
}) => Host<E, R>;

export interface Dispatched { readonly intent: CommandIntent; readonly output: unknown }
export type MeshDiagnostics = { readonly _tag: "MeshDiagnostics"; readonly diagnostics: RuntimeDiagnosticsDocument };
export type UnmappedCommand = { readonly _tag: "UnmappedCommand"; readonly component: string; readonly name: string };
```

Decisions:

- **Pairing is enforced by the signature.** `dispatch` takes the `Render` itself, not a render id. The runtime already binds a render to its snapshot (F5), so there's no registry of kept renders to get wrong. Keeping the render on screen is the caller's job, as MESH's `Host.keep` says. v0.2's tests act as the caller.
- **One selector is the snapshot.** Shaping values to the manifest (F8: records are exact) is the selector's projection, written by the app. The adapter doesn't strip fields: silently dropping data would hide bugs that MESH reports precisely.
- **`renders`** is `scope.changes` through `Stream.mapEffect(render)`. It's sequential, so renders arrive in commit order, and like `changes` it gives future commits only. It's the hook a renderer will subscribe to later. v0.2 tests it, and nothing else consumes it.
- **Errors.** Diagnostics become the typed `MeshDiagnostics` failure. An intent with no table entry is `UnmappedCommand`. Command failures, including `CommandValidationError`, pass through unchanged. Rejections (F9) are programming or installation bugs, so they're **defects** (`Effect.promise`), not typed errors.
- **`output`** is `unknown`, because one table mixes commands with different outputs. Typed per-command outputs are YAGNI until a caller needs them.
- **Dependencies.** `@valancex/mesh-runtime@^0.5.0` is a dependency. `@valancex/mesh-compiler@^0.5.0` is a devDependency, used only by tests to compile the fixture. `engines.node` becomes `>=22` (F14).

## 6. The slice fixture

`tests/fixtures/mesh-slice/` gets a copy of `mesh/examples/slice/` at tag `v0.5.0`: `components.json`, `users.mprx`, `user-card.mprx`, `snapshots/*.json`, `expected/first.tree.json` and `expected/select-first.intent.json`, plus a README naming its source commit. A copy is used rather than a git dependency, because the tests must be reproducible without the MESH repo. The test setup compiles the two templates once, in `beforeAll`, with the compiler: that's the "build time" step.

The NEXUS side of the slice:

- **State `Team`:** `{title, first: User, second: User, compact, selectedUserId: Option<string>}`.
- **Scope selector:** projects `Team` to `{title, first, second, compact}`, without `selectedUserId`.
- **`users.select({userId})`** sets `selectedUserId` and publishes `UserSelected`.
- **`users.refresh()`** replaces `first` with `snapshots/second.json`'s Ada King, standing in for a reload from a repository.
- **The table:**
  - `"user-card/selectUser"` → `users.select` with `{userId: args[0].value.id}`
  - `"users/refresh"` → `users.refresh`

## 7. Acceptance tests: `tests/mesh.test.ts`

All of them run inside a started `Application`, as `vertical-slice.test.ts` does, and shut it down cleanly.

1. **Render parity.** The first render's tree deep-equals `expected/first.tree.json`. This proves the selector-built snapshot equals MESH's.
2. **The full slice.** Click the first avatar (its handler and a `{x, y}` payload). The intent deep-equals `expected/select-first.intent.json`. `users.select` runs, `selectedUserId` is `Some("u1")`, and `UserSelected` is published.
3. **Stale event.** Render A. Click the avatar in A. Run `users.refresh` (the state commits), then render B. Dispatch with A: the intent's user is "Ada Lovelace". Dispatch the same handler with B: "Ada King". Handler ids are equal in A and B, which pins F6's hazard.
4. **Render identity.** Each `render` yields a distinct `Render`. A's tree is unchanged, and A can still be dispatched, after B exists and after further state commits.
5. **Update stream.** Subscribe to `renders`, then invoke `users.refresh` *through a dispatched button click*. The stream's next render shows "Ada King". Nothing is emitted for the state as it was at subscribe time.
6. **Errors.**
   - A scope selector that leaks `selectedUserId` into `first` fails with `MeshDiagnostics`, `runtime-unknown-field`.
   - An unknown handler gives `runtime-handler-other-program`.
   - A wrong payload gives `runtime-value-mismatch`.
   - A table without `"users/refresh"` gives `UnmappedCommand`.
   - A binding that produces an invalid input gives `CommandValidationError`.
   - A hand-made `{tree}` object passed as a `Render` is a defect (TypeError).
7. **Shutdown.** After `Application.shutdown`, a `renders` subscription started in the app's scope has ended.

Existing tests stay green. Coverage is the tests above, not a percentage.

## 8. CI

`.github/workflows/ci.yml` runs on push and on pull requests to `main`. Its steps are `pnpm/action-setup`, then `actions/setup-node` with Node 22 and 24, then `pnpm install --frozen-lockfile`, then typecheck, test and build. It needs no secrets and has no release job.

## 9. Delivery order (for the plan)

1. Verify U1–U3, by installing the packages and running one vitest test that renders the fixture.
2. Rename the package and add CI (mechanical, independently green).
3. Build the adapter with tests 1–7, test first.
4. Update the architecture doc and README.

Nothing is pushed or published without the maintainer's go-ahead.
