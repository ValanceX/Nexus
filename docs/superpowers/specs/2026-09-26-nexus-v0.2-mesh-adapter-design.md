# NEXUS v0.2: the MESH runtime adapter

*Design spec, 2026-09-26. Revision 2, after review. Status: awaiting review.*

## 1. Goal

v0.2 is done when a NEXUS application running in Node drives MESH v0.5 end to end, and tests prove it:

```text
NEXUS State ─▶ Selector ─▶ snapshot ─▶ mesh-runtime render() ─▶ Render (render tree)
                                                                   │  user event
NEXUS Command.invoke ◀─ adapter binding ◀─ command intent ◀─ dispatch(that Render, handler, payload)
```

**The acceptance boundary is the running slice. "The adapter compiles" is not enough.** §8 lists the tests that have to pass. Each of them runs the published `@valancex/mesh-runtime@0.5.0` against MESH's own `examples/slice` program.

## 2. Scope

In:

1. Rename `@valence/nexus` to `@valancex/nexus`. This covers `package.json`, `README.md` and `docs/ARCHITECTURE.md`. Nothing else in the repo names the package.
2. Update the architecture for MESH v0.5 (§4). The "Semantic IR" model is gone. MESH produces templates, render trees and command intents.
3. Add the adapter, `src/mesh/`, exported as `Mesh` (§5, §6).
4. Add the Node vertical-slice acceptance tests, plus lifecycle and error tests (§8).
5. Add basic CI: one GitHub Actions workflow that runs `pnpm typecheck`, `pnpm test` and `pnpm build` on Node 22 and 24.

Out:

- npm publishing
- PORT
- a browser, or any renderer
- compiling MPRX at runtime
- programs that change while the app runs (hot reload)
- composite events, which MESH v0.5 doesn't support

v0.2 adds no abstraction beyond what §5 and §6 name.

## 3. Facts about MESH v0.5 this design relies on

The design treats these as facts because they were verified against the **published** tarballs `@valancex/mesh-runtime@0.5.0` and `@valancex/mesh-compiler@0.5.0`. Some were checked in the `.d.ts` files. Others were checked by a throwaway Node probe that ran the tarballs against `mesh/examples/slice`. None of them comes from the old NEXUS design.

**F13 is a test-fixture fact, not a runtime dependency.** It says how the tests turn the copied `.mprx` sources into the template text that `Program.templates` carries. No `src/` code calls `compile()`, and no NEXUS runtime path depends on it (§5.4).

**Assumptions not yet verified.** The plan's first task verifies them before anything is built on them:

- **U1.** `@valancex/mesh-runtime` loads under **vitest**. Vite's module transform could break F11's `import.meta.url` wasm lookup. If it does, the fallback is `server.deps.external` for the package, or an explicit `init(readFileSync(...))` in test setup. The adapter itself doesn't change.
- **U2.** The package resolves under pnpm's strict `node_modules` layout, with NodeNext types. The probe imported the dist files by path, not by package name.
- **U3.** The `Render`, `RenderTree`, `CommandIntent`, `IntentArgument` and `RuntimeDiagnosticsDocument` types are exported from the package root. `index.d.ts` re-exports `types.js`, but the probe only read that re-export and hasn't compiled against it yet.

**Old NEXUS assumptions that v0.2 drops:**

- §15 said "MESH reads state, evaluates selectors, invokes commands, observes changes". The direction is actually the reverse. MESH never calls NEXUS. The NEXUS adapter is MESH's *host*: it gives MESH a snapshot and gets a command intent back.
- §16 and §24 said "PORT sees the MESH Semantic IR". There is no Semantic IR in MESH v0.5, and neither NEXUS nor PORT consumes one. PORT sees a **render tree**, which holds only primitive components, final values, text, keys and handler ids.
- MESH isn't a "UI-facing API" of NEXUS with its own reactive binding model. Reactivity stays in NEXUS (`Selector.changes`). A MESH render is a pure function of (program, snapshot).

## 5. The adapter boundary

### 5.1 What `src/mesh` is

`src/mesh` is a **thin integration boundary** between NEXUS and `@valancex/mesh-runtime`, and it does exactly two translations:

- **Out:** a NEXUS selector value becomes a MESH snapshot, which `render()` turns into a `Render`.
- **In:** a MESH command intent becomes a NEXUS `Command.invoke`, through an explicit binding.

It must **not** introduce any of these:

- another reactive state model, since reactivity is `Selector.changes`
- a render registry, or any other store of `Render` instances
- a component lifecycle, since MESH templates have none and NEXUS doesn't add one
- a command runtime, since commands run through `Command.invoke` in the caller's Effect context

**NEXUS core stays independent of MESH.** No module outside `src/mesh/` imports `@valancex/mesh-runtime` or `src/mesh/`. Nothing in NEXUS imports `@valancex/mesh-compiler` or depends on compiler internals. An application that never touches `Mesh` runs exactly as it does in v0.1.

### 5.2 Invariants

These are permanent contracts of the adapter. They aren't implementation details, and later versions may not relax them without a new decision in ARCHITECTURE §26.

- **M1: Render provenance.** `dispatch(render, handler, payload)` always dispatches against the exact `Render` the caller supplied. The adapter never resolves, substitutes or looks up a "current", "latest" or "equivalent" render. Because handler ids are equal across renders (F6), substitution would be a silent bug: a click on an old tree would act on newer data. Tests 3 and 4 (§8) pin this invariant.
- **M2: No retention.** The adapter holds no reference to any `Render` after the call that produced it or consumed it returns. It keeps no registry, cache, or "last render".
- **M3: Explicit bindings only.** A command intent reaches behavior only through an entry in the caller's `commands` table. Anything else is `UnmappedCommand`. No fallback, convention-based lookup or reflection is allowed.
- **M4: Runtime only.** `src/mesh` depends on `@valancex/mesh-runtime` and on NEXUS primitives. It never depends on `@valancex/mesh-compiler`.

### 5.3 Lifecycle and resources

The adapter keeps no mutable state of its own. It doesn't retain `Render` instances (M2), and it acquires no resources: there's nothing to open, close or finalize, and `host()` is a plain synchronous constructor.

What the adapter *does* have is a reactive stream. `renders` is built on `scope.changes`, so it lives exactly as long as the Effect scope the caller runs it in. When that scope closes (for example, on `Application.shutdown`), the underlying state stream completes and `renders` ends with it (test 7). The adapter adds no scope of its own and no background fiber. A caller that never runs `renders` never subscribes to anything.

### 5.4 Dependencies

- `@valancex/mesh-runtime@^0.5.0` is a **dependency**. It's the only MESH package NEXUS code imports, and only from `src/mesh/`.
- `@valancex/mesh-compiler@^0.5.0` is a **devDependency**. It's used only by the test setup to compile the copied slice fixture (§7). This is a build-time or test-time step, and it's the "templates compiled at build time" that `Program` assumes. It isn't an architectural runtime dependency.
- `engines.node` becomes `>=22` (F14).

## 6. The adapter API: `src/mesh/index.ts`

One file, exported as `Mesh`.

```ts
export interface Program {
  readonly root: string;
  readonly templates: ReadonlyArray<string>; // template-v1 JSON text, compiled at build time
  readonly model: string;                    // the manifest's text
}

// Translates a command intent's arguments into a NEXUS command's input, then invokes it.
// e.g. Mesh.bind(users.select, ([user]) => ({ userId: ... }))
export type Binding<E, R> = (args: ReadonlyArray<IntentArgument>) => Effect.Effect<unknown, E, R>;
export const bind: <I, O, E, R>(command: Command<I, O, E, R>, toInput: (args: ReadonlyArray<IntentArgument>) => unknown) => Binding<E | CommandValidationError, R>;

export interface Host<E, R> {
  readonly render: Effect.Effect<Render, MeshDiagnostics>;            // renders the scope selector's current value
  readonly renders: Stream.Stream<Render, MeshDiagnostics>;           // one render per future scope commit; see §6.2
  readonly dispatch: (render: Render, handler: string, payload?: unknown) => Effect.Effect<Dispatched, MeshDiagnostics | UnmappedCommand | E, R>;
}
export const host: <E, R>(options: {
  readonly program: Program;
  readonly scope: SelectorHandle<Record<string, unknown>>;            // already shaped to the manifest (records are exact)
  readonly commands: Readonly<Record<string, Binding<E, R>>>;         // key: "component/name"
}) => Host<E, R>;

export interface Dispatched { readonly intent: CommandIntent; readonly output: unknown }
export type MeshDiagnostics = { readonly _tag: "MeshDiagnostics"; readonly diagnostics: RuntimeDiagnosticsDocument };
export type UnmappedCommand = { readonly _tag: "UnmappedCommand"; readonly component: string; readonly name: string };
```

### 6.1 Decisions

- **The signature enforces pairing.** `dispatch` takes the `Render` itself, not a render id. The runtime already binds a render to its snapshot (F5), so there's no registry of kept renders to get wrong (M1, M2). Keeping the render that's on screen is the caller's job, as MESH's `Host.keep` says. In v0.2 the tests act as the caller.
- **One selector is the snapshot.** Shaping values to the manifest is the selector's projection, written by the app (F8: records are exact). The adapter doesn't strip fields, because silently dropping data would hide bugs that MESH reports precisely.
- **`output`** is `unknown`, because one table mixes commands with different outputs. Typed per-command outputs are YAGNI until a caller needs them.

### 6.2 `renders`: lifecycle and failure semantics

`renders` is `scope.changes` piped through `Stream.mapEffect(render)`. This is ordinary Effect `Stream` behavior, and NEXUS has no competing stream convention (`State.changes` and `Selector.changes` never fail, so this is the first failing stream, and it keeps Effect's default):

- **Sequential, in commit order.** One render per scope commit, in the order the commits happen. Like `changes`, it emits future commits only, so nothing is emitted for the value at subscribe time. Use `render` for that.
- **A render diagnostic is terminal.** If a future snapshot can't be rendered and MESH returns diagnostics, the stream **fails with `MeshDiagnostics`** and **terminates**. It emits no `Render` for that commit, and it doesn't emit, re-emit or keep the previous successful render as a substitute. Later selector commits are **ignored** by that stream, because it has ended. The upstream `changes` subscription is released when the stream fails.
- **Why terminal.** A render diagnostic means the selector's projection no longer matches the manifest. The application broke its contract with the model, so this isn't a recoverable UI event. Skipping the commit and continuing would leave a renderer showing a tree that no longer reflects state, and nothing would signal it.
- **Recovery is the caller's choice, made explicitly.** A caller that wants to keep going can re-subscribe to `renders` or call `render`. Both evaluate the *current* state from scratch, because the host holds nothing (M2). The adapter itself never retries, skips or resumes.
- **Defects aren't diagnostics.** A rejection from `render()` (F9) makes the stream die with that defect, the same way as the one-shot `render`.
- **Normal end.** When the caller's scope closes, the stream ends without error (§5.3).

v0.2 tests this stream directly (tests 5, 7, 8). Nothing else in v0.2 consumes it. It's the hook a future renderer will subscribe to.

### 6.3 Command intent to Command: the translation boundary

The flow for one user event is:

```text
MESH command-intent arguments   ReadonlyArray<IntentArgument>, dynamically shaped, from dispatch()
  → adapter binding             commands["component/name"], i.e. Mesh.bind(command, toInput)
  → NEXUS command input         toInput(args): unknown
  → Command.invoke              validates the input against the command's Schema, then runs the handler
```

`toInput` is the **trust and translation boundary** between MESH and NEXUS. MESH has already checked the arguments against the manifest's declared command signature (F8), but they arrive as `unknown` values in `{value} | {absent: true}` slots. TypeScript can't relate them to any particular command's `Input` type, and the API makes no claim that it can. `toInput` returns `unknown` for that reason. The type system doesn't prove that a MESH argument shape matches a NEXUS command input.

**`Command.invoke`'s runtime validation is authoritative.** Whatever `toInput` produces is decoded by the command's `Schema`. A mismatch fails with `CommandValidationError`, and the handler never runs. This is the same guarantee every other `invoke` caller gets, so the adapter adds no second validator.

`toInput` should be a total, pure mapping. If it throws (for example, by reading `.value` of an absent argument), that's a bug in the binding and is surfaced as a defect, not a typed error. Typed rejection of bad input belongs to `Command.invoke`.

### 6.4 Error taxonomy

| Error | Channel | Meaning | Whose fault |
|---|---|---|---|
| `MeshDiagnostics` | typed failure | The MESH runtime rejected the render or dispatch input: a snapshot that doesn't match the manifest, an unknown handler, a wrong or missing payload (F8) | the app's selector projection, or the event it forwarded |
| `UnmappedCommand` | typed failure | MESH returned a command intent `{component, name}` that the adapter's table has no binding for (M3) | the app's binding table |
| `CommandValidationError` | typed failure | The NEXUS command rejected the input that the binding translated (§6.3) | the binding's `toInput` |
| command's own `E` | typed failure | The command ran and failed in its domain. This passes through unchanged | domain logic |
| `TypeError`, `MeshVersionError`, `MeshInternalError` | **defect** (`Effect.promise`) | A promise rejection (F9): a forged `Render`, a non-plain snapshot, a package or wasm version mismatch, or a runtime bug | programming, packaging or runtime defect, not an application failure |
| a throw inside `toInput` | **defect** | The binding itself is broken (§6.3) | programming defect |

The first four are the normal, application-level outcomes a caller handles. The last two are never part of `dispatch`'s or `render`'s error type. This keeps the existing Effect error-channel design unchanged.

## 7. The slice fixture

`tests/fixtures/mesh-slice/` gets a copy of `mesh/examples/slice/` at tag `v0.5.0`: `components.json`, `users.mprx`, `user-card.mprx`, `snapshots/*.json`, `expected/first.tree.json` and `expected/select-first.intent.json`, plus a README naming its source commit. The tests use a copy rather than a git dependency so that they're reproducible without the MESH repo. Test setup compiles the two templates once, in `beforeAll`, with the devDependency compiler (F13). That's the "build time" step. No `src/` code takes part in it.

The NEXUS side of the slice:

- **State `Team`:** `{title, first: User, second: User, compact, selectedUserId: Option<string>}`.
- **Scope selector:** projects `Team` to `{title, first, second, compact}`, leaving out `selectedUserId`.
- **`users.select({userId})`** sets `selectedUserId` and publishes `UserSelected`.
- **`users.refresh()`** replaces `first` with Ada King from `snapshots/second.json`, standing in for a reload from a repository.
- **The table:**
  - `"user-card/selectUser"` → `users.select`, with `{userId: args[0].value.id}`
  - `"users/refresh"` → `users.refresh`

## 8. Acceptance tests: `tests/mesh.test.ts`

Every test runs inside a started `Application`, as `vertical-slice.test.ts` does, and shuts it down cleanly.

1. **Render parity.** The first render's tree deep-equals `expected/first.tree.json`. This proves that the selector-built snapshot equals MESH's.
2. **Full command round trip.** Click the first avatar (its handler, with an `{x, y}` payload). The intent deep-equals `expected/select-first.intent.json`. `users.select` runs, `selectedUserId` is `Some("u1")`, and `UserSelected` is published.
3. **Stale event (M1).** Render A and click the avatar in A. Run `users.refresh` so the state commits, then render B. Dispatching with A gives an intent whose user is "Ada Lovelace". Dispatching the same handler with B gives "Ada King". Handler ids are equal in A and B, which pins F6's hazard.
4. **Render identity (M1, M2).** Each `render` yields a distinct `Render`. After B exists and after further state commits, A's tree is unchanged and A can still be dispatched.
5. **Update stream.** Subscribe to `renders`, then invoke `users.refresh` *through a dispatched button click*. The stream's next render shows "Ada King". Nothing is emitted for the state as it was at subscribe time.
6. **Errors** (one case per row of §6.4):
   - A scope selector that leaks `selectedUserId` into `first` fails with `MeshDiagnostics`, `runtime-unknown-field`.
   - An unknown handler gives `MeshDiagnostics`, `runtime-handler-other-program`.
   - A wrong payload gives `MeshDiagnostics`, `runtime-value-mismatch`.
   - A table without `"users/refresh"` gives `UnmappedCommand` with `{component: "users", name: "refresh"}`.
   - A binding that produces an invalid input gives `CommandValidationError`, and the command's handler doesn't run.
   - A hand-made `{tree}` object passed as a `Render` is a defect (`TypeError`), not a typed failure.
7. **Shutdown.** After `Application.shutdown`, a `renders` subscription started in the app's scope has ended without error.
8. **Render failure is terminal (§6.2).** Use a scope selector that is valid while `selectedUserId` is `None` and leaks it into `first` while it is `Some`. Fork a consumer of `renders` that appends every emitted `Render` to a `Ref`. Then:
   1. Commit a valid change (`users.refresh`). Exactly one `Render` is emitted, and it shows "Ada King".
   2. Commit a malformed change (`users.select`, so `selectedUserId` becomes `Some`). The consumer fiber's exit is a **failure** with `MeshDiagnostics` / `runtime-unknown-field`. It isn't a defect, and it isn't a success.
   3. Commit a change that makes the projection valid again (reset `selectedUserId` to `None` directly through the `Team` state handle).
   4. Assert that the `Ref` still holds **exactly one** `Render`: the one from step 1. There's nothing for the failed commit, the step 1 render isn't re-emitted, and there's nothing for step 3. Assert that the fiber stayed completed after step 3.
   5. Assert that a fresh `render` after step 3 succeeds and reflects the current state. This shows that only the stream ended and the host kept no poisoned or cached state (M2).

   This test fails if the adapter swallows the diagnostic, keeps the stream alive, or emits or re-emits a stale successful render after a failed one.

Existing tests stay green. Coverage means the tests above, not a percentage.

## 9. CI

`.github/workflows/ci.yml` runs on push and on pull requests to `main`. Its steps are `pnpm/action-setup`, then `actions/setup-node` with Node 22 and 24, then `pnpm install --frozen-lockfile`, then typecheck, test and build. It needs no secrets and has no release job.
