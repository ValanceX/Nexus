## Where v0.2 left off

v0.2 (locked 2026-09-26) made a NEXUS application drive MESH v0.5 end to end, in Node:
- `src/mesh`, exported as `Mesh`, is the host adapter between NEXUS core and `@valancex/mesh-runtime`. The MESH compiler is used only at test or build time.
- M1–M4 are normative: exact `Render` provenance, no render retention, explicit bindings only, and a runtime-only dependency.
- `renders` emits future commits only, and fails terminally on a render diagnostic.
- The error taxonomy separates typed failures from defects. A `toInput` throw is a defect.
- Test 9 and the architecture checks enforce the import boundaries.
- `State.changes` completes when its owning scope closes (F-A). This fixed a v0.1 gap the adapter's shutdown test exposed.

v0.2 changed nothing else in the v0.1 core, and its audits covered only MESH-related documentation.

### Findings

- **O1. Event subscriptions don't end on shutdown** (P1).
  - `event.md` says the bus is "released with" the application and that its subscriptions complete when the application's scope closes. No test covers this. It's the same class of bug as F-A.
- **O2. The application lifecycle can be bypassed** (P3, P6, P7, P9).
  - `RunningApplication.runtime.scope` is a public `CloseableScope`. `Runtime.shutdown` accepts the application's handle. Effects still execute after shutdown.
  - These contradict `src/application/index.ts:42-43` ("a public, writable Ref would let any holder forge a lifecycle transition") and the lifecycle in ARCHITECTURE §4.
  - v0.2 made this scope load-bearing (`state.md:58`, and the harnesses in `tests/mesh.test.ts` and `tests/state.test.ts`).
- **O3. The service `Context` is reachable** (P4). This violates `runtime.md:74` and ARCHITECTURE §5 ("must not become a global service locator").
- **O4. Application-owned State has no API.**
  - ARCHITECTURE §4 and §14 say the Runtime owns State. `application.md` lists "initialize state" among the application's responsibilities.
  - The only route today is `Scope.extend(…, running.runtime.scope)`, which is exactly the surface O2 and O3 remove.
- **O5. `publish` doesn't validate** (P2), despite `event.md:66`.
- **O6. The command-name uniqueness rule (`command.md:76`) has nothing to attach to:** there is no application command set.
- **O7. The primitive docs diverge from the code** (D5's table). `primitives/README.md:23` calls any such divergence a bug.
- **O8. Non-Effect callers can't see typed errors** (P5). *Deferred*: documented only (D5).
- **O9. Nobody owns the MESH host composition loop.** *Deferred* (H5).
  - MESH's host has five steps: compile, render, keep, dispatch and map. Its `docs/ARCHITECTURE.md:31` and step 3 of its NEXUS guide say the NEXUS adapter "keeps each render", which contradicts M2.
  - PORT is a scaffold.
- **O10. Capability probing is described but not built.** *Deferred*. Its dead `EnvironmentResolutionFailed` variant is handled under O7.

## Theme

v0.3 is a correctness and coherence release. The ownership and lifecycle model NEXUS already promises (ARCHITECTURE §4, §5, §14 and the primitive docs) becomes true in code, and every primitive's documented contract matches its implementation. There is no new feature family, and the MESH boundary doesn't move.

## Architecture and invariants

### Carried over from v0.2, unchanged

- **M1, render provenance.** `dispatch(render, …)` operates against exactly the supplied `Render` and never substitutes another.
- **M2, no render retention.** The adapter keeps no render registry or cache, and no `Render` for later lookup.
- **M3, explicit bindings only.** An intent with no explicit `commands` entry fails with `UnmappedCommand`.
- **M4, runtime-only dependency.** `src/mesh` uses `@valancex/mesh-runtime` only, never the MESH compiler.
- **Error taxonomy.**
  - Typed failures: `MeshDiagnostics`, `UnmappedCommand`, `CommandValidationError`, and the command's own `E`.
  - Defects: a `toInput` throw, and `TypeError`, `MeshVersionError`, `MeshInternalError` or any other runtime rejection.
- **`renders`.** Future commits only, in commit order. A render diagnostic fails and ends the stream. It ends normally when the owning scope closes.
- **`State.changes`** stays open while its owning scope is alive and completes normally when that scope closes (F-A). Caller-scoped `State.create` keeps exactly this behaviour.
- **Selectors are pure.** `Selector.changes` completes when its underlying `State` does, and `combine` completes when either side does.
- **`Command.invoke`** decodes its input before the handler runs.
- **Import boundaries:** test 9 and the architecture checks. There is no PORT dependency.
- **The MESH v0.5.0 fixture** stays pinned and verbatim.
- **Packaging:** ARCHITECTURE §26, decision 8.

### Lifecycle terms

These terms are used throughout.

- **Initialization outcome.** `Application.start` either succeeds, giving a `RunningApplication` whose status is `Running`, or fails with an `ApplicationInitError`.
  - A failed start follows `Created → Initializing → Failed`. It is **not** a termination route: no `RunningApplication` exists to terminate, because none is returned.
  - Anything a failed start had partly built is released no later than when the caller's start scope closes. That is v0.2's behaviour, unchanged.
- **Termination begins** the moment a termination route (N2) starts. From then on the status is `Stopping`, and then `Stopped`.
- **Terminated** means the status is `Stopped`: every application resource has been released and N1 holds.
- **These terms describe an application.** A standalone runtime (D2) has no status. Its termination begins when its owning `Scope` starts closing, and it is terminated once that `Scope` has closed.
- **The handle outlives the application.** A `RunningApplication`, and its `runtime` handle, remain ordinary JavaScript values after termination. Holding one, reading `Application.status`, or calling `Application.shutdown` stays valid. What termination changes is what the handle can be used for (N2 and D2).

### New in v0.3

- **N1. Shutdown completeness.**
  - Once the application is terminated, every observation stream over application-owned resources has completed with a normal exit, not an interruption and not a failure. That includes:
    - `State.changes` of application-owned `State`;
    - `Selector.changes` derived only from application-owned `State`;
    - `Event.subscribe` streams run against the application's bus (P1);
    - `Mesh.renders` over such a selector.
  - A subscription started after termination has begun completes immediately.
  - **"Completed" means the stream ends:** it emits nothing further and signals its end. A consumer that isn't still processing an earlier element then completes normally. NEXUS doesn't wait for a consumer to finish its own processing, and a consumer's own failures stay its own.
  - Streams over caller-scoped `State` follow their own scope (F-A), not the application's.
  - The Event bus's ordering within `Stopping` is D4.
  - **N1 covers `Event.subscribe`,** the public, per-`EventDef` subscription. It doesn't cover a queue taken directly from the `EventBusShape` service's own members, which are plumbing (D5).
- **N2. Lifecycle integrity.** This applies to an application that started successfully (see "Lifecycle terms").
  - **Two termination routes, and only two:**
    1. `Application.shutdown(running)`;
    2. closing the caller-owned `Scope` in which `Application.start` ran.

    A failed start is an initialization outcome, not a third route.
  - **No public value can end, or partly end, the application:** no scope, and no runtime-shutdown entry point that accepts the application's handle.
  - **Both routes reach the same end state:** the status is `Stopped`, every application resource is released, and N1 holds.
  - **Status is monotonic** along `Created → Initializing → Running → Stopping → Stopped` (or `Initializing → Failed`). It is never observed moving backwards. Once it has left `Running`, it never returns there.
  - **`Application.shutdown` is idempotent and always completes normally:**
    - it never fails;
    - on a `Stopped` application it returns immediately and changes nothing;
    - concurrent calls, or a call concurrent with route 2, shut down once, and every call returns only once the status is `Stopped`;
    - after route 2 has finished, it's a no-op.
  - **New work is admitted only while `Running`** (Q1, resolved). Once termination has begun:
    - an effect passed to `Runtime.run` or `Runtime.runFork` through the application's handle doesn't start;
    - the call ends as a defect: `run`'s Promise rejects, and `runFork`'s fiber exits with a defect, with no typed error in either case (D2);
    - D1's constructor doesn't create `State`; its effect ends as a defect (Q2).

    Status therefore never says `Stopped` while the application is still accepting work.
  - **Effects already running when termination begins** aren't governed by N2 beyond N1's observation streams. Their behaviour is v0.2's, unchanged (see "After v0.3").
- **N3. No ambient Context.**
  - **The four things this distinguishes:**
    1. the public, opaque `NexusRuntime` handle;
    2. the public functions `Runtime.run` and `Runtime.runFork`, which take that handle and execute an effect;
    3. the internal Effect `Runtime` that actually executes it;
    4. the service `Context` and the runtime's `Scope`, which that Effect `Runtime` carries or is built in.
  - **The invariant:** a caller may hold an opaque NEXUS execution handle and pass it to NEXUS execution functions. No public value exposes the underlying Effect `Runtime`, the `Context` or the runtime `Scope`, under any property name, through a getter, or through anything else a caller can read.
  - **N3 doesn't remove the ability to execute effects.** `Runtime.run` and `Runtime.runFork` keep running effects against the service graph. An effect gets the application's services only through its declared `R`.
- **N4. Contract parity.**
  - **Normative sections:** in each `docs/primitives/*.md`, the Data Model, API, Errors and Rules sections, plus ARCHITECTURE §15 for `Mesh`.
  - Every type, signature, error variant and field they name must match the exported declarations in `dist/**/*.d.ts` exactly.
  - Examples are illustrative, but they may use only APIs that exist.
  - A divergence is a defect. It's resolved only by a recorded decision that either changes the code or corrects the document, never by leaving both.

## Goals

1. Application-owned `State` whose lifetime is the application's (O4).
2. Lifecycle integrity: exactly two termination routes for a started application, truthful and monotonic status, an idempotent shutdown, and no new work admitted once termination has begun (O2).
3. No Effect `Runtime`, `Context` or runtime scope reachable from a public value (O3).
4. Shutdown completion for every application-owned observation stream, including `Event.subscribe`, in a defined order (O1).
5. Every primitive's documented contract reconciled with its implementation (O5, O6, O7).

## Non-goals (v0.3)

- **MESH host composition:** keeping the on-screen render, relaying events, re-rendering (O9, H5).
- **Non-Effect host support** (O8), beyond documenting the current behaviour.
- **PORT;** browser, DOM or renderer work.
- **Capability probing or discovery** (O10).
- **Selector memoization or deduplication;** typed command outputs.
- **Extra event buses,** wildcard subscriptions or replay.
- **Splitting the adapter** into a separate package.
- **Hot reload,** runtime MPRX compilation, composite events.
- **npm publishing.**
- **Any change to M1–M4** or to the `renders` contract.
- **A command registry,** or a capability-resolution architecture.
- **Compatibility wrappers** for removed surface.
- **Fixing MESH's documentation** (see "After v0.3").
- **Changing what happens to effects already running** when termination begins, beyond N1.

## Decisions

### D1. Application-owned State (O4; H1(b))

- **The constructor:** an application-scoped `State` constructor in the `Application` namespace takes the `RunningApplication`, a schema and an initial value. Its name is left to the plan.
- **Ownership:**
  - Any holder of the `RunningApplication` may create one.
  - It requires no `Scope` from the caller; not taking one is what makes the ownership explicit.
  - It is bound to that application, and the application owns its lifetime, which ends when the application terminates by either N2 route.
- **Admission.** Construction is admitted only while the application is `Running`.
  - **Already `Stopping` or `Stopped`:** no `State` is created, and the constructor's effect ends as a **defect** (Q2 = A). The defect carries no typed error: `Cause.failureOption` is `None`.
  - **Racing `Application.shutdown` or the caller's start scope closing:** construction and termination are ordered. Either the `State` exists before termination begins, and is then terminated with the application (N1), or construction is refused as a defect. There is no third outcome.
  - **The contract:** no `State` whose ownership extends beyond the application's lifetime may ever be returned. That includes a `State` whose `changes` would stay open after the application is `Stopped`.
- **Errors:**
  - The error channel is exactly `StateInitError`, for an invalid initial value, as with `State.create`.
  - There is no lifecycle error type, and none may be added to the error channel.
  - A lifecycle refusal is a defect: misuse of a handle whose application has begun terminating, the same classification as Q1.
- **Result:** an ordinary `StateHandle<A>`. There is no new kind of state.
- **Access:** commands and other primitives reach it through an explicit handle reference (closures or constructor arguments), as today. It isn't registered in the service graph, and nothing looks it up by name (N3).
- **At termination:**
  - its `changes` completes normally (N1) through the F-A mechanism, and derived selectors and `Mesh.renders` follow;
  - `get`/`update`/`set` on the handle keep their v0.2 behaviour;
  - a new `changes` subscription completes immediately.
- **`State.create(schema, initial)`** is unchanged, for caller-owned state.

### D2. The `NexusRuntime` surface (O2, O3; H2)

There is one public handle type: `NexusRuntime<R>`, an opaque execution handle with no readable `scope`, `runtime` or `context` member (N3). `Runtime.run` (Promise) and `Runtime.runFork` (Fiber) accept it. There are two kinds of runtime behind it, and they differ only in who owns them.

- **The application runtime** is `RunningApplication.runtime`.
  - It is created by `Application.start`, and the application owns it.
  - Callers can't shut it down directly: there's no public scope and no public runtime-shutdown function.
  - It terminates only by the N2 routes, and its lifecycle is the application's.
- **A standalone runtime** is the handle `Runtime.make(layer)` returns. Its contract is unchanged from v0.2, apart from two additions: the admission refusal below, and D4's Event bus ordering when its `Scope` closes.
  - `Runtime.make` requires a caller-owned `Scope`, and that caller owns the runtime.
  - The runtime terminates when that `Scope` closes. Closing it releases every resource the service graph acquired, and completes every `Event.subscribe` stream on the runtime's own bus.
  - Removing `Runtime.shutdown` doesn't remove this lifecycle. Closing the owning `Scope` has always ended a standalone runtime, and it is now the only way. `Runtime.make` has no status; the scope is the lifecycle.
- **Execution through a handle** (both kinds):
  - While the runtime is live, `Runtime.run` and `Runtime.runFork` keep v0.2's semantics. They add no runtime-level error channel, and failures surface as the effect's own `E` to Effect callers (`runtime.md`, Errors). For the Promise that `run` returns, see D5's O8 row, which only documents the existing wrapper.
  - Once the runtime's termination has begun (for an application, from `Stopping`; for a standalone runtime, from its `Scope` closing), an effect passed to either function doesn't start, and the call ends as a defect. That's N2's admission rule.
- **Q1, execution after termination, is resolved as refusal.** The evidence:
  - N2 requires the status to match the runtime's real state, and a `Stopped` application that still executes new work contradicts it.
  - `runtime.md` makes `Runtime` the owner of shutdown and of every resource release, so executing against released services is uncontrolled use-after-release.
  - `runtime.md` also says `run`/`runFork` "do not introduce a runtime-level error channel of their own", so the refusal can't be a typed failure. v0.2's taxonomy classifies misuse of a host-side handle (a forged `Render`, a broken binding) as a defect, so the refusal is a defect.
- **`RunningApplication`** keeps `runtime` (the opaque handle), `status` (through `Application.status`) and `environment`.
  - Its `shutdown` field is removed, leaving `Application.shutdown(running)` as the single sanctioned call.
- **What callers can do:**
  - run effects through a live handle;
  - read the application's status;
  - request its shutdown;
  - create application-owned `State` while it's `Running`;
  - end a standalone runtime by closing its scope.
- **What callers can't do:** close an application's internal scope, reach any Effect `Runtime`, `Context` or runtime `Scope`, change status directly, or start new work after termination has begun.

### D3. Lifecycle integrity (O2)

N2 is the contract. Two consequences of it:
- Route 2 (closing the caller's scope) must also move the status to `Stopped` (P7).
- A repeated or concurrent `Application.shutdown` must never write any status after `Stopped`.

### D4. Shutdown completeness and the Event bus (O1)

N1 is the contract. Within `Running → Stopping → Stopped`, the bus behaves as follows. The evidence:
- `event.md` makes `publish` fire-and-forget, with error channel `never`, and delivers only to active subscriptions; there's no replay.
- A `Resource`'s `release` has no requirements channel, so releasing resources can't publish (`src/resource/index.ts`).

The contract:
- **The bus closes when termination begins, before any other application resource is released.**
  - From that point, no event is delivered to any `Event.subscribe` stream.
  - Every existing subscription ends normally (N1), in the sense N1 defines.
  - The ordering guarantee is about *delivery*: no subscriber is handed an event after the bus has closed, and the bus closes before resource release begins. NEXUS doesn't wait for subscriber consumers to finish processing before releasing resources.
- **New publishes through the application's handle** during `Stopping` or after are refused like any other new work (N2): the effect doesn't start.
- **Publishes from effects already running** when termination began, whether during `Stopping` or later, still complete normally and never fail, as `publish` always does. They reach no subscriber, because none is active once the bus has closed. That is the same outcome as a v0.2 publish with no subscribers.
- **A subscription opened after termination has begun** completes immediately with no events (N1).

A standalone runtime's bus follows the same order when its `Scope` closes (D2).

| Capability docs: probing, and "discovery/fallback" in testing | A pre-resolved map | Probing at startup | The docs | Doc | Resolutions are supplied by the definition. Probing is future work, outside v0.3. |

**`Event.publish` and `EventDef.schema` (Q3 = B).** This is the resulting contract. It replaces every earlier statement to the contrary.
- **`publish` is type-directed.**
  - It accepts a `Payload` typed by its `EventDef` and performs **no runtime decode or validation**.
  - Its error channel stays `never`.
  - It never becomes a defect-producing validation point.
- **Runtime validation isn't part of the Event contract.** A payload that gets past the type system through an untyped escape hatch (a cast, untyped JavaScript) is the publisher's responsibility, and it is delivered as given.
- **`EventDef.schema` describes the payload.** It is the payload's contract, and it's available for runtime validation or serialization at a boundary where that is actually required: persistence, synchronization, or a consumer receiving events from an untyped source (ARCHITECTURE §12, §13). Such a boundary validates with the schema itself; `publish` doesn't do it for it.
- **Why this fits the architecture's boundary principle.**
  - NEXUS validates at the boundaries where untrusted data enters:
    - `Command.invoke` takes `unknown` and decodes it (`command.md:46-48`);
    - `State.update` is trusted, and validation "belongs in the Command's input schema, not repeated" (`state.md:77-79`).
  - Publication is internal. MESH reaches only commands (M3), and events are emitted by commands and services from data that was already validated where it entered.
- **Documentation to reconcile:**
  - `event.md` Rules (lines 65-66): remove the claim that the schema "exists so a malformed payload cannot be published", and the "decode-check" instruction. State the contract above.
  - `event.md` Testing (line 99): "typed event creation" means the schema describes and can validate the payload, not that `publish` rejects anything.
  - ARCHITECTURE §13: Events remain a *potential* schema boundary, validated where they cross an untyped or serialization boundary, not at publication.
  - No other document may imply that `publish` validates.

A new ARCHITECTURE §26 decision records D1–D5, the resolutions of Q1, Q2 and Q3, and the migration below.

## Resolved decisions

- **H1, application-owned State:** (b), an application-scoped constructor bound to `RunningApplication` (D1).
- **H2, the `NexusRuntime` surface:** narrow it to the smallest surface that keeps legitimate execution (D2). This is an intentional public API correction, not a runtime redesign.
- **H3, documented but unbuilt rules:** decided item by item on the repository's evidence (D5):
  - command-name uniqueness: correct the documentation, and add no registry;
  - `EnvironmentResolutionFailed`: remove it from the public union;
  - `publish` validation: correct the documentation (Q3 = B, below).
- **H4, scope:** A + B only. That is lifecycle and ownership closure, plus contract reconciliation.
- **H5, MESH host composition:** deferred. It is recorded under "After v0.3", not designed here.
- **Q1, execution after termination:** refused. The effect doesn't start, and the call ends as a defect (N2, D2). The evidence is in D2.
- **Event bus ordering within `Stopping`:** the bus closes first, and publishes that follow reach no one (D4). The evidence is in D4.
- **Q2 = A, a refused construction of application-owned State is a defect.**
  - The constructor's error channel is exactly `StateInitError`, and no lifecycle error type is introduced.
  - Constructing against an application whose termination has begun, or losing a race with it, is lifecycle or handle misuse, classified as Q1's refusal is.
  - Q1 is unchanged.
- **Q3 = B, runtime payload validation is not part of `Event.publish`'s contract.**
  - `publish` stays type-directed, with no runtime decode and error channel `never`.
  - `EventDef.schema` describes the payload, for validation or serialization at boundaries that need it.
  - The documentation is corrected (D5).

## Definition of Done

Each item is proved by a test written before the change it covers. Every lifecycle case below is tested for the application runtime, and where it applies, for a standalone runtime too.

- **Application shutdown (route 1):**
  - `Application.shutdown` leads to `Stopped`;
  - every application resource is released;
  - N1's streams (application-owned `State.changes`, a derived `Selector.changes`, `Event.subscribe`, and `Mesh.renders` in MESH test 7) end with a normal exit (P1's regression).
- **Caller-scope shutdown (route 2):** closing the caller's start scope without `Application.shutdown` gives the same end state: `Stopped`, resources released, and N1 (P7's regression).
- **Startup failure:**
  - a failing service graph yields a typed `ServiceGraphFailed`, and no `RunningApplication`, so there's no handle through which a shutdown could be requested or a termination observed;
  - partly built resources are released no later than when the caller's start scope closes;
  - the failure is a typed failure of `start`, not a defect, and `ApplicationInitError` has exactly one variant, `ServiceGraphFailed`.
- **Repeated shutdown:** after `Stopped`, another `Application.shutdown` returns normally, and no later status is observed; there's no `Stopping` after `Stopped`. After route 2, `Application.shutdown` is a no-op.
- **Concurrent shutdown:**
  - concurrent `Application.shutdown` calls, and a call racing route 2, release resources exactly once;
  - every call returns only at `Stopped`;
  - status stays monotonic throughout.
- **State construction during lifecycle transitions** (D1):
  - on a `Running` application, the constructor succeeds, and the state's `changes` ends on termination;
  - on a `Stopping` or `Stopped` application, it creates no `State`. Its effect ends as a defect: `Exit.isFailure`, `Cause.isDie`, and `Cause.failureOption` is `None`;
  - an invalid initial value still fails with the typed `StateInitError`;
  - racing shutdown (and, separately, route 2), every outcome is either a `State` whose `changes` ends by termination or a defect refusal. A test asserts no third outcome over many repetitions;
  - at type level, the constructor's error channel is exactly `StateInitError`.
- **Event behaviour during `Stopping`** (D4):
  - no event is delivered to a subscriber after the bus closes. The test records every delivery and a resource's release in one log, with an in-flight effect publishing continuously through shutdown, and asserts that no delivery follows the release;
  - existing subscriptions end normally (N1);
  - a publish from an effect already running during `Stopping` completes normally and reaches no subscriber;
  - a publish through the handle during `Stopping` doesn't start;
  - a subscription opened after termination has begun completes immediately with no events.
- **Execution after `Stopped`** (Q1):
  - `Runtime.run` through the handle rejects, and the effect's body never runs;
  - `Runtime.runFork` returns a fiber that exits with a defect and no typed error;
  - the same holds from `Stopping` onward.
- **Standalone runtime lifecycle** (D2):
  - closing the `Scope` passed to `Runtime.make` releases the service graph's resources;
  - `Event.subscribe` streams on its bus complete normally;
  - later `Runtime.run`/`runFork` through its handle are refused as defects.
- **No raw Scope, Context or Effect `Runtime` on the public handle** (N3):
  - typecheck-time assertions that `running.runtime.scope`, `running.runtime.runtime`, `.context` and a public `Runtime.shutdown` don't exist (P3's, P4's and P9's regressions);
  - at runtime, nothing reachable from the public handle's own properties is a `Context`, an Effect `Runtime` or a `Scope`;
  - `Runtime.run` and `Runtime.runFork` still execute effects that use the service graph through `R`.
- **Status monotonicity:** checked on every route above, including startup failure.
- **F-A:** the scope-owned `State` test is unchanged; the application-owned test uses D1.
- **MESH tests 1–9:** unchanged, except the `runSlice` line that creates `Team`. Test 9 and the architecture checks are unchanged.
- **Q3 = B:**
  - a payload that doesn't fit its `EventDef.schema`, passed through an untyped cast, is published successfully (exit `Success`) and delivered unchanged. This pins "no runtime validation in `publish`";
  - at type level, `publish`'s error channel is `never`;
  - `event.md` and ARCHITECTURE §13 no longer say `publish` validates (N4 review).
- **Deliberate breaks, repeating v0.2's method.** Each break must make a test fail:
  - drop the Event completion → the route 1, route 2 and D4 tests;
  - close the bus after resources are released → the D4 ordering test;
  - admit execution after termination → the Q1 tests;
  - skip the status update on route 2 → P7's test;
  - let a second `shutdown` rewrite the status → the repeated-shutdown test;
  - re-expose the scope, the `Context` or the Effect `Runtime` → N3's type tests;
  - let the constructor return a `State` after termination → the D1 lifecycle tests;
  - report the constructor's refusal as a typed failure → the Q2 defect assertion.
- **N4:** every normative primitive-doc section is checked against `dist/**/*.d.ts`, and every row of D5 is resolved as decided.
- **Clean verification:** a fresh `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test` and `pnpm build`, on Node 22 and 24.

## Risks

- **The migration touches the v0.2 acceptance harness.** Only `runSlice`'s `Team` creation may change. A diff of `tests/mesh.test.ts` that touches anything else, or any change to `src/mesh`, is out of scope.
- **Refusing new work once termination begins affects `Mesh`.** A `dispatch` or `render` run through the handle during `Stopping` is refused as a defect, like any other effect. This is the application-level contract (N2), not a change to M1–M4, the taxonomy of failures inside a running application, or `renders`. The plan must show that MESH tests 1–9 still pass unchanged.
- **Closing the bus first changes event delivery during shutdown.** A subscriber that relied on receiving events during `Stopping` won't. D4 makes this deliberate.
- **Ordering tests are timing-sensitive.** The D4 and concurrent-shutdown tests must assert ordering from observed events, not from sleeps, following v0.2's bounded-wait convention.
- **Q3 = B pins a permissive behaviour.** The test that a malformed payload is delivered documents the contract. It isn't a gap to be fixed later without a new decision.
