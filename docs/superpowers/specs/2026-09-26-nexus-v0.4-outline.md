## 2. Why v0.4 exists, and what "semantic analysis" means here

`FUTURE_DIRECTION.md` describes NEXUS as a system that reasons about work before executing it (§1, §3, I1). It classifies operations as supported, opaque or incompatible (§8), checks requirements against a target's capabilities (§9), and reports the result as structured diagnostics that every tool consumes (§10–§12, I6, I7).

Nothing in the repository can answer the question those sections all depend on:

> *What does NEXUS know about this operation before executing it?*

There is no vocabulary for a semantic fact, no way to say that a fact is unknown, no notion of a target, no source provenance and no diagnostic (A1). Every later stage (IR, optimization, target lowering) consumes these concepts. Designing the IR first would invent them implicitly.

### Definition

**[v0.4]** Throughout this outline, and in everything built from it:

> **v0.4 semantic analysis** is the evaluation of *explicitly declared* semantic facts about an operation against an *explicitly supplied* target profile, producing a structured classification and, where C5 requires one, diagnostics, without executing the operation.

That is the whole of it. It is intentionally much smaller than a compiler: it doesn't read source, inspect code, relate operations to each other, transform anything or change execution.

### What v0.4 cannot know, and why that is a decision

**[v0.4]** The audit's central finding (A2, A3, A12) is that NEXUS v0.4 cannot inspect the semantics of TypeScript or JavaScript:
- every NEXUS work unit is an opaque JavaScript closure: command handlers, service implementations, selector projections, resource acquire and release functions, and binding functions;
- Effect's type parameters are erased at runtime;
- TypeScript compiler and source analysis are outside v0.4.

v0.4 therefore makes **declaration-level analysis** the architecture of this release (D1). NEXUS reasons only about operations presented to it with semantic declarations. When a whole closure is presented as one operation, that operation is the semantic unit, and nothing inside it is visible. This is an intentional boundary, not a temporary limitation of the implementation. Source-level capture, if it ever comes, arrives as a new *producer* of declarations (X2, §14). It doesn't change what the analysis consumes.

### Compatibility timing

**[v0.4]** v0.4 checks compatibility per operation, before any IR exists. That is not the eventual target-validation pipeline, and v0.4 must not be presented as one (D9):

```text
v0.4 (this release)
  semantic declaration
    → declared semantic facts
    → target requirements
    → + explicit target profile
    → per-operation compatibility (classification, diagnostics)

future (v0.5 and later; not defined here)
  operation graph / semantic IR
    → whole-plan analysis
    → optimization
    → target validation of the plan
    → lowering
```

### Discrepancies

Each is recorded with its disposition. None is silently resolved in favour of either side.
- **X1. The pipeline is ordered three ways.** §3 puts "target validation" after optimization. §13 derives diagnostics from the IR. §19 puts diagnostics before the IR and "target compatibility" after the optimizer.
  - *Disposition:* v0.4's check is the early, per-operation check shown above. Whole-plan validation after optimization stays later work (D9).
- **X2. `FUTURE_DIRECTION.md` assumes semantic capture of ordinary TypeScript** (§2, §3, §19), for example classifying a `zod.parse` call inside a handler.
  - *Disposition:* v0.4 has no capture (D1). It classifies declared operations at their declared granularity, so a whole command handler is one operation. Capture is later work, and would add a producer of declarations without changing this contract.
- **X3. `NEXUS → execution plan → PORT`** (§13, §15, §19) contradicts ARCHITECTURE §16, a released contract: NEXUS must not depend on PORT, PORT must not depend on NEXUS, and PORT sees only MESH render trees.
  - *Disposition:* not resolved by v0.4. v0.4 adds no dependency in either direction, and target profiles are supplied independently of PORT (D8, D14). Resolving it is deferred architectural decision L1, a prerequisite for any PORT integration release.
- **X4. "Capability" means two things.** ARCHITECTURE §10 and `capability.md` define an application-level mechanism. §9 of `FUTURE_DIRECTION.md` uses the word for a facility a target provides (A5).
  - *Disposition:* two distinct, named concepts, *application capability* and *target capability* (I15, D7).
- **X5. Diagnostic code style.** §11's examples are numeric (`N2001`, `N1004`). MESH's released diagnostics use kebab-case strings (A7).
  - *Disposition:* NEXUS uses namespaced kebab-case codes (D12). §11's codes are illustrative; it calls its diagnostics "conceptual".

## 4. Audit

The audit read:
- `FUTURE_DIRECTION.md`, ARCHITECTURE and every primitive doc;
- the v0.2 spec, and the v0.3 outline, plan and "As built";
- the v0.2 and v0.3 release notes;
- every file under `src/`, `tests/architecture.test.ts`, and the capability, command, runtime and lifecycle tests;
- `examples/basic-app`, the package metadata, and the git history from v0.2 onward.

It searched `src/`, `tests/` and `docs/` for spans, source locations, diagnostics, provenance, capabilities, semantic descriptions, operation metadata, opaque operations and target compatibility.

### Findings

- **A1. No semantic, provenance or diagnostic concept exists in NEXUS.** **[exists]**
  - The only occurrences of "diagnostic" under `src/` are MESH's, passed through by the adapter (`src/mesh/index.ts:32`, `MeshDiagnostics`).
  - There is no span, source location, target, semantic description or analysis anywhere in `src/` or `tests/`. The only "opaque" is the runtime handle (`src/runtime/internal.ts:9`), which is unrelated.
  - Everything v0.4 defines is new. Nothing is migrated into it.
- **A2. Every NEXUS work unit is an opaque closure that produces an Effect.** **[exists]**
  - `Command.handler` (`src/command/index.ts:6`), service implementations (`src/service/index.ts:7`), `Selector.define`'s projection (`src/selector/index.ts:10`), `Resource.acquire`'s `acquire` and `release` (`src/resource/index.ts:3-6`), and `Mesh.bind`'s `toInput` (`src/mesh/index.ts:60`).
  - NEXUS can learn nothing about what they do without running them or analysing their source. Running them is excluded (`FUTURE_DIRECTION.md` §3, §17), and source analysis is outside v0.4. → **D1, I14.**
- **A3. Effect's type parameters are not runtime facts.** **[exists]**
  - A command's `R` and `E` exist only in the type system. The only runtime-visible metadata a command carries is its `name` and its input `Schema` (`src/command/index.ts:3-7`). No output schema exists.
  - Deriving facts from `R` or `E` needs the TypeScript compiler. → **I14.**
- **A4. Command names aren't a reliable identity.** **[contract]** v0.3 D5: "Names should be unique within an application by convention; NEXUS doesn't enforce it", and there is no registry. → **D4.**
- **A5. The `Capability` primitive is not a target capability.** **[contract]**
  - `Capability<Shape>` is an id and a `Context.Tag` (`src/capability/index.ts:3-6`). Its resolutions are supplied already resolved by `ApplicationDefinition.environment` (v0.3 D5), they carry implementation values, and "unavailable is a value" (`capability.md`). `require` turns `Unavailable` into the typed runtime failure `CapabilityUnavailableError`.
  - Its resolutions describe *which implementation the application chose*, not *what a target provides*. An operation that uses `Capability.resolve` with a fallback doesn't *require* the facility at all. → **I15, D7.**
- **A6. NEXUS has no notion of a target.** **[exists]**
  - The package targets Node only (`engines.node: ">=22"`), there is no browser build, and CI runs Node 22 and 24.
  - ARCHITECTURE §16 forbids any PORT dependency, and `tests/architecture.test.ts` enforces it.
  - So a target in v0.4 can only be a value someone states. → **D8.**
- **A7. MESH already has a mature diagnostic model.** **[exists]** (`@valancex/mesh-compiler` `dist/document.d.ts`, `@valancex/mesh-runtime` `dist/types.d.ts`)
  - Stable kebab-case string codes ("match on this, not on `message`"), and a message that "may change between versions".
  - A versioned document, whose consumers ignore properties they don't know.
  - Half-open spans ("`end` is just past the span's last character"), with several coordinate encodings.
  - Locations as a tagged union, several of which aren't spans.
  - Replacement suggestions.
  - It is precedent for NEXUS's shape, and it is MESH's own contract: the v0.2 taxonomy makes `MeshDiagnostics` a typed runtime failure of `render`, `renders` and `dispatch`, passed through unchanged. → **D12, D15.**
- **A8. NEXUS has two failure categories, and diagnostics are a third.** **[contract]**
  - Typed failures are `_tag`ged records in an Effect's error channel. Defects are refusals and broken bindings (`src/runtime/internal.ts`, `refusal`). Both are runtime outcomes of executing something.
  - A semantic diagnostic is a pre-execution finding. Putting it into either category would change error channels that v0.3 fixed (for example, `createState`'s error channel is "exactly `StateInitError`"). → **D10.**
- **A9. The lifecycle machinery is internal and self-contained.** **[exists]**
  - Admission, the termination claim, bus ordering and status hooks live in `src/runtime/internal.ts` and `src/application/index.ts`.
  - Analysis needs none of them. → **I19.**
- **A10. The import boundaries are enforced by a static test.** **[exists]**
  - `tests/architecture.test.ts` scans import specifiers: core never imports the adapter or any MESH package, the entry reaches MESH only through `./mesh/index.js`, the adapter never imports the compiler, and nothing imports PORT.
  - The same mechanism can enforce v0.4's boundary. → **D13.**
- **A11. The public surface is ten namespaces.** **[contract]**
  - `src/index.ts` exports the nine primitives and `Mesh`, which isn't a primitive (ARCHITECTURE §18).
  - ARCHITECTURE §25 adds concepts "only when real application requirements demonstrate" the need. v0.4's need comes from `FUTURE_DIRECTION.md`. → **R1.**
- **A12. There is no capture mechanism, and v0.4 adds none.** **[exists]**
  - Nothing observes source text, call sites or imports, and ARCHITECTURE §21 already lists tree-sitter and LSP as non-goals.
  - So operations and their spans can only be supplied. → **D1, C2.**
- **A13. Effect is the execution foundation, not the data foundation.** **[contract]**
  - ARCHITECTURE §2.2 uses Effect for execution concerns. A plain-data semantic model recreates none of them.
  - N3 already forbids Effect internals from leaking through public values. → **I18.**
- **A14. Existing validation boundaries are runtime boundaries.** **[contract]**
  - `Command.invoke` decodes `unknown` input, `State.set` validates, and `Event.publish` doesn't (v0.3 Q3 = B).
  - None of them is pre-execution analysis, and v0.4 moves no validation into or out of them.
- **A15. The release notes link to a `v0.3.0` tag that this clone doesn't have.** **[exists]**
  - `git tag` is empty, but `docs/releases/v0.3.md` links to `blob/v0.3.0/…`.
  - This doesn't affect the design. The plan pins its baseline by commit.
- **A16. MESH-originated work already crosses an explicit boundary.** **[contract]**
  - A MESH intent reaches NEXUS only through an explicit binding to a `Command` (M3), so no semantic fact needs MESH's participation.
  - v0.4 needs nothing from the adapter, and adds nothing to it. → **D15.**

## 5. Terms

**[v0.4]** These are used throughout.

- **Operation.** A unit of work presented to semantic analysis as one semantic unit. It exists for analysis only through its semantic declaration (D1). If the work is a closure, the whole closure is the operation.
- **Semantic declaration.** The analysis input for one operation (C1): an identity, an optional display name, optional provenance, and the operation's declared semantic facts. It is data, not code.
- **Semantic identity.** The operation's identity within one analysis context (D4). It is distinct from any display name.
- **Display name.** Optional human-readable metadata. It is never an identity.
- **Semantic property.** A named aspect of an operation that a fact can be about. v0.4 has exactly one: *target requirements* (D5).
- **Known / unknown.** A property is **known** exactly when the declaration explicitly represents it. Otherwise it is **unknown**. Unknown is not a value of the property, and never means empty, false, none or safe (I14).
- **Application capability.** The existing `Capability<Shape>` mechanism: an application-level runtime dependency whose implementation the application definition supplies (A5).
- **Target capability.** A named facility of the target that operations are checked against, such as filesystem, network or workers (I15).
- **Target profile.** Explicit, declarative input stating which target capabilities a target provides and which it doesn't (C4).
- **Compatibility verdict.** For one operation against one profile: **compatible**, **incompatible** or **undetermined** (C4).
- **Classification.** **supported**, **opaque** or **incompatible**, derived from the verdict (C5).
- **Provenance.** Where a declaration or fact came from: a source span (C2).
- **Diagnostic.** A structured, rendering-independent report of one finding (C6).
- **Analysis context.** One invocation of semantic analysis: a set of declarations, one target profile, and the facts the consumer requires established (C7).

## 6. Invariants

### Carried over, unchanged

**[contract]** These hold unchanged, and v0.4 must not weaken, reinterpret or add exceptions to any of them:
- M1–M4 (the MESH adapter) and N1–N4 (v0.3);
- the v0.2 error taxonomy;
- the import boundaries (test 9 and the architecture checks);
- every primitive's documented contract.

### New in v0.4

Each invariant exists because a contract, finding or review decision needs it.

- **I11. Semantic facts precede execution.**
  - Every fact, verdict, classification and diagnostic is established without executing the operation it concerns, and without running any application code: no handler, layer, service, resource function, selector projection, binding or other callback.
  - Semantic analysis requires no started `Application`, no `NexusRuntime` and no Effect `Runtime`.
- **I12. Unknown semantics remain executable, and opaque is never incompatible.**
  - Missing information never produces an **incompatible** verdict, an **incompatible** classification or an **error** diagnostic.
  - Semantic analysis never changes whether or how any operation executes (D10).
  - *Opaque* means "NEXUS cannot establish the fact". It never means invalid, unsafe, unsupported, incompatible or failed.
- **I13. Diagnostics are representation-independent.**
  - A diagnostic is plain data. It survives a JSON round trip unchanged, and it contains no function, class instance, `Error`, Effect value, markup, escape sequence or pre-rendered excerpt.
  - Equal analysis contexts give equal diagnostics in equal order, whoever consumes them: tests, a CLI, an editor, an LSP server or another analysis.
- **I14. Declared semantics are the analysis boundary.**
  - NEXUS treats a semantic property as known only when the operation's semantic declaration explicitly represents it.
  - NEXUS infers no semantic property from:
    - executing operation code, or its JavaScript runtime behaviour;
    - erased type information, including Effect's type parameters;
    - function names, command names or display names;
    - implementation conventions;
    - TypeScript AST inspection or compiler metadata.
  - A property that isn't declared is unknown, and an unknown property is never treated as false or empty.
- **I15. Target capability is distinct from application capability.**
  - Target capabilities and application capabilities are separate concepts with separate identifier spaces.
  - Semantic analysis neither reads nor produces an application capability, its resolution or its `Environment`.
  - Nothing in an application's capability configuration makes a target capability provided, not provided or required, and nothing in semantic analysis changes how application capabilities resolve.
- **I16. Target compatibility is evaluated from declarations, not execution or discovery.**
  - A verdict is a function only of the operation's declared requirements and the explicitly supplied target profile.
  - Incompatibility is proven, never inferred. It requires a declared requirement **and** the profile explicitly stating that the capability is not provided.
  - A capability the profile doesn't mention is undecided, never "not provided".
- **I17. Source provenance is preserved.**
  - Every provenance supplied with a declaration or fact reaches every diagnostic about it, exactly: never synthesized, approximated, widened or moved.
  - A diagnostic about something with no supplied span carries no span, and says so explicitly (C2).
- **I18. Semantic analysis does not expose Effect internals.**
  - The semantic model's public types reference no Effect type (`Effect`, `Layer`, `Context`, `Scope`, `Runtime`, `Cause`, `Exit`, `Fiber`, `Schema`), and no NEXUS runtime type (`NexusRuntime`, `RunningApplication`, `StateHandle`, `Command`, `Capability`).
  - The analysis entry point is not an Effect (D11).
- **I19. v0.3 lifecycle and ownership guarantees are unchanged.**
  - Semantic analysis observes, alters and depends on no lifecycle state: status, admission, scope, termination, bus or resource.
  - No error channel, admission rule or ownership rule changes.
  - N1–N4 and every v0.3 test hold unmodified.

## 7. Contracts

### C1. The semantic declaration (the minimum model)

**[v0.4]** A semantic declaration carries **exactly** what v0.4 needs:

| Part | Required? | Why v0.4 needs it |
|---|---|---|
| Semantic identity | yes | results and diagnostics must name the operation unambiguously (D4) |
| Display name | no | human-readable messages; never identity |
| Provenance | no, but every declaration can carry it | diagnostics point at source (C2) |
| Declared facts: *target requirements* | no; absent means unknown | the only property compatibility needs (C3, C4) |

- **[v0.4]** A declaration is plain data. Every value in it is a string, a number, a boolean, an array or a record of these. It holds no function, closure, `Command`, `Capability`, schema or Effect value, and no reference to the implementation it describes.
- **[v0.4]** How an application keeps a declaration alongside the closure it describes is outside the semantic model in v0.4. Attaching declarations to NEXUS primitives is deferred decision L2. This keeps analysis structurally unable to execute what it describes (I11).
- **[v0.4]** The declaration must not grow into an IR. It has no relationships to other operations, dependencies, data flow, control flow, scheduling, execution plan, lowering data, or optimization metadata (D5).

### C2. Provenance and source spans

- **[v0.4] A source span** identifies one contiguous region of one source:
  - **source identity:** a non-empty value chosen by the producer, stable for the same source within an analysis context. NEXUS treats it as opaque: it never reads, resolves, normalizes or opens it;
  - **start** and **end**, in one coordinate system, with start ≤ end. The span is half-open: end is just past the region. An empty span marks a point.
- **[v0.4] Coordinates are the plan's decision, within these constraints:**
  - the coordinate system must be unambiguous, and documented in the reference page;
  - it must not assume VS Code, LSP, TypeScript source files or any particular parser;
  - it must be mappable onto source text by a consumer that has the text.

  MESH's spans (A7) are precedent, not a requirement.
- **[v0.4] Provenance is semantic data; presentation is the consumer's.** A span says *where the declaration or fact came from*. Excerpts, line numbers, underlines, colours and hover text are presentation, and none of them belongs in provenance or in a diagnostic (I13).
- **[v0.4] Where provenance attaches:**
  - optionally, to a declaration;
  - optionally, to each declared requirement;
  - optionally, to a target profile.
- **[v0.4] A diagnostic has a primary span whenever the thing it's about has one** (I17).
  - A diagnostic about a declaration supplied without a span is **explicitly unlocated**: it identifies its subject by semantic identity, and says it has no source span.
  - It never borrows or synthesizes a span.
  - *Why declarations may omit spans:* v0.4 has no mechanism that produces spans (A12). Requiring authors to hand-write offsets for every declaration would add burden without making anything more exact. Every diagnostic that identifies a source-level problem, meaning one whose subject has source provenance, has a primary span.

### C3. Semantic knowledge

- **[v0.4] Only declared facts are known** (I14). A declaration is a claim by its author. NEXUS doesn't verify it, because it can't without executing (A2). Every verdict is relative to the declared facts, and diagnostics present them as declared, citing their provenance.
- **[v0.4] Knowledge is per property.** For each property, a declaration either represents it (known) or doesn't (unknown). A declaration with no facts has every property unknown.
- **[v0.4] The v0.4 property set is exactly `{ target requirements }`.** It is defined in C4. Adding a property in a later release adds to the set. It doesn't reshape declarations or results.
- **Triage.** Every property named in the brief or in `FUTURE_DIRECTION.md` §4 and §6:

  | Property | v0.4 | Reason |
  |---|---|---|
  | Target requirements | **included** | The only property the compatibility contract needs. Without it, incompatibility can't be represented. |
  | Source provenance | included, as provenance (C2), not as a property | It locates facts; it isn't a fact about behaviour |
  | Inputs, outputs | v0.5 | Needed for dependencies and data flow (IR). Nothing in v0.4 consumes them. |
  | Effects (observable side effects) | v0.5+ | Needed for reordering and optimization. When added, its name must not collide with Effect's `Effect` type. |
  | Determinism, cacheability | v0.5+ | Only an optimizer or a cache consumes them |
  | Composability, fusibility | v0.5+ | Relations between operations, which need the IR |

  Until a later release adds them, every deferred property is simply unknown for every operation.

### C4. Target profiles and compatibility

- **[v0.4] A target profile is declarative input** to semantic analysis (D8). It states:
  - a **name**, used in messages;
  - optionally, its **provenance**;
  - for each target capability it **decides**, whether that capability is **provided** or **not provided**.

  A capability the profile doesn't mention is **undecided** (I16).
- **[v0.4] Where profiles come from.** NEXUS never discovers a profile. It never derives one from PORT, runtime probing, environment inspection, browser or Node detection, application capability configuration or probing, or execution. Automatic discovery is later work, and preserves v0.3's O10 deferral.
- **[v0.4] Target capability identifiers** are stable, non-empty, plain-data identifiers, in their own space (I15). v0.4 defines no universal taxonomy and ships no predefined identifiers or profiles (D8).
- **[v0.4] A target-requirements fact** is a set of target capability identifiers the operation **cannot execute correctly without**, each with optional provenance, plus a completeness statement:
  - **complete:** exactly these, and no others;
  - **partial:** at least these, possibly others.

  An empty complete set is a known fact ("requires nothing"). It is not the same as an unknown property.
- **[v0.4] The verdict** for one operation against one profile:

  | Verdict | Exactly when |
  |---|---|
  | **incompatible** | the requirements fact is declared, and at least one required capability is decided **not provided** |
  | **compatible** | the requirements fact is declared **complete**, and every required capability is decided **provided** |
  | **undetermined** | every other case |

  The three rows are exhaustive and mutually exclusive. Every undetermined verdict records its **cause**, which is exactly one of:
  - **operation-side:** requirements are unknown, or partial;
  - **target-side:** requirements are complete, but some required capability is undecided by the profile.

  If both apply, the cause is operation-side.
- **[v0.4] Compatibility is target-specific** (`FUTURE_DIRECTION.md` I5). Each analysis context has exactly one profile.

### C5. Classification and diagnostic emission

These are two separate outputs. Classification is always produced. Diagnostics are produced only under the rules below.

- **[v0.4] Classification** is derived from the verdict, one to one:

  | Verdict | Classification | Meaning |
  |---|---|---|
  | compatible | **supported** | The declaration gives enough information, and the target satisfies every requirement |
  | undetermined | **opaque** | NEXUS cannot establish compatibility, from the recorded cause. Not invalid, unsafe, unsupported, incompatible or failed. |
  | incompatible | **incompatible** | The declared requirements provably can't be satisfied by the target |

  Every operation in the context receives exactly one classification.
- **[v0.4] An opaque operation stays executable** whenever its ordinary runtime contract permits it (I12). v0.4 adds nothing to execution. No later stage may assume a property that is unknown for an operation. v0.4 has no later stage, but the rule is stated now so the IR inherits it.
- **[v0.4] Required facts.** The analysis context states which facts its consumer *requires established*. In v0.4 the only one that can be required is *target compatibility*, and the default is that nothing is required. This input selects only which knowledge-gap warnings are *reported*. It never changes a classification, a verdict, what a code or severity means, or whether an `error` is reported. It is not a gating policy.
- **[v0.4] Emission rules:**
  1. **incompatible** → always one `error` diagnostic, whatever is required: a proven mismatch is always reported;
  2. **supported** → never a diagnostic;
  3. **opaque, with target compatibility required** → one `warning`, explaining the limitation:
     - operation-side cause → `nexus-opaque-operation`;
     - target-side cause → `nexus-undetermined-target-capability`;
  4. **opaque, with target compatibility not required** → no diagnostic. The classification alone records the opacity.

  So an application full of ordinary, undeclared closures produces no warnings unless its consumer asks for compatibility to be established. When it does, every warning explains a real loss of knowledge that consumer cares about.
- **[v0.4] The result is authoritative; diagnostics are derived.** Every fact a diagnostic asserts is also present as structured data in the result, so no consumer ever needs to parse a message.

### C6. Diagnostics

- **[v0.4] A diagnostic has exactly these parts:**
  - **code:** stable (D12);
  - **severity:** `warning` or `error` (D12);
  - **message:** one human-readable sentence stating what NEXUS knows. It may change between versions, and consumers match on the code, never the message;
  - **primary location:** a primary span, or explicitly unlocated (C2);
  - **subject:** the semantic identity of the operation it concerns, so that it can be joined to the result, and so that an unlocated diagnostic still identifies its subject;
  - **related spans:** optional, each with a short label ("requirement declared here", "target profile declared here");
  - **notes:** optional human-readable context. Notes may say how the condition could be resolved, in prose.
- **[v0.4] Severity is small and fixed:**
  - `warning`: semantic information is insufficient, but execution isn't proven invalid;
  - `error`: semantic analysis has established a condition that violates the applicable contract. In v0.4, the only such condition is a declared operation requirement that the supplied target profile explicitly doesn't provide.

  There is no `info`, and severity never encodes ordinary informational results. Classification and severity are separate: a *supported* or unreported *opaque* operation has a classification and no severity.
- **[v0.4] Meaning, not action.** A diagnostic's code and severity state what analysis established. They never state, imply or require what a consumer does about it: reject, refuse, prevent, display or anything else. Consumer policy is outside the diagnostic model (D10, L3), and no consumer's policy may change what a code or severity means.
- **[v0.4] The v0.4 code set is exactly three codes:**

  | Code | Severity | When (C5) | Primary location | Related spans | Notes must state |
  |---|---|---|---|---|---|
  | `nexus-incompatible-target-capability` | error | incompatible | the declaration's | each not-provided requirement's provenance; the profile's provenance, if any | the capability, and the profile's name |
  | `nexus-opaque-operation` | warning | opaque, operation-side, compatibility required | the declaration's | none | whether requirements are undeclared or partial; that the operation still executes normally |
  | `nexus-undetermined-target-capability` | warning | opaque, target-side, compatibility required | the declaration's | each undecided requirement's provenance | the capability, and that the profile doesn't decide it |

  Each operation yields at most one diagnostic.
- **[v0.4] Order.** Diagnostics follow the order of the declarations in the analysis context. Equal contexts give equal sequences (I13).
- **[v0.4] Evolution.** A later release may add optional parts, codes or severities. Consumers must ignore parts they don't know. A code, once released, keeps its meaning and is never reused.
- **[v0.4] Not in v0.4:** machine-applicable fixes (D12); a versioned diagnostics document; per-code severity configuration or suppression.

### C7. The analysis boundary

- **[v0.4] Input:** an analysis context, meaning a set of semantic declarations, exactly one target profile, and the facts required established (C5).
- **[v0.4] Output:** exactly one of these, both plain data (I13, I18):
  - **a result:** the property set considered, the required facts, the profile's name, one entry per declaration (identity, which properties are known, verdict with cause, classification), and the diagnostics;
  - **a rejection**, when the context violates the data contract (D6). A rejection isn't a diagnostic, because it describes malformed input, not a finding about an operation.
- **[v0.4] Semantic analysis is a total, deterministic, pure function** over well-formed input:
  - it reads no file, clock, environment or network;
  - it keeps no state between calls;
  - it cannot fail except by rejection.
- **[v0.4] It is independent of execution in both directions.** No primitive, lifecycle or error channel consults it, and it consults none of them (D10, I19). It can run in a process that never starts an application.

## 8. Decisions

- **D1. Declaration-level analysis is the architecture of v0.4.**
  - NEXUS reasons only about operations presented with semantic declarations. When a closure is presented as one operation, that operation is the semantic unit.
  - v0.4 doesn't look inside handlers, services, selectors, resource functions, or any other JavaScript or TypeScript.
  - This is a deliberate boundary. Source-level capture would be a future producer of declarations, and wouldn't change this contract (X2).
- **D2. The release is vocabulary and boundary only.** It adds the semantic model (C1–C6) and one analysis (C7). No primitive's data model, API, errors or rules change, and neither does the MESH adapter or any lifecycle.
- **D3. Only declared facts are known** (I14). NEXUS derives nothing from code, types, schemas, names or configuration, and verifies nothing it's told.
- **D4. Semantic identity is independent of any name.**
  - Every declaration has a semantic identity, stable and unique within its analysis context, and representable as plain data.
  - Display names are optional descriptive metadata. Command names are never used as identity, implicitly or by default.
  - Two declarations may share a display name, and that never causes an identity collision.
  - Identity doesn't depend on Effect internals, object identity or anything else that isn't plain data.
  - v0.4 defines no globally unique or distributed identifier scheme. The concrete representation is the plan's.
- **D5. The minimum model** is C1's table: identity, display name, provenance, and the target-requirements fact. Nothing else, and nothing from the IR.
- **D6. Malformed contexts are rejected, not diagnosed.** A context is malformed exactly when it has:
  - two declarations with the same identity;
  - a declaration without an identity;
  - a span with end before start, or an empty source identity;
  - an empty target capability identifier;
  - a profile that decides one capability both ways.

  Everything else is well-formed and produces a result, including declarations with no facts, empty requirement sets, profiles that decide nothing, and unknown identifiers.
- **D7. Application capability and target capability are separate concepts** (I15). The `Capability` primitive is neither renamed nor redesigned, and it isn't used as, read by or linked to the target-capability model. Their relationship, if any, is deferred decision L1.
- **D8. Target profiles are explicit, declarative input** (C4). NEXUS ships no predefined identifiers or profiles in v0.4, so that no de facto taxonomy appears before a real target needs one.
- **D9. Compatibility is per operation, before any IR** (§3). It isn't, and must not be described as, whole-plan target validation.
- **D10. Semantic analysis never gates execution.**
  - No v0.4 code path refuses to start, admit, run or dispatch anything because of a result.
  - No diagnostic enters any Effect error channel, and no defect path is added.
  - What a consumer does with an `error` is the consumer's decision (deferred decision L3).
- **D11. The analysis entry point is a plain, synchronous, pure function, not an Effect.**
  - It sequences nothing, needs no service, acquires nothing and can't fail except by rejection, so an Effect would add only an Effect type to a boundary that I18 keeps free of them.
  - An Effect caller lifts it trivially.
- **D12. Diagnostic codes, severities and fixes.**
  - Codes are stable, namespaced, kebab-case strings, prefixed `nexus-`, and the v0.4 set is exactly C6's three.
    - The prefix makes NEXUS's namespace distinct from MESH's in any combined tool.
    - No MESH code is reproduced, and none implies a MESH one.
    - Numeric codes are not used: an allocation number carries no meaning, and a string code reads the same in every renderer.
  - Severities are exactly `warning` and `error`.
  - v0.4 defines no machine-applicable fixes.
- **D13. The semantic model is a leaf module.**
  - It imports no other NEXUS module and no MESH or PORT package.
  - No primitive, and not the MESH adapter, imports it.
  - It is exported from the package entry as one new namespace that isn't a primitive, as `Mesh` isn't. ARCHITECTURE §3's primitive set is unchanged.
  - `tests/architecture.test.ts` enforces all of this.
- **D14. PORT stays outside.** v0.4 adds no dependency from NEXUS to PORT, and none from PORT to the semantic model. X3 isn't resolved here (L1).
- **D15. MESH stays as it is.**
  - The semantic model is introduced independently of MESH.
  - `MeshDiagnostics` and MESH's diagnostic codes stay MESH's. They are not aliases for, wrapped in, or translated into NEXUS diagnostics.
  - MESH is not required to emit semantic declarations.
  - Any future translation between the two is a later integration decision.
- **D16. Documents.** This outline is authoritative for v0.4. `FUTURE_DIRECTION.md` stays the long-term direction and isn't edited for v0.4. After release, I11–I19 are synchronized into its §18 as a documentation follow-up.

## 10. Deferred architectural decisions

None of these blocks v0.4, and none can be settled responsibly now. Each must be resolved in the outline of the release named.

- **L1. How NEXUS, PORT and targets relate** (X3, X4).
  - *Why not now:* it needs a revision of ARCHITECTURE §16 (a released contract), PORT's own design, and a decision on how target capabilities are physically provided, and whether an application capability may be backed by one. v0.4 touches none of these.
  - *What depends on it:* where production target profiles come from, whether any plan crosses to PORT, and any seed vocabulary of target capabilities.
  - *Resolve by:* the outline of the first release that integrates PORT or performs target lowering, whichever comes first.
- **L2. How declarations attach to NEXUS primitives, and which facts NEXUS states about its own primitives** (the "NEXUS-understood" tier of `FUTURE_DIRECTION.md` §2).
  - *Why not now:* attaching a declaration to `Command` or another primitive changes that primitive's data model (N4). Stating facts about primitives means deciding which primitive behaviour becomes a semantic contract, which depends on the IR's operation model.
  - *What depends on it:* the IR's operation nodes, and whether commands carry semantics natively.
  - *Resolve by:* v0.5.
- **L3. What downstream consumers do in response to an `error` diagnostic.**
  - *Settled by v0.4, and not part of L3:* what an `error` **means**, and its severity (C6). An `error` means semantic analysis has established a condition that violates the applicable contract. In v0.4, the only such condition is a declared requirement that the supplied target profile explicitly doesn't provide.
  - *Deliberately unresolved:* the **action** a consumer takes on receiving one. A future consumer might reject a build, refuse lowering, prevent execution, display the diagnostic without gating, or apply another policy. v0.4 defines no consumer gating behaviour.
  - *Why not now:* no such consumer exists (R1). Choosing a policy would couple diagnostics to a pipeline that isn't designed yet. Any runtime gating would also change v0.3's lifecycle and admission contracts, which v0.4 keeps (I19, D10).
  - *What depends on it:* CLI and build exit behaviour, lowering, and whether an application may refuse to start on an `error`.
  - *Resolve by:* the first release that introduces a consumer whose behaviour depends on diagnostics. That consumer's policy must not change what an `error` means.
- **L4. Identity stability across analysis contexts.**
  - *Why not now:* v0.4 needs identity only within one context (D4). Cross-context stability is an incremental-analysis concern (`FUTURE_DIRECTION.md` §14) with no consumer yet.
  - *What depends on it:* incremental re-analysis and diagnostic updates in a development server.
  - *Resolve by:* the release that introduces incremental analysis or a development server.
- **L5. Producers of declarations and spans from source** (X2).
  - *Why not now:* it requires source capture, which v0.4 excludes by D1, and a choice of technology (the TypeScript compiler or otherwise) that ARCHITECTURE §21 currently excludes.
  - *What depends on it:* sub-closure granularity (R4), and exact spans without hand-authoring (R5).
  - *Resolve by:* the release that introduces capture. It adds a producer; it must not change C1–C7.

## 11. Non-goals (v0.4)

v0.4 is not, and must not become, any of these:
- **a compiler, an AST analyzer, or anything that reads source:** no TypeScript compiler integration or replacement, tree-sitter, decompilation, or call-site or import discovery;
- **a semantic IR:** no relationships, dependencies, data flow, control flow or scheduling;
- **an optimizer:** no constant folding, dead-operation elimination, common-subexpression elimination, fusion, batching, parallelization or memoization;
- **an execution planner or target backend:** no plans and no lowering;
- **a discovery mechanism:** no runtime tracing, probing, environment inspection or verification of declared facts by execution;
- **an LSP, editor, CLI, development server or build integration;**
- **a PORT integration** (D14);
- **a MESH change:** no change to M1–M4, `renders`, the taxonomy or MESH diagnostics (D15);
- **a lifecycle release:** no new lifecycle primitive, and no change to N1–N4, admission, termination, status or ownership (I19);
- **a primitive change:** `Command`, `Capability`, `Event` and the rest are untouched (D2, D7);
- **a capability taxonomy,** or a shipped profile (D8);
- **a fix for deferred v0.3 items** (O8, O9, O10), or npm publishing.

## 12. Compatibility, verification and Definition of Done

### Compatibility and migration

- **[v0.4] Purely additive.** No existing export, type, signature, error channel or behaviour changes. Every v0.3 test passes unmodified, and v0.3 code needs no migration.
- **[v0.4] One new namespace** is added to the package entry (D13).
- **Documentation for the plan to write** (named, not written here):
  - a reference page for the semantic model, with normative sections held to N4 parity against `dist/**/*.d.ts`, including the coordinate system (C2) and the three codes (C6);
  - ARCHITECTURE: §18's export list; a new section on the semantic boundary, stating the application-capability / target-capability distinction next to §10; a §24 Definition of Done entry for v0.4; and a §26 decision recording D1–D16;
  - README status, and v0.4 release notes;
  - after release only, the `FUTURE_DIRECTION.md` synchronization (D16).

### Definition of Done

v0.4 is done when every item below is proved by a test written before the change it covers. Each item names the invariant, contract or decision it proves.

1. **Declared facts are representable** (C1, C3). Declarations with and without a display name and provenance, with complete, partial and empty requirement sets, and with no facts at all, are accepted and appear in the result as declared.
2. **Insufficient information is opaque** (C4, C5). Undeclared requirements, partial requirements, and complete requirements with an undecided capability are each classified *opaque*, with the right cause.
3. **Opaque never becomes incompatible for lack of information** (I12, I16). An operation with no facts, against a profile that decides every capability it mentions as not provided, is *opaque*, has no `error`, and still runs through `Runtime.run` on a started application exactly as it does without analysis.
4. **Known incompatibility is an error** (C4, C6). Any not-provided declared requirement gives *incompatible* and exactly one `nexus-incompatible-target-capability` error, whether the requirement set is complete or partial, and whether or not compatibility is required.
5. **Supported produces no diagnostic** (C5). A complete, fully provided requirement set, including the empty complete set, gives *supported* and no diagnostics, whether or not compatibility is required.
6. **Diagnostics carry stable codes and provenance** (C6, I17).
   - Each code appears exactly under C5's conditions.
   - Each primary span equals the declaration's supplied span.
   - Each related span equals the supplied requirement or profile provenance.
   - A declaration without a span yields an explicitly unlocated diagnostic with its subject.
   - No diagnostic contains a span absent from the input.
7. **Rendering is independent of the data** (I13).
   - Every result and diagnostic in the suite survives a JSON round trip deeply equal.
   - Two throwaway renderers in a test (a plain-text one and a structured one) render the same diagnostics without either altering the data.
   - Every test asserts on codes, spans and subjects, never on message text.
8. **Target profiles are explicit input** (C4, D8). The only way a profile reaches analysis is through the context. The same declarations against two contrasting profiles give each profile's verdicts.
9. **No discovery happens** (I16).
   - Analysis gives equal results with the process environment, platform and host capabilities varied.
   - A static test shows that the semantic module imports no Node built-in (`node:*`), no platform API, and no other `src/` module.
10. **No implementation is executed** (I11).
    - Declarations are analyzed next to a `Command`, a service layer, a selector and a resource whose functions record any invocation and throw if called. The record stays empty.
    - Analysis runs in a test that never starts an application or makes a runtime.
    - A type-level test shows that no function, `Command` or Effect value is accepted anywhere in a declaration.
11. **No Effect type parameter is semantic metadata** (I14, I18).
    - Two commands that differ only in `R` and `E`, with equal declarations, give equal results.
    - A type-level test shows that the semantic model's public types reference no Effect or NEXUS runtime type.
12. **Application capabilities stay distinct from target capabilities** (I15).
    - An application whose `filesystem` application capability resolves `Unavailable`, analyzed against a profile that provides `filesystem`, gives *supported*.
    - One whose application capability resolves `Available`, against a profile that doesn't provide it, gives *incompatible*.
    - In both, `Capability.resolve` and `Capability.require` behave exactly as before.
    - A type-level test shows that the semantic model accepts no `Capability`, `CapabilityResolution` or `EnvironmentShape`.
13. **MESH's diagnostic contract is intact** (D15).
    - MESH tests 1–9 pass unmodified, and a type-level test shows that `MeshDiagnostics` is unchanged.
    - The adapter doesn't import the semantic module, and no NEXUS code is a MESH code.
14. **PORT stays outside the dependency graph** (D14). The existing no-PORT checks pass, and the semantic module imports no `@valancex/*` package.
15. **v0.3 holds** (I19).
    - All 100 existing tests pass unmodified, including `tests/lifecycle.test.ts`, `tests/runtime.test.ts` and `tests/event.test.ts`.
    - A lifecycle test with an analysis run concurrently with shutdown gives the same outcomes.
    - N4 holds for every existing page, and for the new one.

**Negative and mutation tests.** Each deliberate break must make a named test fail.

| Distinction | Deliberate break | Must fail |
|---|---|---|
| opaque ≠ incompatible | classify missing requirements as incompatible; treat an undecided capability as not provided | items 2 and 3 |
| unknown property ≠ false property | treat undeclared requirements as an empty complete set | item 2: no facts must be *opaque*, while an empty complete set is *supported* (item 5) |
| partial ≠ complete | treat a partial set as complete | item 2 |
| command name ≠ semantic identity | key results by display or command name | two declarations with the same display name and different identities give two independent entries; two with the same identity are rejected (D6) |
| application capability ≠ target capability | consult `Environment` resolutions when evaluating a profile | item 12 |
| diagnostic data ≠ diagnostic rendering | put an `Error`, a function, an escape sequence or an excerpt into a diagnostic | item 7's round trip and type tests |
| classification ≠ emission | warn for opaque operations when compatibility isn't required; emit anything for *supported* | items 2 and 5 |
| declared ≠ inferred | derive a requirement from a command's name or from `Capability.require` usage | items 11 and 12 |
| no execution | call any function reachable from the context | item 10 |
| no fabricated provenance | give an unlocated declaration a span | item 6 |
| no gating | consult analysis in `Application.start` or `Runtime.run` | item 3; lifecycle tests |
| leaf boundary | import a primitive from the semantic module, or the reverse | the architecture test (D13) |

**Clean verification:** a fresh `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test` and `pnpm build`, on Node 22 and 24.

## 13. Risks

- **R1. No consumer exists yet.** There is no CLI, build tool or editor, which is the tension ARCHITECTURE §25 warns about.
  - *Mitigation:* the model is minimal (one property, three codes). Item 7's two throwaway renderers show that the data is enough to render. They are test code, not deliverables.
- **R2. Declared facts can be wrong,** giving a false *supported* or *incompatible*. v0.4 can't detect it (C3).
  - *Mitigation:* every diagnostic cites the declaration's provenance, so a wrong verdict leads back to the wrong declaration. Verification by execution is excluded permanently.
- **R3. Classifications can change across releases.** When a later release adds a property that compatibility or support depends on, an operation *supported* in v0.4 may become *opaque*.
  - *Mitigation:* the property set is recorded in every result (C7), and release notes must call out every addition.
- **R4. The granularity is coarse.** A command is one operation, so a command whose handler calls a target-incompatible library is classified correctly only if its declaration states the requirement (D1). This is inherent until L5.
- **R5. Declarations and spans are written by hand.** Many early diagnostics may be unlocated. This is acceptable for a foundation. v0.4 alone doesn't deliver `FUTURE_DIRECTION.md` §10's editor experience.
- **R6. Pressure to infer.** Deriving facts from input schemas, command names or `Capability.require` calls "because they're right there" is forbidden by I14, and item 11 and the mutation table test for it.

## 14. Deferred to v0.5 and later

- **v0.5 (semantic IR):** operations with dependencies and data flow; inputs and outputs; L2; retaining provenance through transformations (`FUTURE_DIRECTION.md` §10).
- **Analysis and optimization:** effects, determinism, cacheability and fusibility as properties; every transformation in `FUTURE_DIRECTION.md` §7; enforcement of I4 and I10.
- **Target work:** whole-plan target validation (D9), lowering, predefined vocabularies and profiles, capability relationships, discovery and probing (O10), and L1.
- **Capture:** L5.
- **Tooling:** CLI, build integration, development server, incremental analysis (L4), LSP, machine-applicable fixes, severity configuration, a versioned diagnostics document, and L3.
- **Still deferred from v0.3:** O8, O9, O10, and effects running at termination.
