## 1. What v0.4 left off

v0.4 gave NEXUS a semantic model: standalone declarations, one target profile, a compatibility verdict per operation, and three diagnostics. It deliberately modeled no relationships between operations. It also left open how a declaration relates to the executable primitive it describes (L2).

Two gaps follow:

1. **No relationships.** Each declaration is analyzed alone. NEXUS cannot say that `checkout` may observe what `addItem` produced.
2. **No representation.** `analyze` walks raw declarations directly (D5). There is no semantic representation that a later pass can build on, so every future pass would re-walk and re-validate the input.

## 2. What v0.5 is

v0.5 introduces the **semantic IR**: one validated, plain-data representation of an analysis context, built once, which analysis passes read.

```text
Declarations → validation → Built IR → analysis passes
                 (Semantic.build)        (Semantic.analyze)
```

The first new content in the IR is **data flow through semantic values**: operations declare the values they consume and produce, and NEXUS derives which operations may observe what others produced.

v0.5 adds no new diagnostics, no new verdicts and no new pass. The existing compatibility pass moves onto the IR, and its results must not change.

### What v0.5 cannot know, and why that's fine

- **Execution order.** A may-flow edge says a value *may* travel from a producer to a consumer. It says nothing about which runs first, whether both run, or which producer wrote the value a consumer sees. Ordering needs effect and lifecycle semantics that NEXUS does not model yet.
- **Relationships outside the context.** Every relationship is relative to the declarations given. A closed set is complete only for this context.
- **What undeclared operations do.** An operation that doesn't declare its inputs or outputs is an opaque boundary. NEXUS records that, rather than guessing.

Evidence from the repository at `e970163`.

## 4. Terms

- ***Value.*** A declared semantic identity that operations may consume or produce: a cart, a session, a draft. It has no type, mutability or version in v0.5.
- ***Reference.*** One occurrence of a value identity in an operation's inputs or outputs, with its own optional provenance.
- ***Data-flow fact.*** An operation's *inputs* or its *outputs*. Each is either **unknown** (not declared) or **declared**. A declared fact is **complete** (these and only these) or **partial** (at least these).
- ***Producer / consumer.*** An operation whose declared outputs, or inputs, reference the value.
- ***Producer set / consumer set.*** A value's producers, or consumers, within the context. Each is **closed** (known complete for this context) or **open** (a lower bound), and an open set names the operations that *opened* it.
- ***May-flow edge.*** `(P, v, C)`: consumer `C` may observe a value `v` produced by `P`. It is **not** a dependency, happens-before, execution order, or a guarantee that `P` runs.
- ***Built IR*** (*Built*). The validated, plain-data representation of a context that `Semantic.build` returns.
- ***v0.4-shaped context.*** A context that sets none of `values`, `inputs` or `outputs`.

## 5. Invariants

### Carried over, unchanged

I11–I19, M1–M4 and N1–N4, as in the v0.4 outline §6.

### New in v0.5

- **I20.** NEXUS understands declarations, not implementations.
- **I21.** NEXUS represents relationships through semantic values; operation relationships are derived from those values.
- **I22.** A may-flow edge expresses possible value provenance, never execution ordering.
- **I23.** A closed relationship set is complete only within the declared analysis context; an open relationship set is a conservative lower bound on the relationships NEXUS knows about.
- **I24.** Value identities are declared by the context; operation references may only refer to declared values.
- **I25.** Raw declarations are an input format. The built IR is the semantic representation. Analysis operates on the IR, not directly on declarations.
- **I26.** The IR records uncertainty; diagnostics interpret it.
- **I27.** For every valid v0.4-shaped context, `Semantic.analyze` returns a result deeply equal to v0.4's. For every invalid one, it returns the same issues in the same order.

## 6. Contracts

### C8. The input model (additive)

- The context gains an optional list of ***value declarations***, each with an `id`, an optional `name` and optional provenance. **An absent list is equivalent to an empty one**: there are simply no values.
- A declaration gains optional *inputs* and *outputs*. Each, when present, has a completeness (`complete` or `partial`) and a list of references. Each reference has a value identity and optional provenance.
- **Absent inputs or outputs mean unknown, not empty** (D20). Each side of an operation is in exactly one of three states, and they must stay distinct everywhere:
  - **unknown**: no fact was declared. Nothing is known about what the operation consumes or produces on that side.
  - **complete-empty**: an explicit `complete` fact with no references. It means "consumes nothing" or "produces nothing".
  - **partial-empty**: an explicit `partial` fact with no references. It is a declared fact that identifies no specific values. It does **not** say the operation has no inputs or outputs; it says only that this declaration names none. It must not be treated as complete-empty or as unknown.
- Operation, value and capability identities are **separate identity spaces**. A value may share an identity string with an operation or a capability without conflict.
- A reference **may repeat** within one fact. The fact's value set is the distinct set, and every occurrence keeps its own provenance.
- An operation may consume and produce the same value. This is valid and yields a self may-flow edge.
- Value provenance, reference provenance and operation provenance are distinct and must all be preserved.
- Nothing about a value is inferred from names, from operation identities, or from primitives (I14, I20).

### C9. Validation (one validation)

`Semantic.build` validates the whole context once and returns either *Built* or `Rejected` with issues. The rejection cases are:

- v0.4's five D6 cases, unchanged;
- **missing value identity** (`""`), reported as `missing-identity`;
- **duplicate value identity**, reported as `duplicate-identity` at every later occurrence, as in D6;
- **unresolved reference**: a reference whose identity names no declared value, including `""`. This is the new reason `unresolved-reference`;
- **invalid span** on value provenance or reference provenance, reported as `invalid-span`.

Rules:

- New cases fire **only** on the new fields. A v0.4-shaped context yields exactly v0.4's issues, in v0.4's order (I27).
- Issue paths locate the offending field, as in v0.4. The traversal order across the new fields is the plan's decision, provided v0.4 issues keep their relative order.
- Validation is a precondition of *Built*: no *Built* exists for an invalid context.

### C10. The Built IR

*Built* is plain data: no functions, classes, cycles, `undefined` fields or non-JSON numbers. It survives a JSON round trip unchanged, and it is deterministic, so equal contexts give deeply equal *Built* values.

**No optional output fields.** Absence is represented explicitly: an absent `name` or provenance appears as an explicit empty marker (the plan picks one encoding), never as a missing key.

*Built* contains:

- **The profile and required facts**, copied from the context. `Semantic.analyze` reads only *Built*, so *Built* must carry everything the compatibility pass needs (D22).
- **Operations, in declaration order.** Each has its identity, name and provenance; its requirements (as declared, or unknown); and its inputs and outputs, each one of:
  - `Unknown`: a tag with no other fields. No fact was declared on that side, and nothing is recorded in its place.
  - `Declared`: completeness; the distinct values, in first-occurrence order; and every reference occurrence, with its provenance.

  The three C8 states map one-to-one onto these tags:

  | Input | In *Built* | Meaning |
  |---|---|---|
  | absent | `Unknown` | no fact declared |
  | `complete`, no references | `Declared { completeness: "complete", references: [] }` | consumes or produces nothing |
  | `partial`, no references | `Declared { completeness: "partial", references: [] }` | a declared fact that identifies no specific values; it keeps the side open |

  `build` must never turn one of these into another: an absent fact is never recorded as a declared empty fact, and a partial-empty fact is never recorded as `Unknown` or as complete-empty.
- **Values, in declaration order.** Each has its identity, name and provenance, a producer set and a consumer set. Each set is one of:
  - `Closed { members }`;
  - `Open { members, openedBy }`.

  `members` and `openedBy` list operations in declaration order, each once.

### C11. Openness and may-flow

- A value's **producer set is closed if and only if every operation in the context has complete outputs**. Otherwise it is open, and `openedBy` lists exactly the operations whose outputs are unknown or partial.
- Consumer sets follow the same rule, using inputs.
- **Consequence, stated explicitly:** within one context, every value's producer set has the same openness, and so does every consumer set. This is intentional in v0.5: an unknown or partial fact could involve any value.
- An operation with `partial` outputs that list `v` appears in `v`'s producer `members` *and* in `openedBy`. An operation with unknown outputs, or with partial outputs that list no values (partial-empty), appears only in `openedBy`. Partial-empty opens sets exactly as unknown does, but in *Built* it stays `Declared`, not `Unknown`.
- An opaque operation stays an operation node. **No synthetic or wildcard value is created** to stand for "anything".
- A **closed empty** set means only "no operation in this context declares producing (or consuming) this value". It is never a global claim. Closed-empty and open-with-no-members must not be confusable: they are different tags.
- **May-flow `(P, v, C)` holds if and only if `P` is in `v`'s producer members and `C` is in `v`'s consumer members.** A value with many producers yields an edge from every producer to every consumer: unordered, with no indication of which producer wrote it.
- **No edge list is stored.** Edges are derived from membership, and they are never declared (I21).

Example: `addItem`, `removeItem` and `clear` produce `cart`, and `checkout` consumes it. That gives three may-flow edges into `checkout`. If every operation's facts are complete, both sets are closed.

### C12. Analysis on the IR

- `Semantic.analyze(context)` keeps its v0.4 signature and outcome type. It runs `Semantic.build`; on `Rejected` it returns that unchanged; otherwise it runs the compatibility pass over *Built*.
- The compatibility pass reads **only** *Built*. It never reads the raw context after `build`.
- The pass is not exported. It ignores the data-flow fields: **data-flow facts cannot affect verdicts, classifications or diagnostics**.
- `Analyzed.properties` stays exactly `["target-requirements"]`. No data-flow property is added to the analysis outcome, because no pass interprets data flow yet.

## 7. Decisions

- **D17. L2 is resolved by rule: declarations are canonical and standalone.** Association between a declaration and executable primitives is outside the NEXUS semantic model and is the author's concern. NEXUS provides no association and ships no helper in v0.5. Analysis never requires a primitive instance. (Answers L2 with option A.)
- **D18. Relationships go through explicit values** (I21). Operations never reference each other directly.
- **D19. Values are declared, and every reference must resolve** (I24). An unresolved reference is rejected before analysis, not treated as an implicit value.
- **D20. Undeclared means unknown, never empty.** Unknown is never normalized into an empty fact, and open is never treated as closed.
- **D21. Multiple producers give unordered may-flow edges** (I22). There are no sequencing edges.
- **D22. `Semantic.build` takes the full context, including the profile and required facts** (settled). This follows from the approved single pipeline, `raw declarations → validation → Built IR → compatibility pass` (D24, I25). The compatibility pass reads only *Built*, never raw declarations, so *Built* must carry everything needed to reproduce v0.4's compatibility behaviour, including the copied profile and required facts. Operations and values stay target-independent; the profile is carried, not merged into them.
- **D23. Openness is relative to the context** (I23). A set closes only when every operation's corresponding fact is complete.
- **D24. D5 is amended and replaced.** v0.4's D5 had analysis walk declarations directly. From v0.5: one model, one validation, one pipeline (I25). `Semantic.build(context)` returns `Built | Rejected`, and analysis operates only on *Built*. This is the pattern for future releases: new passes read *Built*, and new input fields extend `build`.
- **D25. No new diagnostics for data flow** (I26). Uncertainty is structured IR state. No code is reserved speculatively; future passes define their own codes.
- **D26. The IR is plain data** (C10), inspectable and JSON-round-trippable, with no stored edges and no optional output fields.
- **D27. The semantic module stays a strict leaf.** It is still one file with no imports, exported once as `Semantic`. `build` and the new types join that namespace. No new namespace is added to the entry.
- **D28. Exactly three v0.4 tests are amended, each additively; the other 134 stay unmodified.** Findings B5–B7 show the "unmodified" goal can't be met literally. The amendments are:
  1. **B5, the read allowlist.** Extend the *modeled* key set by exactly the new modeled field names (the working terms *values*, *inputs*, *outputs*, *references*, *value*, and *completeness*, which is already allowed). No other trap changes, so writes, `has`, `ownKeys` and unmodeled reads still fail.
  2. **B6, the exports pin.** Change `["analyze"]` to `["analyze", "build"]`.
  3. **B7, the rejection-reasons pin.** Add `"unresolved-reference"` to the exact union.

  Each amendment only widens a pin to include the approved v0.5 addition. No assertion is removed or loosened beyond that.
- **D29. The no-primitives test.** Removing every executable primitive from the project must not prevent a declaration context from being built into an IR and analyzed.

## 8. Deferred architectural decisions

- **L1, L3, L4, L5:** still deferred, as in the v0.4 outline §10. L4 (cross-context identity) matters more now that values exist; v0.5 keeps every identity context-local.
- **L2:** resolved by D17.
- **Per-value openness.** v0.5 closes or opens every value's sets together (C11). Scoping partial facts to particular values would need a way to say "partial, but only for these values". That is deferred until a pass needs it.

## 9. Non-goals (v0.5)

- No ordering, effects, lifecycle or happens-before.
- No value types, mutability, versioning or schemas.
- No association helper, and no NEXUS knowledge of its own primitives (D17).
- No new diagnostics or diagnostic codes (D25).
- No new analysis pass, and no exported pass.
- No stored edge list or graph API beyond *Built*.
- No target verdicts in the IR's operations or values; the profile is carried only for the compatibility pass.
- No cross-context identity (L4).
- No changes to PORT, MESH, primitives or runtime lifecycle.

## 10. Compatibility, verification and Definition of Done

### Compatibility

- 0.5.0 is additive: `Semantic.build`, the new types, the new optional input fields, and one new rejection reason, all within the `Semantic` namespace.
- Every valid v0.4-shaped context analyzes to a deeply equal result, and every invalid one gives the same issues in the same order (I27).
- 134 of the 137 v0.4 tests stay unmodified and passing; three are amended additively (D28).

### Definition of Done

1. **Input model.** The three states (unknown, complete-empty, partial-empty) map to `Unknown`, `Declared` complete-empty and `Declared` partial-empty, and no state is recorded as another. Partial-empty opens its side's sets, exactly as unknown does. An absent value list builds like an empty one. Identity spaces are separate. Duplicate references keep every occurrence's provenance. Self-reference yields a self may-flow edge.
2. **Validation.** Every C9 case is rejected with the right reason and path. New cases fire only on new fields. Validation runs once.
3. **Closed vs open.** Sets close exactly when every corresponding fact is complete, including the **closed-empty** case. Closed-empty and open-empty are distinguishable.
4. **Uniform openness.** Every value in a context has the same producer openness and the same consumer openness, and `openedBy` is exactly the operations with unknown or partial facts, in declaration order.
5. **May-flow.** Edges are exactly producer members × consumer members, with self-edges. The cart example yields its three edges. Nothing is derived from names.
6. **Plain data.** *Built* survives a JSON round trip, has no optional output fields, and is deterministic.
7. **Purity and no execution.** The v0.4 proxy and recorder tests are extended to *Built* and the new fields: no writes, no unmodeled reads, input unchanged, no ambient channels, synchronous.
8. **Leaf boundary.** The v0.4 architecture checks pass unchanged.
9. **No primitives** (D29). A test builds and analyzes a context without importing any primitive module.
10. **Differential compatibility.** A corpus of valid and invalid v0.4-shaped contexts gives deeply equal results under v0.4's expected outcomes and v0.5's `Semantic.analyze`, including issue order.
11. **Data flow can't reach verdicts.** Adding, removing or changing data-flow facts on a valid context never changes verdicts, classifications, diagnostics or properties.
12. **Docs parity.** `docs/semantic.md` names every new export and field (B8).
13. **Verification.** Typecheck, the full test suite and build all pass.

### Deliberate breaks

As in v0.4, each break below must be caught by at least one test, and the plan records which.

| Break | Must be caught by |
|---|---|
| Unknown facts treated as empty complete facts | DoD 1, 3 |
| A partial-empty fact recorded as `Unknown` or as complete-empty | DoD 1, 3 |
| Partial facts treated as complete | DoD 3, 4 |
| A set closed although some operation's fact is unknown | DoD 3, 4 |
| `openedBy` missing an operation, or listing a complete one | DoD 4 |
| A stored edge list added to *Built* | DoD 6 |
| An edge derived from matching names or identities across spaces | DoD 5 |
| A synthetic wildcard value created for an unknown fact | DoD 3, 6 |
| `Semantic.analyze` reading the raw context after `build` | DoD 7 |
| A data-flow fact changing a verdict or diagnostic | DoD 11 |
| An unresolved reference accepted | DoD 2 |
| A new rejection fired on a v0.4-shaped context, or issue order changed | DoD 10 |
| Duplicate references collapsed so provenance is lost | DoD 1 |

## 11. Risks

- **R7. Uniform openness is coarse.** One unknown operation opens every set, so real projects may see mostly open sets. That is accepted: it is honest, and per-value openness is deferred (§8).
- **R8. May-flow read as dependency.** Consumers may treat edges as ordering. The docs must repeat I22 wherever edges are described.
- **R9. The IR becomes a de facto public format.** *Built* is exported and inspectable, so its shape becomes a compatibility surface. Its fields are documented (B8), and changes to it follow the evolution rule.
- **R10. Declaration drift.** Declarations are standalone (D17), so they can drift from the code they describe. That is the author's concern in v0.5; tooling may address it later, outside the semantic module.
- **R11. Test amendments hide regressions.** D28 limits amendments to widening three pins by exactly the approved additions, and the plan must show each diff.
