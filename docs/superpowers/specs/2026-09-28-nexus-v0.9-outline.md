## 1. Problem statement

**FACT / EVIDENCE.**
- The integration audit found one defect, P1 (IA §16). A default service that a platform supplies, `Layer.setClock` for example, becomes visible in the fiber that called `Application.start`. It can stay there after the application stops. A later application started from that fiber then observes it.
- The audit also found the first gap in evidence (IA §15, items 1–5). No composed slice has yet exercised all of these together:
  - a NEXUS `Application`;
  - a `Platform`;
  - a capability requirement;
  - the MESH runtime;
  - PORT;
  - a real browser.

**INTERPRETATION.**
- v0.9 must make the existing platform seam correct before any composition relies on it.
- v0.9 must then prove the seam in the smallest real composition.
- It must not add a platform abstraction, and it must not change ownership.

## 2. Evidence

All experiments ran against effect 3.22.2, the version NEXUS resolves. NEXUS's source was never modified.
- **E1 and E2** ran as temporary test files in NEXUS's `tests/`, which were deleted afterwards.
- **E3** ran in a **throwaway copy** of NEXUS in the session scratchpad, not in the repository. The copy carried the candidate change from §6 and was discarded afterwards.

### E1. The mechanism, traced by instrumentation (raw Effect, no NEXUS)

**What was done.** Effect's own `Layer.setClock` was re-implemented with logging added, following Layer.ts:1371 → fiberRuntime.ts:3379 → 3364. It was built with `Layer.buildWithScope` into a fresh scope, and that scope was then closed. Each step printed the fiber id and the `currentServices` FiberRef stack.

```text
merge:         caller #0: (no entry → initial)
               acquire in #3; stack #3:C1                 ← a forked branch fiber
               caller after build; stack #0:C1            ← joined into the caller
               release in #5; before #3:C1                ← a close-time fork, running with #3's refs
               release in #5; after  #5:C0 > #3:C1
               caller after close; stack #0:C1            ← the restore is lost
provideMerge:  acquire in #8 (the caller itself); release in #8; caller after close #8:C0   ← restored
```

**A falsified hypothesis.** One hypothesis was that the value persists only when the caller's services equal the FiberRef's initial value. That is false. With the caller on `Effect.withClock(C7)`, the raw `merge` case still ends at 42, and so does the NEXUS platform-merge case.

### E2. Baseline invariant matrix (the repository's `src/`, v0.8.1)

**What was done.**
- **The matrix.** 4 FiberRef kinds × 2 compositions × 2 placements × 2 termination routes = 32 cases.
  - FiberRef kinds: `Layer.setClock`, `Layer.setRandom`, `Layer.setConfigProvider`, and `Layer.locallyScoped(FiberRef.currentMinimumLogLevel)`.
  - Compositions: `Layer.merge` and `Layer.provideMerge`.
  - Placements: in the platform, or in the application's `runtime` layer.
  - Termination routes: `Application.shutdown` (route 1), or closing the start scope (route 2).
- **What each case records:**
  - the caller's value before start;
  - the value inside the application (`Runtime.run`);
  - the caller's value during the run;
  - the caller's value after termination;
  - what a second application, started afterwards from the same fiber with no platform, observes.

**Results:**

| Case | Inside the application | Caller during the run | Caller after stop | Second application |
|---|---|---|---|---|
| `merge`, any kind, either placement, either route | correct | **leaks** | **leaks** | **leaks** |
| `provideMerge`, any kind, either placement, route 1 | correct | **leaks** | restored | clean |
| `provideMerge`, any kind, either placement, route 2 | correct | **leaks** | **leaks** | **leaks** |

The same run gave these further results:
- **Failed start.** When the application layer fails after the platform has been acquired, the platform is released, but the caller keeps the platform Clock.
- **Precedence.** A third application started with no platform, while an application whose own layer set Clock 3 was still running, reads **3** (the other application's own-layer Clock).
- **Concurrency.** Two applications started concurrently on platform Clocks 10 and 20 each see their own Clock, and the caller is left on one of them.
- **Raw scope finalizer.** A finalizer registered directly on the scope writes into the caller on both routes. The platform used for this was `Layer.scopedDiscard(Effect.flatMap(Effect.scope, (s) => Scope.addFinalizer(s, FiberRef.set(currentMinimumLogLevel, Error))))`.

**A correction to IA §16 P1 (X3).** The audit said an application-layer Clock is "restored after shutdown". That holds only on route 1. On route 2 it persists too.

### E3. The candidate change, in the throwaway copy

**What was done.** The change in §6 (build and close isolation) was applied to the throwaway copy.

**Results:**
- `tsc -p tsconfig.typecheck.json` is clean.
- **The full existing suite passes, 391 of 391, with no test edited.** This includes:
  - the lifecycle, platform-lifetime, start-failure and interruption tests;
  - the D39 precedence tests.
- All 32 matrix cases pass.
- The E2 extras now hold:
  - precedence `{platform over caller: 2, application over platform: 3, caller reaches a new application: 1, caller after: 1}`;
  - concurrent applications see 10 and 20, and the caller sees neither;
  - an interrupted start releases the platform, and the caller is clean;
  - a failed start releases the platform, and the caller is clean;
  - a raw scope finalizer leaves the caller clean on both routes.
- The Clock that finalizers see is identical before and after the change: an application release sees 42, and a sibling platform resource's release sees the wall clock, which is Effect's `merge` semantics.
- If the caller changes its own Clock between start and stop, the change is kept.
- `Effect.runSync` of `start`/`shutdown` and of `Runtime.make` works both before and after the change.
- **A build-only variant** (the build isolated, the close not) passes the Clock cases, but **leaks the raw-scope-finalizer write on both routes**. So close isolation is needed, and not speculative.

**FACT** (from the source; the file and line references are to effect 3.22.2 and NEXUS 0.8.1).

      ▼

**INTERPRETATION.**
1. **What leaks.** Leak 1 is Effect's documented meaning of a FiberRef layer: it changes *the fiber that builds it*, for the build scope's lifetime. `Runtime.make` is written exactly like Effect's own `Layer.toRuntime` (layer.ts:1085). So the defect is not an Effect bug. It is NEXUS choosing the caller's fiber as the building fiber, which makes the caller and the application share one set of FiberRefs.
2. **What persists.** Leak 2 comes from two things combined:
   - Effect's finalizer semantics: a release runs under the *acquiring* fiber's refs, and is inverted relative to the *finalizing* fiber's refs;
   - FiberRef join semantics.

   Restoring the caller is therefore not something any shutdown ordering can guarantee while the build happens in the caller's fiber.
3. **Not Clock-specific.** Every default service set by a Layer (`setClock`, `setRandom`, `setConfigProvider`, `setTracer`) goes through the one `currentServices` FiberRef. Every other FiberRef layer (`Layer.locallyScoped`, `Logger.*`, `setTracerEnabled`, …) behaves the same (E2). The unit of the defect is **a FiberRef**, not a service.
4. **Capability resolution is unaffected.** It is a `Context` lookup of `Environment`, not a FiberRef.

## 4. Required invariants

Here, **the caller** means both:
- the fiber that evaluates `Application.start` or `Runtime.make`;
- the fiber that performs termination, whether through `Application.shutdown` or by closing the start scope.

**I44. Caller isolation.**
- For every FiberRef `F`, if the caller's value of `F` is `v0` immediately before `start`, then:
  - after `start` returns (successfully, with failure, or interrupted), the caller's `F` is `v0`;
  - while the application runs, the caller's `F` is `v0`;
  - after termination by either route, the caller's `F` is `v0`.
- The only exception is a change the caller itself makes. NEXUS keeps that change (E3: "the caller's own change is kept").
- Example: caller Clock = C0, platform Clock = C1. Then the caller's Clock is C0 before start, during the run and after the stop, and `Runtime.run(running.runtime, Clock.currentTimeMillis)` sees C1.

**I45. Application view (D39 unchanged).**
- An effect run through `Runtime.run` or `Runtime.runFork` sees each FiberRef as follows:
  1. the caller's value at `start`,
  2. overridden by the platform,
  3. overridden by the application's `runtime` layer.
- The later one wins, which is Effect's layer semantics.
- A caller's tracing span still reaches the application, as `runtime.md` states.

**I46. Lifecycle.** Once termination completes, no FiberRef value written by the platform or the application layer, in acquisition or release, is visible in any fiber outside the application. This holds for any composition (`merge`, `provideMerge`, `mergeAll`, …) and on the start-failure and interruption paths.

**I47. Cross-application.** An application observes only its own caller's values plus its own platform and layer. That holds whether the other application was started concurrently or in sequence, and whether it is still running or has stopped.

**I48. Finalizer view (unchanged).** An application or platform finalizer registered through `acquireRelease` or `addFinalizer` sees the FiberRefs of the fiber that acquired it. This is Effect's rule (fiberRuntime.ts:1710), and v0.9 doesn't change it. Resource release order (C15, I31) is unchanged.

**I49. Start semantics (unchanged).**
- `start` stays an `Effect` with the same type, errors (`ServiceGraphFailed`) and status transitions.
- It stays interruptible during the build, with partially acquired resources released.
- It stays runnable with `Effect.runSync` when every layer is synchronous.

## 5. Proposed boundary semantics

**C29. The application's FiberRefs are its own.**
- `Runtime.make`, and so `Application.start`, builds the service graph (the platform and the application layer) and captures the application `Runtime` in a **child fiber of the caller**.
- The child inherits the caller's FiberRefs at fork, which keeps I45.
- NEXUS never joins the child. It observes it with `Fiber.await`, never `Fiber.join`, so nothing the build writes reaches the caller.

**C30. Termination writes nothing into the terminating fiber.** `terminateLifecycle` closes the lifecycle scope in a child fiber of the terminating fiber, observed with `Fiber.await`. The steps before and after the close are unchanged: the claim, draining admitted work, `onBegin`, closing the bus, `onEnd`, and re-raising a release failure.

**C31. Interruption is forwarded.**
- If the caller of `start` is interrupted while the build fiber runs, NEXUS interrupts the build fiber and waits for it to finish (`Fiber.interrupt`), before the caller's scope finalizer runs termination.
- This gives the same observable order as today's in-fiber interruption: partial acquisitions are released, platform last.

**D68.** The change applies at the one place both routes share: `Runtime.make` for the build, and `terminateLifecycle` for the close. `Application.start` doesn't change.

**D69.** There is no new public type, option, function or export. Types, errors and exports are identical (§6).

**D70.** The guarantee is stated in terms of FiberRefs, not named services. NEXUS still names no default service (D38).

**PROPOSED CHANGE.**
- One internal helper in `src/runtime/internal.ts`: run an effect in a supervised child fiber; await its `Exit` without inheriting its FiberRefs; forward interruption.
- It is used at two call sites: the build in `Runtime.make` and the close in `terminateLifecycle`.

The trial code (E3), for review only:

```ts
// Runs `effect` in a child fiber, and never inherits its FiberRefs (Fiber.await, not Fiber.join).
export const isolated = <A, E>(effect: Effect.Effect<A, E>): Effect.Effect<A, E> => Effect.uninterruptibleMask((restore) =>
  Effect.flatMap(Effect.fork(restore(effect)), (fiber) => restore(Fiber.await(fiber)).pipe(
    Effect.onInterrupt(() => Fiber.interrupt(fiber)),
    Effect.flatten
  )));
```

## 6. Candidate isolation mechanisms

**INTERPRETATION.** The smallest *existing* Effect mechanism that meets I44–I49 is a **forked child plus `Fiber.await`, with interruption forwarded**, applied to both the build and the close. Every other candidate either fails an invariant or brings in a lifecycle hazard.

| Candidate | What it isolates | Fiber / runtime | Do children inherit the application environment? | Scoped finalization | Interruption and shutdown | Start's asynchrony | Public API change | Verdict |
|---|---|---|---|---|---|---|---|---|
| **A. `Effect.fork` + `Fiber.await` + `onInterrupt(Fiber.interrupt)`, for the build and the close** (chosen) | every FiberRef, in both directions | a supervised child of the caller; the application `Runtime` is captured in it | yes: `Runtime.run` roots come from the captured snapshot; the build's own concurrent branches join into the child | unchanged: the resources belong to `lifecycle.scope`, and finalizers run under their acquire refs (E3: identical) | unchanged, and interruption is forwarded explicitly (E3: an interrupted start releases the platform); termination stays uninterruptible, since the forked close inherits its flags | same `Effect`; one extra fiber hop; `runSync` still works (E3) | none | **Chosen.** E3: 391/391 unchanged, and 32/32 matrix cases |
| B. The same, **build only** | FiberRefs written during the build | as A, for the build | yes | unchanged | unchanged | same | none | **Rejected.** A raw scope finalizer still writes into the terminating fiber on both routes (E3) |
| C. `Effect.fork` + `Fiber.join`, or `Effect.disconnect` | nothing | a child | — | — | — | — | none | **Rejected.** `join` is `await` plus `inheritAll` (fiber.ts:160), and `disconnect` uses `join` (fiberRuntime.ts:3555), so the build's refs reach the caller as they do today |
| D. Snapshot and restore the caller's refs (`getFiberRefs`/`setFiberRefs`) around start and termination | whatever was snapshotted | the caller | yes | unchanged | **hazard:** a whole-FiberRefs restore also rewrites refs that the build or finalizers must not reset, such as the runtime-flags ref inherited through `inheritAll` (fiberRuntime.ts:487), inside uninterruptible regions; and it would silently undo a caller's own concurrent change (M10) | same | none | **Rejected.** It hides a lifecycle hazard |
| E. `Effect.locally` or `locallyScoped` around the build, per FiberRef | only the FiberRefs listed | the caller | yes | unchanged | unchanged | same | none | **Rejected.** It needs an inventory of FiberRefs, which is Clock-special thinking (§3, item 3); unknown and user FiberRefs still leak |
| F. `ManagedRuntime.make` / `Layer.toRuntime` on a fresh root fiber (`Effect.runFork` on the default runtime) | everything, including the caller's refs | a new root fiber, detached from the caller | the application loses the caller's refs | its own disposal, outside `lifecycle.scope` | **breaks:** the caller's interruption and scope no longer govern the build; admission and termination would need rewiring | different: `ManagedRuntime` builds lazily and is `Promise`-based | likely | **Rejected.** It breaks I45 (the D39 test "the caller's Clock reaches the application runtime") and C15/I31 ownership. `Layer.toRuntime` alone is exactly today's code (layer.ts:1085) and leaks |
| G. Document "use `provideMerge`, not `merge`, in platforms" | nothing during the run | the caller | yes | unchanged | unchanged | same | none | **Rejected.** `provideMerge` still leaks during the run, and after route 2 (E2) |
| H. Forbid FiberRef layers in platforms (a type or runtime check) | — | — | — | — | — | — | yes | **Rejected.** It contradicts D38 ("a platform is the intended place to set them"), and it's a new restriction rather than isolation |

**A note on the rejected alternatives.** None of them was rejected merely because it failed the Clock test. C, E, F, G and H fail invariants. D is rejected for a hidden lifecycle hazard, even though it could be made to pass the matrix.

## 7. Public API impact

**FACT.**
- Candidate A changes no exported type, value, error or module (D69).
- The existing tests pass unedited, including `tests/exports.test.ts` and the D39 tests (E3).

**INTERPRETATION. The fix is an implementation change together with a new, documented guarantee (I44–I47).** It does not change any existing documented contract:
- `application.md` and `runtime.md` document the D39 precedence *into* the application, and that "a runtime inherits them from the fiber that builds it". Both stay true.
- Nothing documents the reverse direction. The leak was undocumented behavior.

It is observable, though. Code that read a platform-set default service *outside* the application (for example, a composer that happened to see the platform's Clock) will see its own instead. The release notes must state this as a behavior change. Because NEXUS is pre-1.0, it belongs in a minor release: **0.9.0**.

## 8. Browser evidence goal

**Goal.** Prove, in real Chromium, one composition of everything the audit found unexercised:

```text
MPRX ─(mesh-compiler, build time, Node)─▶ template-v1 ─▶ @valancex/mesh-runtime (WASM, init(url) in the page) ─▶ render-v1
  ─▶ NEXUS Application (state, users.select, users.refresh + one capability requirement)
  ─▶ test Platform (provides the capability; also sets a Clock, to exercise I44 in the page)
  ─▶ composer (test infrastructure) ─▶ @valancex/port-web ─▶ Chromium DOM ─▶ real click ─▶ back
```

### Design (specified here, implemented in the plan's PORT tasks)

**Where.**
- PORT's private `integration/` workspace. It's the only place all three packages meet (IA §3).
- It uses the published `@valancex/nexus` 0.9.0, once released (the plan orders this).

**Runner.**
- Vitest browser mode with the Playwright provider, on the pre-installed Chromium (`executablePath` `/opt/pw-browsers/chromium`; `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`).
- Test code, NEXUS, `port-web`, `effect` and `mesh-runtime` run *in the page*.
- Clicks go through `@vitest/browser/context`'s `userEvent.click`, which drives Chromium's real input pipeline, producing trusted `MouseEvent`s.
- An alternative is recorded in O16.

**Build step.**
- A vitest `globalSetup`, in Node, compiles `fixtures/mesh-slice` with `@valancex/mesh-compiler`.
- It passes the `Program` (the root, the template-v1 texts and the manifest text) to the page with `provide`/`inject`.

### The negative case

The same page, program and composer, with a platform that provides **no** `UsersSource`. The platform is `Capability.EnvironmentLive(new Map())` merged with the same Clock, and its statement is `{ provided: [], notProvided: [UsersSource.id] }`.
1. **Analysis.**
   - `users.refresh` is `incompatible`, with verdict `{ _tag: "Incompatible", notProvided: [UsersSource.id] }` and a diagnostic `nexus-incompatible-target-capability`.
   - `start` and `users.select` are `supported`.
   - Conformance reports `[]` (the statement is honest).
2. **Start still succeeds.** Status is `Running`. This is current NEXUS semantics: an admitted unit's requirement is not start necessity (C27, I41, and the v0.8 test "an admitted unit's requirement is only that unit's"). v0.9 doesn't change it.

4. **A real click on Refresh:**
   - the dispatch `Exit` is a failure whose error is `{ _tag: "CapabilityUnavailableError", id: UsersSource.id, reason: "no resolution registered for 'slice.users-source'" }`;
   - the state is unchanged;
   - the DOM is unchanged, with the same `<img>` and `src="ada.png"`;
   - the application is still `Running`.
5. **Afterwards, a second avatar click still dispatches `users.select` successfully.**

- It doesn't move the composer into a package.
- It doesn't use `hydrate` or SSR, because the jsdom tests already cover them.
- It doesn't add a second capability.
- It doesn't bundle for production.

## 14. J1: the application fiber `Runtime.runFork` hands out (investigation, 2026-09-28)

The full analysis is in the decision memo, [`../../architecture/2026-09-28-j1-application-fiber-boundary.md`](../../architecture/2026-09-28-j1-application-fiber-boundary.md). This section records only what changes in this outline. **I44–I49 are not redefined.**

**FACT / EVIDENCE.**
- **Where the fiber comes from.** `Application.start` returns `RunningApplication` (`status`, an opaque `runtime` handle, `environment`), not a fiber. The fiber is `Runtime.runFork`'s return value: the application runtime's own root fiber.
- **What it leaks.** On the P1 fix (`b7f5e4d`), `Fiber.join`, `Effect.fromFiber` or `Fiber.inheritAll` on that fiber copy the application's FiberRefs into the caller, and they persist after shutdown. `await`, `interrupt`, `poll` and `status` don't.
- **How it's used.** There are 24 `runFork` call sites (NEXUS tests, PORT jsdom and Chromium). 9 `join`, and only for the value; none uses the FiberRef import.

**INTERPRETATION.**
- Under the current API, I44, I46 and I47 **cannot be guaranteed for ordinary use of `runFork`**.
- J1 splits into two parts:
  - **J1a, `runFork`'s fiber:** an implementation defect, fixable with no public API change;
  - **J1b, execution state that application code returns as a value through `run`/`runFork`:** unresolved architecture (O19).

**PROPOSED CHANGE (pending approval; not implemented).**
- **C32.** `Runtime.runFork` returns a handle NEXUS controls, never the application's own fiber:
  - a root fiber on Effect's default runtime that awaits the application fiber (`Fiber.await`, never `join`) and forwards interruption;
  - the same exported type, `Fiber.RuntimeFiber<A, E>`;
  - the returned fiber's `id()` and `status` describe the handle.
- **Evidence in a throwaway copy:**
  - all 444 tests pass unedited;
  - the unchanged Chromium tracer bullet, with its original `Fiber.join`, is green 3 of 3;
  - the jsdom integration passes 15/15.
- **Decision D71.** Option D in the memo, over B (a breaking change to the return type) and C (a documented escape, which is weakening), and over A (the status quo, which breaks I44).

**OPEN QUESTION O19 (J1b).** Should I44's boundary cover execution state that application code deliberately returns as a value, such as a daemon fiber, its `FiberRefs` or its Effect `Runtime`? No NEXUS return type can prevent it. It is deferred past v0.9. No current consumer does it.

**Exit criteria, amended (additive).**
- 7. The J1a regressions (plan Task A7) pass. Returning the application fiber from `runFork` again fails them.
- 8. The Chromium tracer bullet passes **unchanged**, including its `Fiber.join`, against the release candidate.
