## 1. Problem statement

> *How does an actual NEXUS application and its primitives declare the capabilities they require, at the correct semantic granularity, without coupling runtime execution to static analysis?*

v0.7 defined what a requirement **means** (D46: necessity, not use) and how it is **related** to a platform (the platform binding, C19–C23). It left open **what owns one**. "Granularity is the producer's" was a deliberate placeholder, with L2 as the question.

The audit shows why the placeholder can't stay:
- **NEXUS has no data representation of an application beyond its `name`** (ASA F1). It has no primitive graph, no inventory and no registry.
- **A requirement is true of code that runs, in a given composition** (F2, F3). The same `Command` value requires `acme.network` under one service implementation and nothing under another (Y3).
- **"The application requires X" has two different meanings** (N2). One is necessity of the whole: without X, the application doesn't start (Y5). The other is the union of its parts: some unit can't work without X. v0.7's wording conflates them (ASA §M, contradictions 1 and 3).

v0.8 must decide **where a requirement is owned**, **what "an application's requirements" means**, and **how unit requirements combine**. It must do so without giving any runtime value a requirement, and without giving `Semantic` any knowledge of NEXUS primitives.

The question this outline answers is not *"what API is convenient?"* It is *"what semantic fact must exist, where is it owned, and what is the smallest boundary that can carry it?"*

## 3. Terminology

Working terms. Each names a meaning, not a new type.

- **Unit.** A part of an application that NEXUS executes as a whole, at one execution position (§5). A unit is what one semantic declaration describes. It is Semantic's *operation*, under the platform binding.
- **Start unit.** The application's service graph build: its `runtime` Layer, built by `Application.start` after the platform. If it fails, `start` fails with `ServiceGraphFailed` and the application never runs (ASA §B).
- **Admitted unit.** An effect that runs as admitted work through `Runtime.run` or `Runtime.runFork`, while the application is running. Commands, invoked through `Command.invoke`, are the named case. So are long-lived forks, and a MESH dispatch that reaches a command. If it fails, only that effect fails.
- **Composition.** The choice of implementations an application's `runtime` Layer makes: for example, `HttpUserRepository` or `InMemoryUserRepository` behind `UserRepository`.
- **Application context.** An `AnalysisContext` under the platform binding that describes **one application composition**, against one platform statement (C24).
- **Unit requirement.** A unit's declared `requirements`: the v0.7 fact, unchanged.
- **Application necessity.** The capabilities without which the application can't start. By C27 this is exactly the start unit's requirement.
- **Application requirement set.** The capabilities that *some* unit of the application can't work without: the union of C26. It is not necessity.
- **Application classification.** Supported, opaque or incompatible for the application as a whole, derived by C26.

## 4. A. What is a requirement?

**D56. The requirement is exactly v0.7's.**
- A *unit requirement* is the plain-data claim *"this unit cannot correctly perform its declared behavior unless capability `X` resolves `Available`"*.
- Its form is a `Semantic.Requirement { capability: X.id, provenance? }` inside the unit's `TargetRequirements`.
- `complete` means exactly these. `partial` means at least these. Absent means unknown.

No new requirement type is introduced. The evidence is ASA F5: the released type already carries identity, completeness and per-occurrence provenance, and every other form in ASA §I.1 either duplicates it or couples to the runtime.

**Optional use stays outside the model** (C23 kept, O10 still deferred). *"This unit can optionally use `X`"* is not a requirement. A unit that `resolve`s `X` and has a fallback declares nothing about `X`. If it requires nothing else, it declares `complete` and empty. v0.8's evidence shows no consumer that needs optional use as a fact. The unit model doesn't need it either, because a unit with a fallback is simply not incompatible.

**A requirement is a structural claim, never an effect** (I43).
- It is not an `Effect`, a `Layer` or an `R` type parameter (D51).
- It isn't produced by running anything.
- Declaring one executes, resolves, acquires or registers nothing.

## 5. B. What owns a requirement?

### Evidence

- ASA §B: application code reaches the `Environment` at exactly two execution positions. These are the start-time service graph build and admitted work. They fail differently (Y5).
- ASA §D: `State`, `Selector`, `Event`, the `Service` contract and `Capability` can't require a capability (F4). A service implementation, a resource or a command handler can, but only a command has a NEXUS identity (its `name`).
- ASA F3: a command's requirement depends on the composition (Y3). It is intrinsic only to anonymous code.
- ASA F1, F6: there is no application inventory, and Semantic has no containment.

### Options

| # | Owner | Assessment |
|---|---|---|
| 1 | **The application**: one declaration, or a definition field | It hides which part needs what, and conflates necessity with union (N2). As a field it is dead or a gate (Y4, D46). As one declaration it is kept as a special case of option 4. |
| 2 | **Primitive definitions** (`Command`, `Service`) | Wrong in kind for services, because a contract has no requirement. Composition-relative for commands (Y3). As a field it is dead, or couples runtime or MESH to requirements (N5). |
| 3 | **Primitive instances** (an implementation `Layer`, a handler closure) | This is where the fact is intrinsic (F3), but instances are anonymous. Carrying data on them needs a NEXUS layer type (against D52) or a registry (against ROADMAP §20). |
| 4 | **Units**: the start unit and each admitted unit, one standalone declaration each | It uses the released type (F5). It is aligned with the lifecycle (Y5) and composition-relative like the fact (I42). It gives per-unit diagnostics, and the application level is derivable exactly (Y1). No runtime change. |
| 5 | **Layered with containment** (application ⊇ services ⊇ operations, with inheritance) | It needs a containment relation and a new IR pass. It makes necessity inheritable, which is false (N2). It answers an authoring-scale problem that has no evidence yet (G2, O14). |

### Decision

**D57. Requirements are owned by units (option 4).**
- An application has exactly one **start unit**, and any number of **admitted units** (§3).
- Each unit an application context covers is described by **exactly one** `Semantic.Declaration` (C25).
- A unit is identified by that declaration's `id`, which is context-local (L4 unchanged).

**D58. These are not requirement owners:**
- the `ApplicationDefinition` and `StartOptions`;
- any primitive value: `Command`, a `Service` tag, `State`, `Selector`, `EventDef`, `Capability`;
- any `Layer`;
- anything finer than a unit, such as a service method or a resource acquisition inside a unit.

Such parts contribute to the requirement of the unit they run in. Declaring them separately, in the same context, overlaps that unit (C25). Reuse of a shared implementation across units is O14.

**Why not option 1.** It stays *expressible*: an application with one admitted unit, or an author who declares the start unit only, is a one-unit or two-unit context. It isn't the owner, because it can't state "the application starts, but `export-pdf` doesn't work" (N2).

**Why not option 5.** Containment is new IR structure that no consumer needs. Inheriting necessity would be false (C27). v0.7's "whole-application declaration" is an aggregation, and C26 gives it exactly without containment.

**Why not options 2 and 3.** The fact isn't intrinsic to the definition (Y3). Where it *is* intrinsic, the thing has no identity NEXUS could carry data on without a registry or a wrapper.

### C28. What a unit can contain (the roles of NEXUS primitives)

This is the documented meaning of each primitive for application semantics. It is not data on any value.

| Primitive | Role in application semantics |
|---|---|
| `Application` | Its `runtime` Layer build is the **start unit**. The definition itself owns nothing. |
| `Runtime` | The mechanism admitted units run through. It is not a unit. |
| `Command` | The typical **admitted unit**. Its requirement is relative to the composition. |
| service implementation (`Service.layer`) | Part of the start unit if it resolves capabilities while being built. Part of each admitted unit that calls its methods otherwise. |
| `Resource` | Part of the unit that acquires it. |
| `Event`, `State`, `Selector`, `Service` contract, `Capability` | Never require a capability (F4). They appear in no unit's requirements. |
| a forked effect (`Runtime.runFork`) | An admitted unit, if the author declares it. |

## 6. C. How are requirements combined?

### D59. The application is the analysis context (C24)

An application's requirements, as analyzed, are the requirements of the units in its application context. There is no application-level *declaration* separate from its units (I40), and no NEXUS value that lists an application's units (F1). **The context contains the units the producer has chosen to describe.** Nothing says it lists every unit of the application. Every application-level fact derived from it is relative to that choice (I23, R26), and whether a context can claim completeness is O13, deferred.

### D60. Two application-level facts, both derived

1. **Application necessity** is the start unit's requirement (C27).
2. **The application requirement set** and **the application classification** are the aggregation of all units (C26).

Neither is declared separately. Neither is stored by NEXUS.

### C26. The aggregation algebra (normative)

Over the units `u₁ … uₙ` of one application context, in declaration order:

| Aspect | Rule |
|---|---|
| **Identity** | By `Capability.id`, exact string equality (I34). |
| **Set** | The distinct ids of every unit's declared requirements. |
| **Order** | First occurrence: declaration order, then each unit's `capabilities` order. |
| **Duplicates** | Within a unit, evaluated once and every occurrence kept (C4, unchanged). Across units, one set member, and every occurrence kept, each attributed to its unit's `id`. |
| **Completeness** | `complete` exactly when every unit's requirements are declared `complete`. Otherwise `partial`. An **undeclared** unit contributes *partial-empty*, never "absent": Y1's counter-check shows that "absent" would hide an incompatible unit. |
| **Classification** | `incompatible` if any unit is incompatible; otherwise `opaque` if any unit is opaque; otherwise `supported`. |
| **Equivalence** | The classification equals C4's classification of one declaration carrying the union (the set, with the completeness above). Y1 checks this over 7,380 cases. This is the exact meaning of v0.7's "whole-application declaration gives the verdict of the union". |
| **Verdict cause** | Not aggregated. Causes stay per unit (ASA F7). |
| **Empty context** | Complete-empty and *supported*, **vacuously**. Like every closed fact, it is relative to the context (I23). It says nothing about units the context doesn't list (R26, O13). |
| **Contradiction** | Requirements are monotone positive claims. Across *different* units nothing can contradict: the union is always defined. Two claims about the *same* unit can't meet in one context: Semantic already rejects a duplicate `id` (C9, ASA F8). How a producer merges several sources about one unit is outside NEXUS (D62). |
| **Inheritance** | A unit's requirement enters the application **requirement set**. It never becomes application **necessity** (C27, I41). |
| **Partial** | A unit's `partial` stays `partial`: it opens the aggregate, and makes it opaque unless some unit is incompatible (C4 step 1 still first). |

**D61. The algebra is contract, not API.** v0.8 states C26 normatively and pins it with **test tooling only**, as v0.7 did for conformance (C21). No `Semantic` function or field computes it (D66). Any future consumer or export must compute exactly C26.

**D62. One unit, one declaration.** A unit is described once per context. Combining several statements about the same unit (for example, hand-written plus tool-produced) is the producer's job, done before analysis. NEXUS defines no merge, because two `complete` claims that differ about one unit contradict each other, and choosing one is the producer's policy.

### C25. Units are disjoint

In one application context, **no declaration may describe execution that another declaration in the same context describes.**
- Semantic can't check this, because it has no containment (Y2), so this is a producer rule.
- Overlap doesn't corrupt the aggregate set, because the union is idempotent.
- Overlap does make per-unit results misleading. An `app` declaration that claims `complete [A]` next to a unit requiring `B` reads as "`app` supported" (Y2). That claim is false about the application, and true only of a unit that doesn't exist.

### C27. Necessity is per unit

- The application's necessity is exactly the **start unit's** requirement.
- An **admitted** unit's requirement is that unit's necessity only.
- An incompatible admitted unit means that unit can't work on that platform. It never means the application can't start or run (Y5; I37 unchanged).

## 7. D. Provenance

**D63. v0.8 adds no provenance, and O3 stays deferred.**

- **Which unit** a requirement comes from is structural: the declaration `id`. `Built` already keeps it with every `BuiltRequirement` (ASA F11). C26's attribution of every occurrence to its unit needs nothing more.
- **Where** a requirement was written is the optional per-occurrence `Span`, as released (C2, I17). v0.8 adds no source-location machinery, and producing spans stays L5.
- **O3** asks *which platform contribution supplied an id*. That is provision-side provenance. It has no consumer in v0.8. With one platform per start (D50), it has one answer.
- Requirements need provenance *at declaration time* only in the sense they already have: an optional span. A requirement without a span is complete, and its diagnostics are unlocated or have no related span, exactly as today.

## 8. E. Relationship to `Semantic`

**No change to `src/semantic`.** No type, field, code, message, rejection, export or behavior changes.

```text
application author / tooling (outside src/)
        │ writes one Declaration per unit, naming Capability ids   (C19, D57)
        ▼
plain data: AnalysisContext { declarations: units, profile: platform statement }   (C24)
        ▼
Semantic.analyze(context)        → per-unit verdicts and diagnostics (unchanged)
        ▼
aggregation (C26)                → computed by a consumer, or by NEXUS test tooling only (D61)
```

- The v0.7 invariant holds exactly: **application declarations → plain data → `Semantic.analyze`.**
- No NEXUS runtime module imports `Semantic`, and the leaf test is unchanged (D13).
- Semantic never discovers units, and never executes an application to find them.
- No closure, `Effect`, `Layer`, `Environment` or runtime service is ever an input.
- The 35-export and 2-runtime-value pins hold, and so does the v0.4 corpus (I27). An aggregate field on `Analyzed` would break I27 (ASA F9). That is one reason for D66.

## 9. F. Relationship to `Capability`

- **`Capability.id` is the semantic capability identity** (I34), with no second identity and no mapping table. A unit's requirement names `SomeCapability.id` verbatim, written by the producer (C19).
- No registry. NEXUS defines no capability id (I38).
- **The capability contract is never a requirer** (C28). A capability doesn't require other capabilities in this model. Composing capabilities is platform composition (D50).
- `resolve` and `require` are unchanged. `require` without a fallback is still the typical sign of necessity, and `resolve` with a fallback the typical sign of use (C23). Neither is *read* by anything.

## 10. G. Relationship to the runtime

**Static requirement ≠ runtime resolution** (I36, I37, I43).

A declared requirement changes none of these, in any case:

| | Unchanged |
|---|---|
| `Application.define` | takes and keeps exactly `{ name, runtime }`; no requirement field (I39) |
| `Application.start` / `StartOptions` | exactly `{ platform? }` (D42); no gating (I37) |
| `Capability.resolve` / `require` | exactly the platform's resolutions (I36) |
| platform acquisition | unchanged (C15, I31) |
| service graph construction | unchanged; the start unit is a *reading* of it, not a new step |
| `Runtime.run` / `runFork`, `Command.invoke` | unchanged; admission ignores declarations |
| MESH dispatch | unchanged (M1–M4) |

Enforcement ("refuse to start on an incompatible start unit", "refuse a command whose unit is incompatible") would each be a separate, explicit decision about L3. v0.8 makes neither. They would also have to keep I37, or revise it deliberately.

## 11. Relationship to MESH

**None.**
- The adapter is unchanged, and M1–M4 hold.
- A MESH intent reaches a command only through the host's binding table. So a dispatched intent reaches an *admitted unit* only through the host. Relating a MESH intent to that unit's verdict is the host's or tooling's join, outside NEXUS. v0.8 defines no join key (D65).
- MESH owns no application capability, and no requirement enters MPRX, render trees or bindings.

## 12. Relationship to PORT

**None.**
- Application contexts are platform-binding contexts (C22).
- A PORT binding, render-side requirements, and any implication across bindings (for example, a DOM target implying a platform that hosts it) stay **L1**.
- NEXUS gains no PORT dependency, and PORT none on NEXUS.

## 13. L2 and D17

**D64. L2 is closed, and D17 is confirmed (not revised).**
- *First half*, how declarations attach to primitives: they don't. Declarations stay canonical and standalone. Association is the producer's, and outside the contract (D65).
- *Second half*, which facts NEXUS states about its own primitives: **NEXUS states no plain-data facts about its primitive values.** It states *meanings* in its documentation: which roles can be units, and which can never require a capability (C28).
- A producer that derives declarations from primitives, source or types would be **L5** (capture), outside `src/`, and would add a producer without changing this contract.

The evidence is ASA N5 and Y4: every attachment point is dead, gating, coupling, wrong in kind, or a registry. D17 was chosen before this evidence existed. It is now confirmed by it.

**D65. A declaration identifies a unit within its application analysis context** *(Revision 2)*.
- The mapping between an external producer's unit and a NEXUS primitive identity is producer or tooling responsibility. It is **not part of the NEXUS v0.8 contract**.
- v0.8 establishes no unit-id convention. `Command.name`, `Application.name` and every other primitive identity are neither required nor recommended as declaration ids.
- *Why:* no consumer needs this join yet. Establishing it now risks a de facto second identity relationship. Identity across contexts and systems is L4, which stays deferred. The first real consumer should provide the evidence for whether a stable cross-system unit identity is needed.

*Revision 1's text, kept for the record:* a non-normative convention, with a command unit's id being its `Command.name` and the start unit's being the `Application` definition's `name`.

**D66. No exported aggregate in v0.8.** C26 is computed by consumers. Any future export is O11.

**D67. The public API of v0.8 is identical to v0.7**: the same 11 namespaces, G3, the 35 and 2 pins, and `StartOptions`. v0.8 adds contracts, tests and documentation.

## Contracts (new)

- **C24. One application context, one composition.** Under the platform binding, an application context describes exactly one application composition against one platform statement. Its declarations describe units of that composition. A different composition is a different context.
- **C25. Units are disjoint** (§6). This is a producer rule, and Semantic doesn't check it.
- **C26. The aggregation algebra** (§6), normative, and pinned by test tooling only.
- **C27. Necessity is per unit.** Application necessity is exactly the start unit's requirement. An admitted unit's requirement never becomes the application's.
- **C28. Primitive roles** (§5). This is documented meaning, not data.

## Invariants (new)

- **I39. Requirements live in declarations, not in primitives.** No NEXUS primitive value, definition, `Layer`, start option or runtime handle carries a requirement.
- **I40. Application-level requirement facts are derived.** They are computed from unit declarations. NEXUS never declares or stores them separately.
- **I41. Unit necessity is not application necessity.** A requirement is inherited into the application's requirement set, never into its necessity.
- **I42. Requirements are relative to the composition.** A unit's requirement holds for the composition its context describes.
- **I43. Requirements are structural claims, not effects.** Declaring executes, resolves, acquires and registers nothing, and executing declares nothing.

## Risks

- **R24. Composition drift.** A unit declared for one composition (`Http`) is analyzed with another (`InMemory`). *Mitigation:* C24 and the docs. It is undetectable by design.
- **R25. The union read as necessity.** "The application requires X" said of the requirement set. *Mitigation:* C27, I41, and the terminology in `capability.md`.
- **R26. Incomplete inventory.** A context missing a unit gives a false application-level *supported*. The unit is invisible, not unknown. *Mitigation:* I23's "relative to the context" wording. Escalation is O13.
- **R27. Overlapping units** (Y2) give misleading per-unit results. *Mitigation:* C25, the docs, and a characterization test.
- **R28. Authoring scale.** Many commands using one implementation repeat its requirement (G2). *Mitigation:* none in v0.8. Escalation is O14.
- **R29. A producer's id read as a NEXUS identity.** Tooling may choose ids that happen to equal `Command.name`s, and readers may take that as a NEXUS relationship. *Mitigation:* D65 states that the mapping is outside the contract, and the docs repeat it. L4 is unchanged.
- **R30. A second release with no API change reads as no release** (as R23). The new contracts are C24–C28 and I39–I43, with tests (§T), per roadmap §22.1.

## Migration

**None: v0.8 is non-breaking.**
- No public type, value or behavior changes, and no existing test is amended.
- Wording changes only:
  - v0.7's "Granularity is the producer's" becomes the unit model (D57), in `capability.md` and `semantic.md`;
  - "Application requires Network and Storage" is reworded as the requirement set, not necessity (R25);
  - ROADMAP §9's tree gains a note that its `requires` lines denote C27's two readings (ASA §M.1, §M.2).
- A v0.7 context with one "whole-application" declaration stays valid. It is a one-unit context, and C26 gives it the same classification.

## Non-goals

v0.8 does not introduce:
- any change to `src/`;
- a requirement field, metadata bag, annotation or decorator on any primitive, definition, `Layer` or start option;
- a registry or inventory of units, commands or services in NEXUS;
- automatic discovery; deriving declarations from execution, `Layer`s, `R` types or source (L5);
- environment detection, platform inspection or platform composition (D50);
- start-time or dispatch-time gating, or any enforcement (I37, L3);
- a second capability identity, a mapping table or NEXUS-owned capability ids (I34, I38);
- containment, "uses" relations or inheritance in the semantic IR (O14);
- an exported aggregate (O11), a unit kind (O12), or an inventory-completeness fact (O13);
- provenance beyond the released spans (O3);
- optional-use facts (O10), a serialized format (O9), a domain tag (O8), or public conformance (O7);
- PORT dependencies or a PORT binding (L1); MESH changes; MESH capability dependencies.

## Tests (§T)

**Guardrails.** These must pass unchanged, with no amendments:
- all 366 tests;
- the leaf, G1–G4, and the 35 and 2 pins;
- the v0.4 corpus;
- the v0.7 capability-model and conformance tests.

**New tests.** One file, `tests/application-semantics.test.ts`, using only the public API. The aggregation helper is a local function in that file: test tooling, not exported and not in `src/` (D61).

1. **Units in the lifecycle** (C27, Y5):
   - a start unit whose implementation `require`s a capability at build fails `start` with `ServiceGraphFailed` on a platform without it;
   - an admitted unit that `require`s it leaves the application `Running`, and fails alone.
2. **Composition relativity** (C24, I42, Y3):
   - the same `Command` under two compositions has two behaviors;
   - the two contexts that describe them give two verdicts, and neither context changes either behavior.
3. **Aggregation algebra** (C26, Y1):
   - exhaustive equivalence of the worst per-unit classification with the union's C4 classification;
   - first-occurrence order;
   - cross-unit duplicates keep every occurrence, attributed to its unit;
   - an undeclared unit contributes partial-empty (with the Y1 counter-check as a named case);
   - the empty context is vacuously supported.
4. **No inheritance of necessity** (C27, I41):
   - an application whose admitted unit is *incompatible* against a statement still starts on a platform matching that statement;
   - its other admitted units run.

## Decisions for the reviewer

These are the choices that most need a reviewer's explicit yes or no. Each has a recommendation, and each can be changed without invalidating the others.
