  - **P1. Override precedence.** Effect's `Clock` as seen by `Runtime.run`: a caller's `Effect.withClock` alone gives the caller's clock. A platform `Layer.setClock` beats the caller's. An application-layer `Layer.setClock` beats the platform's.
  - **P2. Release order.** A resource acquired in the platform layer is acquired **before**, and released **after**, a resource acquired in the application layer: `platform acquire, app acquire, app release, platform release`.
  - **P3. Failure.** A platform layer that fails after a scoped acquisition makes the build fail, and releases that acquisition.
  - **P4. Isolation.** One platform `Layer` value used by two starts is acquired twice, once per start.

  In addition:
  - **F1–F3 (Revision 2 failure-path probe).** This uses v0.5's `Application.start` with the definition layer `provideMerge(appLayer, platformLayer)`, which is v0.6's composition.
  - **F1.** The application layer fails after the platform acquired: `platform acquire, app acquire, app release, platform release`, all before `start` returns `Failed { ServiceGraphFailed }`, and the application never reaches `Running`.
  - **F2.** The platform fails: `platform acquire, platform release`, and the application layer is never built.
  - **F3.** An application resource's release throws during `Application.shutdown`: `app release, platform release`, then `status` is `Stopped`.
- **T1 (type probe).** A layer with a requirement (`RIn ≠ never`) is **not** assignable to `Layer<EnvironmentShape, unknown, never>`. A layer with *extra* outputs **is** assignable.
  - **T2 (Effect 3.22 source).** The default services are `Clock`, `Console`, `Random`, `ConfigProvider` and `Tracer` (`internal/defaultServices.js`). `ConfigProvider.fromEnv` reads `process.env` when it exists. The `Scheduler` is a FiberRef (`currentScheduler`, default based on `setTimeout`), not a service. The audit listed `Scheduler` among the services and missed `ConfigProvider`; this outline corrects both.
- **Labels.** Contracts C13–C18, decisions D30–D42, invariants I28–I33 and risks R12–R17. Open questions O1–O6 are new, and L1–L8 carry over. Where v0.5's I11–I27, M1–M4, N1–N4 and the v0.3 lifecycle labels (B4, D1, N2, Q1, Q2, Q3) are cited, they carry over unchanged.
- **Normative words.** *must*, *must not*, *only* and *exactly* are normative. Code names that appear here are the proposed public names. Names in *italics* are working terms.

## A. Objective

> **What is actually NEXUS, and what is supplied by the execution environment?**

v0.6 answers this with **one explicit boundary**: an application's environment is supplied by a **platform**, at exactly one place, `Application.start`. NEXUS itself names no execution environment. v0.6 does not add environment functionality. It moves the environment's existing entry points behind that boundary and pins them there.

```text
Effect                                  mechanism: Layer, Scope, Context, default services
  ↓
NEXUS runtime + application semantics   lifecycle, State, Selector, Command, Event, Resource,
  ↓                                     Service, Capability (contract), Semantic
platform contract                       Application.Platform = a Layer providing Capability.Environment
  ↓
platform implementation                 any Layer of that type: test, Node, browser, worker, native…
```

## C. Architectural decision (summary)

1. **The platform is a `Layer`, passed to `start` in its options.** `Application.start(app, options?)`, with `Application.StartOptions = { readonly platform?: Application.Platform }` and `Application.Platform = Layer.Layer<Capability.EnvironmentShape, unknown, never>`. `options.platform` is the single authoritative supply point for the environment (D30). The options object fixes the start boundary's shape; it is not a configuration bag (D42).
2. **The application definition carries no environment.** `ApplicationDefinition.environment` is removed (D31).
3. **NEXUS names no execution environment.** `CapabilitySource` and `Available.source` are removed (D33).
4. **The mechanism is the platform's choice, explicitly.** Host-owned values go through `EnvironmentLive`; application-scoped platform resources go through a scoped layer. Both are a `Platform`, and application code can't tell which (D35).
5. **A capability is a NEXUS identity.** `Capability<Shape>` keeps `id` and loses `tag`. A phantom type member keeps `Shape` inference (D37).
6. **NEXUS names no Effect default service.** Their precedence is Effect's: caller, then platform, then application layer, with the later one winning. The platform is the intended place to set them, and a test pins the order (D38, D39).
7. **Host independence is enforced.** `src/` compiles with no ambient types, and `src/` may import only its declared dependencies (D40).
8. **The first platform is a reference test platform**, not a Node package (D41).

### Contracts

- **C13. Guardrails.** Host independence and the primitive export surface are enforced by tests and compiler settings before any boundary change (K, G1–G4).
- **C14. Build order.** The platform layer is built first, then the application layer. Both are provided to the application-owned runtime scope. The application layer may require `EnvironmentShape` (`ApplicationAmbient`, unchanged). The platform layer requires nothing.
- **C15. Ownership.** See F.
- **C16. The platform contract.** `Application.Platform = Layer.Layer<Capability.EnvironmentShape, unknown, never>` is the whole contract NEXUS exposes to platforms, together with the existing `Capability.Environment`, `EnvironmentShape` and `EnvironmentLive`.
- **C17. The capability model.** See G.
- **C18. Test categories.** See K.

## D. Blocker decisions

### I-1. The platform supply point

**Evidence.** The environment enters today in three uncoordinated ways: `definition.environment` (the author supplies it); the caller's fiber (default services, E2); and the application's own layer (P1). `start` already owns building the application runtime inside its own scope, and the runtime scope is where every application resource lives and is released (N1, D4). `Runtime.make` is also public, and builds standalone runtimes with no `Environment`.

**Alternatives.**

| | Shape | Assessment |
|---|---|---|
| a | Keep `definition.environment` (status quo) | Rejected. The author supplies the environment, so one definition can't run on two platforms without being rewritten (E-1). |
| b | **`start(app, { platform })`, an options object carrying a `Layer`** | Selected (Revision 2). It is explicit, and chosen per start, so two starts of one definition may use different platforms concurrently. The platform Layer is provided to the application-owned runtime scope, so its resources are governed by the application's lifetime (P2, P3, F1–F3). `start` is the foundational application-host boundary, and an object argument fixes its shape now, so a later, separately justified start concern needs no signature migration (D42). It is type-checked: requirements are rejected (T1). It reuses the existing `provideMerge` composition, so "Environment before the service graph" holds by construction. |
| c | `start(app, platform?)`, positional | Rejected (Revision 1 had selected it). It is equivalent today, but any second start concern would force a new signature on the host boundary. |
| d | Effect-native: `start` requires `EnvironmentShape` in its `R`, and the caller provides it | Rejected. The caller's `Effect.provide(layer)` builds the platform in the *caller's* scope, not the application's, so platform resource lifetime detaches from the application lifecycle (the v0.3 closure). Two starts in one provided context share one environment implicitly. It formalizes the implicit channel E2 criticized, and changes `start`'s `R` for every caller. |
| e | A NEXUS `Platform` object (`{ name, layer, … }`) through `Platform.define` | Rejected. It adds a namespace and metadata (`name`) with no consumer (same reasoning as D33). A `Layer` already composes, and a later release can wrap it if a consumer appears. |

**Decision D30.**

```ts
type Platform = Layer.Layer<Capability.EnvironmentShape, unknown, never>;

interface StartOptions {
  readonly platform?: Platform;
}

function start<R>(app: Application<R>, options?: StartOptions): Effect.Effect<RunningApplication<R>, ApplicationInitError, Scope.Scope>;
```

Both call forms are valid:

```ts
Application.start(app)                                                    // no platform: the empty environment
Application.start(app, { platform: Capability.EnvironmentLive(resolutions) })
```

- `start` provides `Layer.provideMerge(definition.runtime, platform)` to the application-owned runtime scope, exactly as v0.5 provided `provideMerge(definition.runtime, EnvironmentLive(...))`.
- **Absent `options`, or absent `options.platform`, means the empty environment**, `Capability.EnvironmentLive(new Map())`: every capability resolves `Unavailable`. This is exactly v0.5's behavior for an absent `environment`, and it is not an environment assumption. It supplies nothing.
- A platform build failure is an application start failure: `Failed { ServiceGraphFailed { cause } }`, with everything already acquired released (P3).

- `RunningApplication.environment` is the `EnvironmentShape` the platform built, read from the built context. Its shape and meaning are unchanged: the resolved environment.
- `Runtime.make` is unchanged. A standalone runtime has no platform and no `Environment`, exactly as today.

**Decision D34.** `ApplicationInitError` stays exactly `ServiceGraphFailed`. The platform is part of the application's service graph build, and the `cause` distinguishes platform failures. A new error tag would break the pinned "exactly one initialization failure" contract (`tests/lifecycle.test.ts:87`) without a consumer that needs the distinction (O4, R16).

**Decision D42. `StartOptions` is a boundary shape, not a configuration bag.** It contains exactly `platform`. It exists to fix the shape of the application-host boundary while holding only the one justified field. A future field must earn its place through a later, explicit architectural decision recorded in that release's outline. v0.6 adds no other field and reserves none.

**Decision D31.** `ApplicationDefinition.environment` is **removed**. It is not deprecated alongside: two supply points for one concept is the defect being fixed.

**Consequences.**
- There is one supply point for capability implementations.
- The same definition can start on different platforms.
- Platform resources are scoped to the application (C15).
- It is a breaking change for any definition that set `environment` (J).
- Because `options` is optional, every existing `start(app)` call except one (`tests/application.test.ts:70`) is unaffected.

**Deliberately unresolved.**
- O1: composing several platform contributions into one `Environment`.
- O5: whether a platform may output services other than `Environment`. Today they are type-invisible (T1).
- Request-scoped environments (v0.10).

### I-2. `CapabilitySource`

**Evidence.**
- No code in `src/` reads `source`: `resolve` and `require` ignore it.
- Its only readers are two test assertions.
- `capability.md`'s own rule forbids application code from branching on platform identity, yet `source` is the one field that invites exactly that.
- The v0.5 values name environments (`native`, `browser`) and one strategy (`fallback`), so it isn't even one taxonomy.
- In the new model, a "fallback" implementation supplied by a platform is simply an available implementation. The *application's* fallback is the `Unavailable` branch it handles itself (capability.md, Rules).

**Question.** *Does NEXUS need to know whether an implementation is browser, native, remote or fallback?* No. No NEXUS behavior depends on it, and no application behavior may (by NEXUS's own rule).

**Alternatives.** Keep it (rejected: environment vocabulary in NEXUS, E-2). Widen it to an opaque platform string (rejected: still invites branching, and has no consumer). Move it to *provenance metadata* (rejected for now: no consumer; provenance of platform-supplied implementations is a v0.8/v0.10 inspectability question, O3). Remove it (selected).

**Decision D32.** NEXUS assigns no meaning to how an implementation was produced.

**Decision D33.** `CapabilitySource` is removed from the public API, and `CapabilityResolution` becomes:

```ts
type CapabilityResolution<Shape> =
  | { readonly _tag: "Available"; readonly implementation: Shape }
  | { readonly _tag: "Unavailable"; readonly reason: string };
```

A platform may label its implementations however it likes, inside its own code. NEXUS neither reads nor exposes such labels.

**Consequences.** This is a breaking change to a public type (J), and 3 test cases are amended (K). `Unavailable.reason` stays: it is the platform's explanation to the application, already free text, and it carries no environment vocabulary.

**Deliberately unresolved.** O3: capability provenance, meaning which platform supplied what, for inspection. No new taxonomy is introduced.

### I-3. Value or `Layer`

**Evidence.**
- A resolution holds a pre-built value, and `EnvironmentLive` is `Layer.succeed`, so a platform capability that needs a resource (socket, handle, device session) has no lifetime NEXUS knows about.
- P2 and P3 show a platform `Layer` gives exactly the ownership NEXUS already guarantees for application resources: acquired in the runtime scope, released during termination, released on a failed start.
- P4 shows per-start isolation.

**The requirement, stated as ownership.** A platform capability implementation is owned by one of two parties:
- **the host**: it outlives the application, may be shared by several applications, and the host releases it; or
- **the application**: it is acquired for one application and released when that application terminates.

Both occur. A process-wide clock or a pooled client is host-owned. A per-application connection is application-scoped. The boundary must make the choice explicit, and must hide it from application code.

**Alternatives.**
- **A: values only** (v0.5). Host-owned lifetime is fine. Application-scoped platform resources are impossible, or leak.
- **B: per-capability layers, with each capability as its own Effect service.** This gives resources, but it changes the application-facing contract: `resolve`'s `R` would become the capability's service, `Unavailable` loses its reason, and every existing call site changes. It would also make the Effect mechanism the capability's identity (see D37).
- **C: one platform `Layer` producing the resolved map.** Selected.

**Decision D35 (option C).**
- The platform is one `Layer` producing `EnvironmentShape`.
- **Host-owned** implementations are supplied as values: `Capability.EnvironmentLive(map)`, which is unchanged.
- **Application-scoped** implementations are supplied by a scoped layer that builds the map (`Layer.scoped(Capability.Environment, …)`). The layer is provided to the application-owned runtime scope, so the application's lifetime governs acquisition and release (C15).
- Mixing is the platform's business (for example, a scoped layer that includes host-owned values in its map).

In every case the application sees the same thing: a `CapabilityResolution` through `resolve`/`require`.

**Decision D36.** Resolutions are fixed when the platform layer is built, during `start` and before the application's service graph (C14). This is unchanged from v0.5: "resolutions are fixed at start", and "Environment before the service graph".

**Evaluation against the listed concerns.**

| Concern | Result |
|---|---|
| Resource acquisition, lifetime, cleanup | The application's lifetime governs scoped platform acquisitions: acquired before, and released after, every application resource, on every route (P2, F1–F3, C15). |
| Failure | A failed platform build is a failed start, and what it acquired is released (P3, D34). |
| Dependency composition | The platform layer requires nothing (T1). The application layer may require `EnvironmentShape` (`ApplicationAmbient`, unchanged). |
| Lazy initialization | Not a NEXUS concept. An implementation may defer work internally, but anything it acquires must be scoped by the platform layer. Otherwise it is host-owned (R14). |
| Per-application scope | Yes: the default for scoped platforms (P4). |
| Per-request scope | Not in v0.6. A capability operation that needs a per-request resource returns an `Effect` requiring `Scope`, and the caller's scope owns it, which is already expressible. A request scope as a NEXUS concept is v0.10. |
| Sharing | Host-owned values (`EnvironmentLive`) may be shared across applications. Scoped platform layers are never shared (P4). |
| Test replacement | A test supplies its own `Platform`: the reference platform (D41) or any layer. |
| Capability resolution | Unchanged: `resolve` never fails, and `require` fails only with `CapabilityUnavailableError`. |
| Semantic inspection | After start, `RunningApplication.environment` lists every id and whether it is available. Before start, a `Layer` is opaque. A declarative platform profile for `Semantic` is v0.7 (O6, L6). |

**Contract versus mechanism.** The capability *contract* is NEXUS's: `Capability<Shape>` (identity plus a typed interface), `resolve`, `require`, and unavailable as a value. The platform's `Layer`, and whether it holds values or acquires resources, is the *mechanism*, and `resolve` and `require` don't reveal it (I32).

**Deliberately unresolved.**
- O1: platform composition.
- O6: pre-start inspection of what a platform provides.
- Request scope (v0.10).

### I-4. Effect default services

**Evidence.**
- T2: the default services are `Clock`, `Console`, `Random`, `ConfigProvider` and `Tracer`, plus the `Scheduler` FiberRef.
- P1: precedence is caller, then platform, then application layer, with the later one winning.
- The NEXUS core uses none of them directly: there is no `sleep`, `timeout`, `Clock`, `Random`, `Console`, `Config` or span in `src/` (audit E, "not found"). Every fiber runs on the `Scheduler`, which is Effect infrastructure.

| Service | NEXUS must name it? | Platform should control it? | Application declares it? | Affects NEXUS semantics? | Lifetime |
|---|---|---|---|---|---|
| `Clock` | No | Yes: time is environmental | No: not in any `R` | No: the core never reads time | the platform's layer, or the caller's |
| `Random` | No | May, for determinism | No | No | same |
| `Console` | No | Yes: where output goes is environmental | No | No | same |
| `ConfigProvider` | No | **Yes**: the default reads `process.env` (T2) | No | No: the core reads no config | same |
| `Tracer` | No | May | No | No | same. Inheriting the caller's is *desirable*: it carries the parent span. |
| `Scheduler` (FiberRef) | No | Rarely: host integration (for example, a UI host yielding differently) | No | No: lifecycle ordering is by admission and Deferreds, not scheduling | Effect's |

**Alternatives.**
1. Promote them into a NEXUS `PlatformServices` contract: rejected, because no NEXUS semantics depend on them.
2. Isolate the application from the caller's fiber, building the runtime from a fresh default runtime: rejected, because it breaks tracer-span and log-level propagation and changes E2 behavior for no semantic gain.
3. **Leave them as Effect infrastructure, name none of them, and designate the platform layer as the intended place to set them. Effect's precedence stands, and a test pins it.** Selected.

**Decision D38.** NEXUS names no Effect default service, and none enters any NEXUS type. A platform sets them with Effect's own layers (`Layer.setClock`, `Layer.setConfigProvider`, …), merged into its `Platform`.

**Decision D39.** The effective precedence is **caller fiber < platform < application layer**, which is Effect's layer and FiberRef semantics (P1). NEXUS neither adds nor forbids a route:
- the caller's services are an Effect inheritance, kept for tracing;
- the application layer overriding a service is the application's own decision (for example, a seeded `Random`), not an environment supply.

A characterization test pins all three routes, so any future change is deliberate.

**Consequences.** No API is added. The documentation states the precedence (runtime.md, application.md). The E2 behavior remains, and is now documented and pinned.

**Deliberately unresolved.** Whether a later release (v0.10, request or replacement scope) needs the application layer to be *unable* to override platform services. There is no evidence for that yet.

### D40. Host independence is enforced, not assumed

**Evidence.** Audit E1: `src/` compiles with `types: []`, but the build config lets Node globals typecheck in `src/`. The existing architecture tests check MESH and PORT imports only.

**Alternatives.**
- A grep test for host identifiers: rejected, because it is brittle and misses aliases.
- A separate core `tsconfig`: rejected, because it duplicates the build config.
- **`"types": []` on the build config itself (`src/` only), with the test config opting back into `["node"]`, plus an import-boundary test:** selected. The build is exactly the core, so the core can't compile with a host global.

**Decision D40.** G1 and G2 (K). `lib` stays `ES2022`, with no DOM.

## F. Lifecycle and resource model

**Contract C15, the lifetime invariant.** The platform Layer is provided to the application-owned runtime scope; acquisition and release of platform resources are therefore governed by the application's lifetime. Concretely, for every application that reaches `Running`:

```text
platform acquisition
        ↓
application resource acquisition
        ↓
application running
        ↓
application shutdown            (route 1: Application.shutdown; route 2: closing the start scope)
        ↓
application resource release
        ↓
platform resource release
```

The same order holds on failure paths:
- **Platform acquisition fails.** Anything the platform acquired before failing is released. The application layer is never built. `start` fails with `ServiceGraphFailed`, returns no handle, and the application never reaches `Running` (F2).
- **Application layer fails after the platform acquired.** Application acquisitions are released, then platform acquisitions, before `start` fails. There is no handle and no `Running` (F1).
- **A release fails during shutdown.** The remaining releases still run in order, platform last. Status reaches `Stopped`, and only the performer re-raises (F3; v0.3's B4).

A start that fails leaves nothing partially started: no handle, no admitted work, and nothing left acquired.

**Ownership table.**

| What | Owner | Acquired | Released |
|---|---|---|---|
| Host-owned platform implementations (`EnvironmentLive` values) | host | before `start`, by the host | by the host, after the application ends. NEXUS never releases them. |
| Application-scoped platform resources (scoped platform layer) | the application runtime's scope | during `start`, **before** the application layer (C14) | during termination's scope close, **after** every application resource (P2) |
| Application resources (application layer, commands, `Resource.acquire`, application-owned State) | the application runtime's scope | during start or while `Running` | during termination's scope close, in reverse acquisition order |
| The runtime scope | NEXUS (hidden, N3) | `start` | termination (route 1 or 2) |
| The caller's start scope | the caller | — | closing it is route 2 |
| The resolved `Environment` map | NEXUS | when the platform layer builds (D36) | with the runtime scope |

**Termination order (v0.3's, made explicit for platforms).** Claim, then drain admitted work, then `Stopping`, then close the bus, then close the scope: application resources first, then platform resources. Then `Stopped`. The v0.3 order is unchanged. v0.6 pins *where* platform resources fall in it (I31).

**Failure.** If the platform or application layer fails to build, the result is `Failed { ServiceGraphFailed }`, and every acquisition made so far is released, platform included (P3; the existing "a failed start … releases what it built" contract).

**Concurrency.** Two concurrent starts, with the same or different platforms, get independent environments and independent scoped platform resources (P4). Only host-owned values can be shared, and only because the host chose to share them.

## G. Capability model (v0.6 meanings)

- **Capability.** A NEXUS identity (`id`) plus a typed contract (`Shape`), which application code resolves and uses. It stays a NEXUS concept: platform-independent, with no environment vocabulary.
- **Platform.** Whatever supplies an application's environment at `start`. In v0.6 that means an `Application.Platform` layer. NEXUS knows no platform by name.
- **Implementation.** A value of `Shape` that a platform makes available for an `id`. Who owns its lifetime depends on how the platform supplies it (C15).
- **Resolution.** The platform's answer for one `id`, fixed at start: `Available { implementation }` or `Unavailable { reason }`. An id the platform doesn't mention resolves `Unavailable` (unchanged).
- **Environment.** The resolved map for one running application (`EnvironmentShape`).
- **Source or provenance.** Not retained (D33). Deferred as O3.

These are the v0.6 meanings only. v0.6 does not relate `Capability` ids to the semantic model's profile identifiers (L6, I15 unchanged), does not model capabilities an application *offers*, and defines no capability vocabulary (D8 unchanged).

**Decision D37, `Capability.tag`.**
- **Why it exists.** `tag` was added in v0.1 by analogy with `Service` (capability.md: "both wrap a `Context.Tag`"), anticipating capabilities provided as their own Effect services. In five releases nothing has read it.
- **Why it has no v0.6 role.** Provision goes through `Environment` by `id` (D35), so the tag is a second identity for the same concept.
- **Why it is a hazard.** `Layer.succeed(Haptics.tag, impl)` type-checks and provides a service, yet `resolve(Haptics)` returns `Unavailable`. That is a silent second supply path, contradicting D30. Its `GenericTag(id)` key also shares a namespace with `Service.define(name)`.

**Decision.** Remove `tag` from `Capability<Shape>`. `define` no longer creates a `Context.Tag`. To keep `resolve`/`require` inferring `Shape` (a structurally empty `{ id }` would infer `unknown`), `Capability<Shape>` carries a type-only phantom member, `readonly [CapabilityTypeId]?: (_: Shape) => Shape`. This is declared, never assigned, and follows `NexusRuntime`'s pattern. The phantom makes `Shape` invariant.

**Deliberately unresolved.** O2: whether v0.7 gives capabilities a typed per-capability identity in `R` (for example, to express requirements). If so, it is designed there, not kept alive here.

## H. Effect relationship

| NEXUS semantic API (the contract) | Effect mechanism (the means) |
|---|---|
| `Capability` (`id`, `Shape`), `resolve`, `require`, `CapabilityResolution`, `CapabilityUnavailableError` | `Context` lookup of `Environment`; the `Layer` that built it |
| "The environment is supplied by a platform at `start`" | `Application.Platform` *is* `Layer<EnvironmentShape, unknown, never>`. NEXUS names the contract type, and doesn't wrap Layer |
| The lifecycle and termination order, including where platform resources fall (I31) | `Scope`, `Layer.buildWithScope`, finalizer order |
| "NEXUS names no default service" (D38) | `Clock`, `Console`, `Random`, `ConfigProvider`, `Tracer`, `Scheduler`, and their precedence (D39) |
| `Service` (deliberately an Effect `Context.Tag`, ARCHITECTURE §6) | the same thing, by design |

NEXUS does not re-export, alias or wrap any Effect default service, `Layer` constructor or `Scope`. The one new public name, `Platform`, is a type alias naming *which* Layer NEXUS accepts. `EventBusShape`'s exposed mechanics (audit G.1) are out of scope for v0.6.

## I. The first platform experiment

**What the evidence says.** NEXUS core requires **no** capability and **no** host API (audit E1, grep), so a "Node platform" would supply nothing Node-specific: an empty environment plus Effect's defaults, which Node already gives. A Node package would therefore prove nothing the core suite doesn't, and would start the package family ROADMAP §7.4 warns against. The audit's "headless Node host platform" (answer 8) is refined here: the experiment is **host-agnostic**, and it happens to run under Node because the test runner does.

**Decision D41. The first platform is a reference test platform**, in `tests/platform/reference.ts`. It is not in `src/`, not a package and not exported.

- **Minimum responsibility:**
  - supply a caller-given resolution map as host-owned values (`EnvironmentLive`);
  - optionally set a caller-given `Clock` (the one default service the tests exercise), to prove D38/D39;
  - nothing else.

  Scoped platform capabilities are exercised by tests that build their own scoped layer (C15), not by features added to the reference platform.
- **Contract NEXUS exposes to it:** exactly `Application.Platform`, `Capability.EnvironmentShape`, `Capability.Environment` and `Capability.EnvironmentLive`.
- **Constraints:**
  - it imports only `effect` and `src/` (G2 extends to it);
  - it uses no host API;
  - it provides no filesystem, HTTP, process, browser, SSR, rendering, PORT or dev-server functionality.
- **What it proves:** `platform → start → NEXUS → existing behavior`. The vertical slice and the MESH slice run on it unchanged.
- **When a real platform package is justified:** when a capability an application needs is host-specific (the earliest candidate is the I1 server path). Not in v0.6.

## J. Compatibility and migration

v0.6.0 is a **deliberate breaking release** within v0.x (like v0.3). The breaks are exactly three, all in the capability and environment boundary.

1. **`ApplicationDefinition.environment` is removed (D31).**
   ```ts
   // v0.5
   Application.start(Application.define({ name, runtime, environment: resolutions }))
   // v0.6
   Application.start(Application.define({ name, runtime }), { platform: Capability.EnvironmentLive(resolutions) })
   ```
   Runtime behavior is identical: the same map, built at the same point, before the service graph.
2. **`CapabilitySource` is removed, and `Available.source` is dropped (D33).** Delete `source` from resolutions. Code that branched on `source` should branch on `_tag`, or the platform should supply a different implementation.
3. **`Capability.tag` is removed (D37).** There was no reader in NEXUS. Code that provided `capability.tag` directly never affected `resolve`; supply the implementation through the platform instead.

**Unchanged:**
- every lifecycle, admission, termination, State, Selector, Command, Event, Service, Resource and Runtime contract;
- `Semantic`, the diagnostics and provenance;
- the MESH adapter (M1–M4);
- the entry namespaces.

No compatibility wrappers are provided (same policy as v0.3). The release notes carry this migration table.

## M. Exit criteria (Definition of Done)

v0.6 is release-ready only when all of these hold:

1. **Single supply point.** `options.platform` of `Application.start(app, options?)` is the only way an application's environment is supplied; `StartOptions` has exactly the one field `platform` (type test); `ApplicationDefinition` has no environment field (type test); `Capability.EnvironmentLive` passed as the platform reproduces every v0.5 resolution behavior (tests 1, 2).
2. **No environment vocabulary.** No public NEXUS type names an execution environment: `CapabilitySource` and `source` are gone (type test, and a grep of `src/` for `"browser"`, `"native"` and `"remote"` finds only comments or none).
3. **Capability identity.** `Capability` is `{ id }` plus a phantom; `Shape` inference is preserved (type test); `define` creates no `Context.Tag`.
4. **Lifetime (C15, I31).** The full order holds on both shutdown routes and on the three failure paths; a failed start leaves nothing acquired and returns no handle; starts are isolated (tests 3, 4, 4a, 4b, 5, 6).
5. **Default services.** Precedence is caller < platform < application, pinned by G4 and test 7. No NEXUS type names a default service.
6. **Host independence enforced.** G1 and G2 pass, and fail when a deliberate break is applied (the deliberate-breaks table below).
7. **Exports.** G3 passes unchanged across v0.6; the entry still has exactly 11 namespaces; `Application.Platform` and `Application.StartOptions` are the only new public types.
8. **Reference platform.** The vertical slice and the MESH slice pass on it; it imports only `effect` and `src/`.
9. **Nothing else changed.** Exactly the 5 amendments in K, in 3 files (touching 6 test cases); the other 281 v0.5 test cases pass unmodified; within the semantic suite, only the fifth amendment's fixture lines change; `tests/reference/semantic-v0.4.ts` and `src/semantic/` are untouched.
10. **Docs parity.** `application.md`, `capability.md` and `runtime.md` match the exported declarations; ARCHITECTURE §4, §10, §14, §24/§25.2 and §26 (new decision 12) are updated; the README, ROADMAP status and audit cross-references are updated; `docs/releases/v0.6.md` carries the migration table.

## N. Risks

- **R12. The options object invites accretion** (Revision 2). An object is easy to extend, so fields could be added without architectural justification. Mitigated by D42: each new field needs its own outline decision, and a type test pins the exact shape, so an unreviewed field fails CI.
- **R13. Extra platform outputs are type-invisible but present (T1).** A platform can merge in other services; the application can't require them by type, but untyped lookup could find them. Accepted for v0.6, and documented. Whether to forbid them is O5.
- **R14. Lazy acquisition inside an implementation escapes scoping.** An implementation that acquires on first use, outside its platform layer's scope, is effectively host-owned and unreleased by NEXUS. It is documented as platform guidance; NEXUS can't detect it.
- **R15. The application layer can override platform-set services (D39).** This is Effect's semantics, and accepted. If replacement or request scope needs it forbidden, that is a v0.10 decision.
- **R16. `ServiceGraphFailed` now also covers platform failures (D34).** The cause distinguishes them; no new error tag is added (the "exactly one init error" contract holds). Whether to split them is O4.
- **R17. Breaking three public items.** Mitigated: exactly three, all in the boundary being fixed, with migration steps, and no runtime semantics change.

## P. Invariants (new)

- **I28.** The NEXUS core uses no host API, and this is enforced at compile time and by import checks (G1, G2).
- **I29.** An application's environment reaches it only through the platform supplied to `Application.start`. The application definition carries none.
- **I30.** No NEXUS public type names or distinguishes an execution environment.
- **I31.** The platform Layer is provided to the application-owned runtime scope; acquisition and release of platform resources are therefore governed by the application's lifetime. Platform resources are acquired before, and released after, every application resource, on both shutdown routes and on every start-failure path. A failed start leaves nothing acquired.
- **I32.** A capability is a NEXUS identity with a typed contract. How its implementation is supplied (a host-owned value or a scoped acquisition) is invisible to application code.
- **I33.** NEXUS names no Effect default service. Their precedence is Effect's: caller < platform < application layer.
