## 1. Problem statement

> *How does an application declare what it requires from its execution environment, and how does a platform declare what it provides?*

v0.6 made the platform the only supplier of an application's environment, and NEXUS now names no environment. What NEXUS can't yet do is **say, before anything runs, whether a given platform satisfies what an application needs.**

The runtime half exists: `Capability.resolve`/`require` against a platform-built `Environment`. The static machinery exists too: `Semantic.analyze` computes required × provided → supported / opaque / incompatible (CMA F1). What is missing is **meaning** (CMA §A):

- what a semantic *target profile* denotes (L6);
- whether its identifiers can be application capability ids (I15);
- what counts as a *requirement*;
- what a platform *states*, and when.

The goal is a model in which each of the following stays a distinct statement, with an explicit and narrow relationship between them:

- the application states what it needs;
- the platform states what it provides;
- the platform's `Layer` actually provides it;
- analysis relates the two statements.

v0.7 must not collapse *application capability*, *platform capability*, *semantic capability* and *PORT target capability* into one abstraction.

## 3. L6 decision: what a semantic target profile denotes

### Evidence

- CMA F2: Semantic interprets no identifier. It compares strings, and profiles are caller input.
- CMA F1: its relation is already the roadmap's relation.
- RPA §F: every worked example (`"browser"`, `"filesystem"`) reads as an execution environment. PORT has its own rendering-target capabilities, not present in NEXUS.

### Options

**Option 1. Target profiles become platform capability profiles.** "Target" in Semantic means the execution environment, permanently.

| Criterion | Assessment |
|---|---|
| Released contracts | Types and codes stay the same. Only the meaning is narrowed. |
| Diagnostics | Unchanged. |
| MESH | Unaffected. |
| PORT ownership | Rendering compatibility could never reuse the relation without re-widening this decision, or duplicating the machinery in PORT or MESH tooling. |
| Conflation | Low today. It fixes the word "target" to the one reading that disagrees with PORT's use of the same word (RPA §F, ambiguity 1). |
| `Capability` participation | Natural. |
| Identifier stability | Stable. |
| Migration | None. |
| Execution and rendering targets later | **No**, unless reopened. |

**Option 2. Semantic target profiles remain a concept separate from platform capabilities.** v0.7 adds a parallel `PlatformProfile` (or similar) and new codes.

| Criterion | Assessment |
|---|---|
| Released contracts | Additive. |
| Diagnostics | A second set of codes for the same relation. The existing three denote nothing assigned. |
| MESH | Unaffected. |
| PORT ownership | Leaves `TargetProfile` free for PORT, but still undefined. |
| Conflation | None. Instead, **duplication**: two implementations of one relation that can drift, which breaks I25's "passes read Built" economy. |
| `Capability` participation | Via the new type. |
| Identifier stability | Stable, but the old ones become orphaned. |
| Migration | Consumers must choose between two models. |
| Execution and rendering targets later | Yes, at the cost of permanent duplication, with L6 still unanswered for the old types. |

**Option 3. Semantic profiles are neutral facts, mapped from platform provisions or PORT target capabilities.**
- Semantic defines a **relation**, not a vocabulary or a domain: an analysis context evaluates declared requirements against the provisions of *one* provider.
- Which kind of provider it is (an execution platform, a rendering target) is fixed by the **binding** that produced the context, outside Semantic.
- v0.7 defines exactly one binding, the platform binding (D44).

| Criterion | Assessment |
|---|---|
| Released contracts | Types, codes, messages and behavior are unchanged. "Target" is read as "the provider this analysis is evaluated against", consistent with I5 ("incompatibility is target-specific"). |
| Diagnostics | All three codes keep their exact conditions. Under the platform binding they read as "the platform's statement doesn't provide / doesn't decide". |
| MESH | Unaffected. |
| PORT ownership | PORT (or tooling) may later define its own binding with PORT-owned identifiers, in its own analysis contexts (C22). Nothing is decided for PORT now (L1 stays open). |
| Conflation | Prevented by C22: one context, one binding. Identifiers from two bindings never meet in one analysis. The risk is that a producer mixes them anyway (R19). |
| `Capability` participation | Yes, only through the platform binding, and only by `id` (D44). |
| Identifier stability | All stable. |
| Migration | None. |
| Execution and rendering targets later | **Yes**, by construction. |

**Option 4. Semantic gains a domain tag.** This is Option 3 plus a `domain` field on `TargetProfile` and on `Requirement`, checked for equality. It is considered and not selected:
- Semantic would still assign no meaning to the tag, so it adds a field whose only effect is a new rejection.
- Only one domain exists, so nothing could exercise it.
- It would change the released plain-data types, and the 35-export pin, for a hazard with no instance yet.

It is the natural escalation if R19 materializes (O8).

### Decision

**D43 (L6 resolved): Option 3.**
- A semantic `TargetProfile` denotes *the provisions of the one provider an analysis context is evaluated against*.
- A semantic capability identifier has no intrinsic domain. Its domain is the binding's.
- Semantic defines the relation (C4, unchanged) and assigns no vocabulary (D8, unchanged).
- The released names `TargetProfile`, `TargetRequirements`, `target-requirements`, `target-compatibility`, `nexus-incompatible-target-capability` and `nexus-undetermined-target-capability` stay exactly as released, with the reading above.

**Why not Option 1.** It gives the same v0.7 behavior as Option 3, but closes the door on rendering-target analysis for no present gain. It would also make the word "target" mean the opposite of PORT's usage *by decision* instead of by accident.

**Why not Option 2.** It duplicates a released relation, and leaves L6 unanswered for the types it orphans.

## 4. I15 decision

### Evidence

- CMA F3: v0.6 removed I15's founding premise (A5a). Resolutions are now the platform's, not the author's.
- CMA F4: I15 bundles
  - **I15a, independence**: analysis neither reads nor affects resolution, and configuration never decides a target capability. It is pinned by DoD 12.
  - **I15b, separate identifier spaces**: documentation only. DoD 12 itself uses one string on both sides.
- CMA F5: a static claim and a runtime resolution are different facts, even when they are about the same capability.

### Options

- **Keep both halves.** Rejected. The platform binding then needs a mapping table from application capability ids to "platform target ids". Every entry would be the identity, because roadmap §17 and the v0.6 runtime already have the platform answer *for the application capability's id* (CMA §B). A mapping that is always the identity is a second vocabulary with nothing to say.
- **An explicit mapping as a NEXUS artifact** (a function or table from `Capability` to identifier). Rejected. The mapping is the identity. A NEXUS-side producer would also have to import `Semantic` from a NEXUS module, which reverses D13 (CMA F8) for a one-field projection (`{ capability: Cap.id }`).
- **Unify: one capability vocabulary for everything.** Rejected. It would make PORT target identifiers and application capability ids one space: the conflation §1 forbids.
- **Keep I15a exactly, and replace I15b with a binding rule.** Selected.

### Decision

**D45 (I15 revised).** I15 is replaced by:

> **I15 (v0.7): Analysis is independent of resolution, and identifiers belong to a binding.** Semantic capability identifiers are opaque. Each analysis context's identifiers belong to the single domain of the binding that produced it (C22).
> - In the **platform binding** (D44), a semantic capability identifier is an application `Capability`'s `id`, verbatim.
> - Semantic analysis still neither reads nor affects how any application capability resolves.
> - A running application's resolutions never decide a profile: a profile is never derived from an `Environment`, a `Layer` or execution (I16, unchanged).

*Original I15 text, kept for the record:* "Target capabilities and application capabilities are separate concepts, with separate identifier spaces. Semantic analysis neither reads nor affects how application capabilities resolve, and application capability configuration never decides a target capability."

**Why this doesn't collapse the four concepts.** The only thing that becomes shared is one string: the identifier of a **capability contract**, which the application's requirement and the platform's provision are both *about*. What stays distinct:

| Concept | What it is | Where it lives | Changed by v0.7? |
|---|---|---|---|
| Application capability | a contract: `id` plus `Shape` | `Capability.define`, by its definer | no |
| Application requirement | a *claim*: this unit can't work unless that contract resolves `Available` | semantic declaration (D46) | new meaning, no new type |
| Platform provision (static) | a *claim*: every start of this platform will resolve these ids `Available`, and those `Unavailable` | a `TargetProfile` authored by the platform (D47) | new meaning, no new type |
| Platform provision (runtime) | the *fact* for one start | the platform `Layer` → `Environment` | no |
| PORT target capability | a rendering-realization guarantee | PORT, in its own binding and its own contexts | not modeled (L1) |

The DoD 12 tests stay **unmodified and passing**. They now demonstrate I15a precisely: an `Available` resolution does not make a profile provide an id, and an `Unavailable` one does not make it not provide one.

## 5. Application capability requirement

**D46.** An *application capability requirement* is a declared claim that a unit of the application **cannot fulfil its declared behavior unless** a named application capability resolves `Available`.

- **Requirement means necessity, not use.** An operation that calls `Capability.resolve` and handles `Unavailable` with a fallback does **not** require that capability (CMA F3b). Declaring it as required would produce a false *incompatible*. An operation that uses `Capability.require` with no fallback does require it.
- **It is expressed as a semantic declaration.** A `Semantic.Declaration` whose `requirements.capabilities[i].capability` is `SomeCapability.id`. No new type.
- **Granularity is the producer's** (D1, unchanged): per command, per service, or one declaration for the whole application. "Application requires Network and Storage" is one declaration with `complete` requirements `[Network.id, Storage.id]`. Finer declarations give finer diagnostics.
- **Completeness keeps its v0.4 meaning.** `complete` means exactly these. `partial` means at least these, and gives *opaque*. Absent means unknown, and gives *opaque*.
- **It is not attached to `ApplicationDefinition`.** A definition-level field would be either:
  - dead: unread by the runtime, the hazard D37 removed; or
  - enforced at `start`: gating, a second error, and a runtime copy of a fact the declaration already states.

  Attaching facts to primitives is v0.8's question (L2, D17).
- **It has no runtime effect.** `resolve` and `require` behave exactly as in v0.6 (D49).

## 6. Platform capability provision

**D47.** A *platform provision statement* is a plain-data `Semantic.TargetProfile`, authored by the platform alongside its `Platform` layer. Its identifiers are application capability ids.

| Profile entry | Claim about **every** start of that platform |
|---|---|
| id in `provided` | the platform's `Environment` resolves it `Available` |
| id in `notProvided` | the platform's `Environment` resolves it `Unavailable` (or doesn't mention it, which is the same, `capability.md`) |
| id in neither | undecided: the platform does not claim either way. This is correct for anything conditional: permissions, optional devices, remote services |

- **The platform authors it, and NEXUS never derives it.** It is not derived from the `Layer`: that would mean building it, which is execution (I16, CMA F5). It is not derived from a running `Environment` either, because a profile from execution is not a pre-execution fact.
- **It is a claim.** NEXUS doesn't verify it, just as it doesn't verify a declaration. Conformance is the platform's obligation (C21).
- **`name` is the platform's own label.** NEXUS passes it through to diagnostics text and never interprets it. This is consistent with D33 ("a platform may label its own implementations"), and it names no environment in any NEXUS type (I30 holds).
- **It is not passed to `Application.start`** (D30, D42 and I29 hold). It is an input to analysis only. A host that wants both calls `Semantic.analyze(...)` and `Application.start(...)`, and decides what to do with the result (L3).

## 7. NEXUS `Capability` and semantic capability facts

**D44 (the platform binding).** The one binding v0.7 defines:
- the **requirement side** is a declaration naming `Capability.id`s (D46);
- the **provision side** is a platform provision statement (D47);
- a semantic identifier is `Capability.id` **verbatim**, with no mapping table, prefix or transformation.

**C19. The binding is one-directional, and it lives outside NEXUS modules.**
- Data flows `Capability.id → plain string → Semantic input`, written by the producer (application author, platform author, or tooling).
- No NEXUS module imports `Semantic` (D13 and the leaf tests are unchanged).
- `Semantic` imports nothing, so it never sees a `Capability`, `EnvironmentShape` or `Layer` (I18 holds).
- The only coupling is the string, and the rule that it is the `id`.

This makes the wrong boundary hard. Nothing in NEXUS can turn a resolution into a profile, or a profile into a resolution, because no code path connects them.

## 8. Relationship to Effect `Layer`

The `Layer` is **how** a platform provides. The provision statement is **what** it claims to provide:

```text
capability contract   Capability.define<Shape>(id)             (definer: app or shared contract module)
        │ requirement (claim)            │ provision (claim)
        ▼                                ▼
Semantic.Declaration              Semantic.TargetProfile         ── Semantic.analyze ──▶ verdicts
                                         ┊ must conform to (C21; tested, never derived)
                                         ▼
                                  Application.Platform = Layer<EnvironmentShape, unknown, never>
                                         │ built at start (D36)
                                         ▼
                                  Environment ──▶ resolve / require       (runtime fact)
```

- NEXUS wraps no `Layer` and adds no layer type. `Platform` is unchanged.
- **D51 (O2 closed).** There is no typed per-capability identity in Effect's `R`, such as `Effect<A, E, Requires<Storage>>`.
  - Effect's type parameters are erased, so they can't produce plain-data facts without source analysis (I14; DoD 11: "Effect type parameters are not semantic metadata").
  - It would reintroduce a second, Effect-level identity for a capability, which D37 removed.
- **D52 (O5 decided).** The platform contract stays exactly `Layer<EnvironmentShape, unknown, never>`.
  - Environment-dependent *functionality* reaches an application only as a `Capability`.
  - Effect's default services stay Effect's (D38, D39).
  - Any other service a platform layer happens to output remains type-invisible and outside the NEXUS contract (R13, unchanged). NEXUS adds no check, since it couldn't detect such services without inspecting the built context.

## 9. Relationship to `Semantic`

**No change to `src/semantic`**: no type, field, code, message, rejection, export or behavior changes.
- The 35-export pin and the 2-runtime-value pin hold.
- The v0.4 differential corpus holds, messages included (I27).
- `semantic.md` changes in prose only: the meaning of "target" (D43), the platform binding (D44), and I15 as revised (D45).
- Semantic stays pure, synchronous and plain-data. It doesn't execute effects, discover the platform, inspect closures, or gate anything (I11, I16, D10, I19).

## 10. Relationship to MESH

**None.**
- The adapter imports no capability, and M1–M4 and the error table are unchanged.
- MESH owns template semantics and command intents. An application's capability requirements are NEXUS declarations, never MPRX.
- Engine initialization outside Node stays L7, a host concern. It is not a capability.

## 11. Relationship to future PORT target capabilities

- **PORT target capabilities are not platform provisions.** They are a separate binding, which v0.7 doesn't define.
- A later release, when a real PORT target exists (L1, I1 at the earliest), may use Semantic's relation for render-side requirements against a PORT-authored profile. It would do so in **its own analysis contexts**, with PORT-owned identifiers (C22).
- Whether a render-side requirement can ever *imply* a platform requirement (for example, a DOM target needing a platform that hosts it) is an L1 question. v0.7 relates nothing across bindings.
- PORT remains outside NEXUS's dependency graph in both directions (ARCHITECTURE §16).

## 12. What is available statically

Everything the analysis uses is plain data, known before start, and stated by its author:
- the requirement declarations, including their completeness and provenance;
- the platform provision statement, with its `name` and provenance;
- the verdict per unit (supported / opaque / incompatible) and the diagnostics.

## 13. What remains opaque

- Any unit with undeclared or `partial` requirements (C4 steps 2–3).
- Any required id the platform statement leaves undecided (step 4). This covers everything conditional on the host at runtime.
- **The runtime correspondence itself.** Whether a platform's `Layer` actually honours its statement is not a static fact. It is established by platform conformance tests (C21), and at runtime by the `Environment`.
- Optional use (resolve with fallback) is not modeled. It is neither a requirement nor a finding.

## 14. What constitutes incompatibility

**C20.** Under the platform binding, a unit is *incompatible* with a platform exactly when:
- the unit **declares** it requires capability `id`; and
- the platform's provision statement **explicitly** lists `id` in `notProvided`.

This is v0.4's C4 step 1, unchanged (I12, I16). Missing information is never incompatibility.

A runtime `Unavailable` is **not** static incompatibility: it is a runtime value that the application handles (`capability.md`). A static *incompatible* verdict does not stop anything from starting or running (D10, D49).

## 15. Capability identity

**D53. Identity is nominal, by the `id` string.**
- It is not structural: `Shape` is erased and never compared.
- The same `id` is the identity at runtime (the `Environment` key) and statically (the semantic identifier), so the binding adds no second identity (CMA F7).
- **Collisions are the definer's responsibility.** Two contracts sharing an `id` already share an implementation at runtime (X2), and they would share verdicts statically.
- v0.7 documents a convention: an `id` qualified by the defining package or application, for example `"acme.asset-store"`. It doesn't enforce the convention.
- There is no registry (ROADMAP §20).
- NEXUS defines no ids, and ships no profiles (D8, unchanged).

**Vocabulary ownership follows from this.** Capability ids are owned by whoever defines the **contract**. An application-facing contract such as `AssetStore` is the preferred shape (ROADMAP §5). A platform owns only its *statement about* the contracts it implements. A platform that implements `AssetStore` with a filesystem says `provided: ["acme.asset-store"]`, never `"filesystem"`, unless an application actually requires a filesystem contract.

## 16. Lifetime and scoping implications

- A provision statement has **no lifetime**. It is a claim about every start of a platform.
- Resolutions are fixed at start (D36). Host-owned and application-scoped implementations are indistinguishable to both application code (I32) and analysis.
- A scoped platform acquisition that can fail at start makes `start` fail (`ServiceGraphFailed`, D34). It does not make a capability `Unavailable`, unless the platform chooses to catch the failure and resolve `Unavailable`.
  - A platform that may do either should leave that id undecided in its statement.
- Request scope is not modeled (v0.10).

## 17. How provisions are supplied through `Application.start`

**Unchanged.** `Application.start(app, { platform })` is the only supply point for the runtime environment (D30, I29). v0.7 adds no field to `StartOptions` (D42), no parameter, and no second channel. The provision statement never reaches `start` (D47).

## 18–19. Platform composition

**D50 (O1 decided): NEXUS does not compose platforms.**
- A `start` receives exactly one `Platform`.
- Composing platform contributions (a base platform plus an application-scoped storage layer, for example) is the platform author's or host's job, done before `start`, and it produces one `Layer` that builds one `Environment`.
- The same holds for statements: composing two provision statements is outside NEXUS.

Evidence and reasons:
- No platform composes today (D41's reference platform builds one map).
- Composition needs a **conflict policy** (the same id supplied twice: first wins, last wins, or failure). That is platform policy, and NEXUS has no basis for choosing one.
- A NEXUS merge helper would be the first NEXUS-owned piece of platform assembly, a step toward the platform registry ROADMAP §20 forbids.

**The hazard is documented, not hidden (R18).** `Layer.merge` of two `Environment` layers silently keeps only the last map (X1). `capability.md` states this, and a characterization test pins it, so that any future composition decision is deliberate.

## 20. Capability provenance

**D54: not part of the v0.7 contract (O3 stays deferred).**
- Nothing in the relation needs to know *which* platform contribution supplied an id. With one platform per start (D50), that question has one answer.
- The provision statement's own `provenance` span (already in `TargetProfile`) locates *where the statement was written*, which is all diagnostics use.
- Revisit when composition or inspection has a consumer (v0.8 / v0.10).

## 21. Error and diagnostic behavior

- **Static.** Exactly the existing three codes, with the same severities and conditions. There are no new codes, no new rejections, and no message changes.
  - Under the platform binding, an `error` means "a declared requirement that the platform's statement explicitly doesn't provide".
  - What a consumer does with that is still L3. There is still no consumer (CMA F9), so L3 stays open, and its trigger moves to the first tool or host that calls `analyze`.
- **Runtime.** Unchanged:
  - `resolve` never fails;
  - `require` fails only with `CapabilityUnavailableError`;
  - `ApplicationInitError` is exactly `ServiceGraphFailed`.
- **D49: no gating.** v0.7 adds no start-time check of requirements against the `Environment`, and no analysis result affects start, admission, run or dispatch (D10).
- **Rejections.** A malformed statement (an empty id, or an id both provided and not provided) is a `Rejected` outcome, exactly as today.

## 22. Serialization

- Declarations, provision statements, outcomes and diagnostics are already JSON-plain (I13). A platform can ship its statement as JSON, and tooling can load it without importing the platform's code.
- v0.7 defines **no file format, schema version or distribution mechanism** for statements. That is tooling's concern, and has no consumer yet (O9).
- `Capability` values and `Environment`s are runtime values and are never serialized by NEXUS.

## 23. Migration from v0.6

**None: v0.7 is non-breaking.**
- No public type, value or behavior changes.
- No existing test is amended. The DoD 12 tests keep their titles, fixtures and assertions.
- The only contract text that changes is I15's wording (D45), plus prose in `semantic.md` and ARCHITECTURE §16.1 that called the two "unrelated".

**D55.** The public API of v0.7 is identical to v0.6: the same 11 entry namespaces, the G3 primitive export pin, the 35 `Semantic` exports and the 2 runtime values. The release adds contracts, tests and documentation.

## 24. Explicit non-goals

v0.7 does not introduce:
- any change to `src/`: no new function, type, field, code or behavior;
- a capability vocabulary, shipped ids, shipped profiles, or a registry (D8);
- Node, browser, worker or server platform packages; platform detection or runtime discovery;
- a platform profile derived from a `Layer` or an `Environment`;
- a second supply point, or any new `StartOptions` field;
- start-time enforcement of requirements, or any gating;
- platform composition helpers (D50); capability provenance (D54);
- typed per-capability identity in `R` (D51);
- a domain tag in `Semantic` (O8);
- modeling of optional capability use;
- attaching declarations or facts to primitives (L2, v0.8);
- PORT dependencies, a PORT binding, or renderer dependencies (L1);
- MESH adapter changes; MESH engine initialization (L7);
- SSR, HMR, hydration, request scope, source analysis or automatic semantic discovery.

## Contracts (new)

- **C19. The platform binding** (D44). A semantic capability identifier is `Capability.id` verbatim. The binding is written by producers outside NEXUS modules.
- **C20. Platform incompatibility** (§14). A declared requirement, together with an explicit `notProvided` in the platform's statement. Nothing else.
- **C21. Platform conformance.** A platform that publishes a statement must make every start resolve each `provided` id `Available` and each `notProvided` id `Unavailable`.
  - NEXUS doesn't check this at runtime.
  - v0.7 pins it with test tooling (`tests/platform/`), not with a public API (O7).
- **C22. One context, one binding.** An analysis context's requirements and profile belong to the same binding. Platform-binding contexts contain only application capability ids.
- **C23. Requirement means necessity** (D46). Use with a fallback is not a requirement.

## Invariants (new)

- **I34.** Capability identity is the `id`, at runtime and statically. There is no second identity, no mapping table, and no `Shape` comparison.
- **I35.** A provision statement is authored by the platform. NEXUS never derives one from a `Layer`, an `Environment` or execution.
- **I36.** Requirements and statements never change runtime resolution, and runtime resolution never changes a statement.
- **I37.** Analysis never gates `start`, admission, `run` or dispatch (D10, restated for capabilities).
- **I38.** NEXUS owns no capability identifier. The definer of the contract owns it.

## Risks

- **R18. Silent loss on platform merge** (X1). Documented and pinned by a characterization test. Composition stays outside NEXUS (D50).
- **R19. Mixed bindings.** A producer puts PORT ids and capability ids in one context. Semantic can't detect it (opaque strings). Mitigated by C22 and the docs. Escalation is O8.
- **R20. Statement drift.** A platform's statement disagrees with its `Layer`. Mitigated by C21 conformance tests, which each platform owns. NEXUS can't detect it statically.
- **R21. `id` collision** (X2). Pre-existing. Mitigated by the D53 convention.
- **R22. A "neutral" relation read as licence for a universal vocabulary.** Neutral means the *relation*, never the *vocabulary* (D8, I38). Stated in `semantic.md` and ARCHITECTURE.
- **R23. A release with no API change reads as no release.** The new contract is C19–C23 and I34–I38, with tests (§T). This follows the roadmap discipline (§22.1: "what new contract exists").

## Tests (§T)

Guardrails first; these must pass unchanged, with no amendments:

- G1–G4;
- the leaf tests;
- the 35-export and 2-runtime-value pins;
- the v0.4 differential corpus;
- the DoD 12 (I15a) tests.

New tests:

1. **`tests/capability-model.test.ts`: the platform binding (C19, C20, C22, C23).** It uses only the public API.
   - A declaration requiring `Storage.id` and `Network.id`, against a statement providing both, is *supported*.
   - The same declaration against a statement with `Storage.id` in `notProvided` is *incompatible*, with one `nexus-incompatible-target-capability`, and related spans for the requirement and the statement.
   - Against a statement that leaves `Storage.id` undecided, it is *opaque*, with cause `target`.
   - A whole-application declaration versus per-operation declarations gives the same verdict for the union, and finer diagnostics when split.
   - Necessity: an operation using `resolve` with a fallback, declared with no requirement on that id, is *supported* against a statement not providing it. The mis-declared control is *incompatible*.
   - The semantic identifier is exactly `Capability.id`: renaming the id changes the verdict, and renaming the TypeScript binding doesn't.
2. **Independence (I36, I37).** For each verdict, starting the application on a platform that contradicts the statement gives exactly the runtime resolutions its `Layer` supplies, and `start` succeeds.
3. **Conformance tooling (C21).** `tests/platform/conformance.ts`, test-only, imports only `effect` and `src/`, and is covered by the existing `tests/platform/` architecture block.
   - Given a `Platform` and a statement, it starts an application and reports every `provided` id not `Available` and every `notProvided` id not `Unavailable`.
   - Tests: the reference platform with a matching statement conforms; a deliberately drifting statement is reported, in both directions; undecided ids are never reported.
4. **Composition characterization (R18, D50).** Merging two `EnvironmentLive` layers as one platform resolves only the last map's ids.
5. **Identity characterization (D53, R21).** Two `define` calls with the same `id` resolve the same implementation.
6. **No new surface (D55).** The existing pins are unchanged. The one addition is a type test that `StartOptions` still has exactly `platform`.

## Self-review

- **Four concepts, four places.**
  - Application capability: the `Capability` contract.
  - Application requirement: a declaration, with necessity semantics.
  - Platform provision: a platform-authored statement (claim) and the `Layer` (fact).
  - PORT target capability: not modeled, in a separate binding.
  - The single shared element is the contract `id`, by an explicit rule (D44), with no code path between the claim and the fact (C19, I35, I36).
- **v0.6 is kept.**
  - The single supply point, `StartOptions`, lifetime, no environment vocabulary, no default-service wrapper, host independence.
  - The leaf; the released semantic names, codes and messages.
- **Nothing is invented.**
  - No vocabulary, package, registry, detection or provenance.
  - No new API, because the evidence (CMA F1, F2, F8, X3) shows none is needed.
- **Open items are named** (§25). None blocks implementation.
