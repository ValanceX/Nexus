# NEXUS v0.4.0 release notes

*Unreleased draft.*

v0.4 adds a semantic analysis foundation: NEXUS can now say what it knows about an operation before executing it. You describe operations as plain data, supply a target profile, and `Semantic.analyze` classifies each operation as **supported**, **opaque** or **incompatible**, with structured diagnostics. It is purely additive: no existing export, type, error channel or behaviour changes, and nothing executes differently.

## Highlights

- **`Semantic.analyze(context)`,** a plain, synchronous, pure function. It reads only the declared fields of its input, runs no application code, and needs no started application or runtime.
- **Declaration-level analysis.** NEXUS reasons only about facts you declare. It reads no source and inspects no closure, so a command handler declared as one operation is one semantic unit.
- **One semantic property: target requirements.** The property set is recorded in every result, and later releases will call out each addition, since a new property can change a classification.
- **Opaque is not incompatible.** Missing or undecided information gives *opaque*, never *incompatible* and never an error. *Incompatible* needs a declared requirement and a profile that explicitly doesn't provide it.
- **Three diagnostic codes, two severities:** `nexus-incompatible-target-capability` (error), `nexus-opaque-operation` and `nexus-undetermined-target-capability` (warnings, emitted only when the context requires target compatibility). Diagnostics are plain data with exact source provenance, and state findings, never actions.
- **Rejection is separate.** A malformed context (duplicate or missing identities, invalid spans, empty capability identifiers, a capability decided both ways) is `Rejected` with structured issues, never diagnosed.
- **Nothing is gated.** No start, admission, run or dispatch consults an analysis result.
- **Target capability ≠ application capability.** Target capabilities are opaque identifiers in a profile you supply; the `Capability` primitive is unchanged and unrelated.

## Try it

v0.4 isn't published to npm. From a clone:

```console
$ pnpm install
$ pnpm test
$ pnpm build
```

See [`docs/semantic.md`](../semantic.md) for the model, the rules and an example.

## Upgrading from v0.3

Nothing to change. The package entry gains one namespace, `Semantic`.

## Not in v0.4

No source capture, semantic IR, optimizer, target lowering, discovery, CLI, editor or LSP integration, and no PORT integration. How declarations attach to primitives, what a consumer does with an `error`, and cross-context identity are deliberately undecided.
