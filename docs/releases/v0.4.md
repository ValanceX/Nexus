# NEXUS v0.4.0 release notes

*Released 2026-09-26.*

v0.4 adds a semantic analysis foundation: NEXUS can now say what it knows about an operation before executing it. You describe operations as plain data, supply a target profile, and `Semantic.analyze` classifies each operation as **supported**, **opaque** or **incompatible**, with structured diagnostics. It is purely additive: no existing export, type, error channel or behaviour changes, and nothing executes differently.

## Highlights

- **`Semantic.analyze(context)`,** a plain, synchronous, pure function. It reads only the declared fields of its input, runs no application code, and needs no started application or runtime.
- **Declaration-level analysis.** NEXUS reasons only about facts you declare. It reads no source and inspects no closure, so a command handler declared as one operation is one semantic unit.
- **One semantic property: target requirements,** declared `complete` or `partial`. The property set is recorded in every result. A later release that adds a property will call it out, because a new property can change a classification.
- **Opaque is not incompatible.**
  - Missing or undecided information gives *opaque*, never *incompatible* and never an error.
  - *Incompatible* needs a declared requirement and a profile that explicitly doesn't provide it.
- **Three diagnostic codes, two severities:**
  - `nexus-incompatible-target-capability` is an `error`, always emitted for an incompatible operation;
  - `nexus-opaque-operation` and `nexus-undetermined-target-capability` are `warning`s, emitted only when the context requires `target-compatibility`.

  Diagnostics are plain data with exact source provenance (UTF-16 code-unit offsets). They state findings, never actions.
- **Rejection is separate.** A malformed context is `Rejected` with structured issues, never diagnosed. Malformed means: a duplicate or missing identity; an invalid span (`end < start`, an empty source, or an offset that isn't finite or is `-0`); an empty capability identifier; or a capability decided both ways.
- **Nothing is gated.** No start, admission, run or dispatch consults an analysis result.
- **Target capability ≠ application capability.**
  - Target capabilities are opaque identifiers in a profile you supply. The `Capability` primitive is unchanged and unrelated.
  - No `Capability`-related type appears in, or is required by, the semantic model.

## Try it

v0.4 isn't published to npm. From a clone:

```console
$ pnpm install
$ pnpm test        # 17 files, 237 tests
$ pnpm build
```

See [`docs/semantic.md`](../semantic.md) for the model, the rules and an example. `tests/semantic.test.ts`, `tests/semantic-isolation.test.ts` and `tests/semantic-types.test.ts` cover the behaviour, purity and the type boundary.

## Upgrading from v0.3

Nothing to change. The package entry gains one namespace, `Semantic`, and every v0.3 test passes unmodified.

## Notes

- **The DoD 12 wording was amended (outline Revision 3).** It now says no `Capability`-related type appears in, or is required by, the semantic model.
  - TypeScript is structural, so a `Capability` value, which has an `id`, can still be passed where a `Declaration` is expected.
  - If it is, analysis reads only the declaration's own fields and treats it as an operation with unknown requirements, which is *opaque*. Runtime semantics are unaffected.
- **`FUTURE_DIRECTION.md` §18** now includes the invariants I11–I19 established by this release.

## Not in v0.4

- No source capture, semantic IR, optimizer, target lowering or discovery.
- No CLI, editor or LSP integration, and no PORT integration.
- Deliberately undecided:
  - how declarations attach to primitives;
  - what a consumer does with an `error`;
  - identity across analysis contexts.
