# NEXUS v0.10.0 release notes

*Released 2026-10-02.* Tagged `v0.10.0` on the merge of its release pull request, and published to npm as [`@valancex/nexus`](https://www.npmjs.com/package/@valancex/nexus) 0.10.0:

```console
$ pnpm add @valancex/nexus@^0.10.0
```

v0.10 adds one observation primitive: **`values`, the current value and then every later change, with no gap between them.**

## What was wrong

`State.changes` (and so `Selector.changes` and `Mesh.Host.renders`) are future commits only. An observer that needs to start from the present had to read the value and then subscribe, two steps, and a commit between them was seen by neither. The observer then held a value older than the state, with nothing later to correct it.

The Valance tracer bullet hit exactly this: it rendered the initial state and then subscribed to renders. A commit in between left state `count: 1` and the DOM at `0 clicks`, in 100 of 100 runs of the probe. It was a composition-boundary defect with a substrate cause: there was no atomic way to ask NEXUS for "now, and then everything after".

## What is new

| | |
|---|---|
| `StateHandle.values: Stream<A>` | The value current at subscription, then every later commit, in order. |
| `SelectorHandle.values: Stream<B>` | The same, projected. For `combine`, each input is atomic with its own subscription. |
| `Mesh.Host.values: Stream<Render, MeshDiagnostics>` | The render of the current value, then one render per later commit. |

**The guarantee.** Nothing can be committed between `values`'s first element and its subscription to later commits (one `SubscriptionRef.changes` step; the same mechanism `changes` already used before it dropped the first element). A commit that lands while the consumer is busy, including while the *first render* is being produced, is delivered next, in order. It is never skipped or reordered.

**What it is not.**
- Not a new reactive model, buffer or cache: it is the existing subscription with its first element kept. The consumer's backlog is the existing unbounded subscription's, exactly as for `changes`.
- Not coupled to MESH: `State.values` and `Selector.values` know nothing of renders; `Mesh.Host.values` is the same adapter mapping `renders` already was.
- Not a lifecycle change. No fiber, runtime or scope is created or changed (J1/P1 untouched); `values` ends when the owning scope closes, like `changes`, and is empty if subscribed after that.
- Not a change to `changes` or `renders`. API compatible: no name removed or changed. The two interface additions (`values` on handles NEXUS itself makes) matter only to code that builds a `StateHandle`, `SelectorHandle` or `Host` by hand.

## Evidence

- `tests/observation.test.ts` (8): the two-step gap reproduced (observer holds 0, state is 1, `changes` never delivers the 1); `values` order, "current at subscription, not initial", scope close; commits racing the subscription at 16 relative timings are always a contiguous run ending at the last commit, and the subscription provably landed at different points; a slow consumer misses nothing; `Selector.values` and `combine`.
- Mutation-checked: replacing `values` with read-then-subscribe (one yield between) fails the race test and the slow-consumer test.
- `tests/mesh.test.ts` 5b: a commit made after the host subscribes and before its first render is produced is rendered next.
- All 483 earlier tests pass unmodified; 492 in total.
