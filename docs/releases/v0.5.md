# NEXUS v0.5.0 release notes

*Released 2026-09-27.*

v0.5 gives the semantic model a validated, plain-data intermediate representation. `Semantic.build` validates a context once and returns the semantic IR (`Built`), which the compatibility pass now reads instead of walking raw declarations. The first content the IR carries beyond v0.4 is **data flow**: declared values, and which operations may produce or consume each one. It is purely additive: `Semantic.analyze` keeps its v0.4 signature and outcome type, and every v0.4 result is unchanged.

## Highlights

- **`Semantic.build(context)`,** the only place a context is validated or a `Built` is constructed. `Semantic.analyze` is now `build` followed by the compatibility pass, which reads only `Built` and never the raw context again.
- **Values and data flow.** A context may declare **values** — identities like a cart or a session — and a declaration's `inputs` and `outputs` reference them. Each side of an operation is `Unknown` (nothing declared), `Declared` complete (exactly these, or none), or `Declared` partial (at least these, or none specific) — three distinct states, never collapsed into each other.
- **Closed and open sets.** Each value's producer set and consumer set is `Closed` (complete within this context) or `Open` (a lower bound, with `openedBy` naming the operations that left it open). Every value in a context shares the same producer openness and the same consumer openness, because one unknown or partial fact could involve any value.
- **May-flow is not ordering.** `(P, v, C)` holds exactly when `P` is among `v`'s producers and `C` among its consumers, including self edges. It says nothing about execution order, whether both operations run, or which producer wrote what a consumer sees. No edge list is stored; every edge is derived from the two sets' membership.
- **No new diagnostics, verdicts or passes.** The compatibility pass ignores data-flow fields entirely: they cannot affect a verdict, classification or diagnostic. `Analyzed.properties` is still exactly `["target-requirements"]`.
- **L2 is resolved.** Declarations are canonical and standalone; association between a declaration and the primitive it describes is outside the semantic model and is the author's concern. NEXUS provides no association helper.
- **One new rejection reason, `unresolved-reference`,** for an input or output reference that names no declared value (including `""`). It fires only on the new fields: a v0.4-shaped context — one that sets none of `values`, `inputs` or `outputs` — gives exactly v0.4's issues, in v0.4's order.

## Compatibility

For every v0.4-shaped context, `Semantic.analyze` returns a result deeply equal to v0.4's, and every invalid one gives the same issues in the same order. This is proven differentially, against the released v0.4 module itself (`tests/reference/semantic-v0.4.ts`, a verbatim copy of v0.4.0), over a generated corpus of valid and invalid contexts — not against hand-written fixtures.

133 of the 137 v0.4 test cases stay unmodified and passing. Four are amended, each additively widening a pin to include the approved v0.5 addition; no assertion is removed or loosened beyond that:

- **B5.** `tests/semantic-isolation.test.ts`'s `modeled` read allowlist gains the new modeled field names (`values`, `inputs`, `outputs`, `references`, `value`), so the isolation proxy still permits exactly the fields `build` reads. No assertion changes — only the file-level `modeled` constant.
- **B6.** `tests/semantic.test.ts`'s runtime-exports pin changes from `["analyze"]` to `["analyze", "build"]`.
- **B7.** `tests/semantic.test.ts`'s rejection-reason pin gains `"unresolved-reference"` in the exact union.
- **O1** (from finding B8). `tests/semantic.test.ts`'s N4 doc-parity export-count pin changes from `toBe(20)` to `toBe(35)`: `build` plus 14 newly exported types.

Counted separately: **4 of 137** v0.4 test cases are amended, **133** are unmodified, and **3 assertions** change (B6, B7, O1) — B5 changes no assertion, only the `modeled` constant.

Additive only: no change to PORT, MESH, any primitive, or the application lifecycle.

## Try it

```console
$ pnpm install
$ pnpm test        # 20 files, 287 tests
$ pnpm build
```

See [`docs/semantic.md`](../semantic.md) for the model, data flow and an example. `tests/semantic-build.test.ts` covers the IR; `tests/semantic-compatibility.test.ts` covers v0.4 compatibility and that data flow can't reach a verdict; `tests/semantic-no-primitives.test.ts` covers building and analyzing with every primitive removed.

## Upgrading from v0.4

Nothing to change. `Semantic` gains one runtime export, `build`, and the new optional context fields (`values`, and `inputs`/`outputs` on a declaration); every v0.4 call to `Semantic.analyze` keeps its result.

## Not in v0.5

- No ordering, effects, lifecycle or happens-before, and no execution-order edges.
- No value types, mutability, versioning or schemas.
- No per-value openness — every value in a context opens and closes together; scoping openness to particular values is deferred until a pass needs it.
- No cross-context identity, no association helper, and no NEXUS knowledge of its own primitives.
- No CLI, editor or LSP integration, and no PORT integration.
