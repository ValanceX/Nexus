# NEXUS v0.9.0 release notes

*Prepared 2026-09-28.*

v0.9 makes the platform boundary an actual boundary. **FiberRefs flow from the code that starts an application into the application, and never back.**

An application's platform and `runtime` layer can set Effect's default services (`Clock`, `Random`, `ConfigProvider`, `Tracer`, …), log levels, or any other FiberRef. From v0.9, those settings apply inside the application only:
- the caller that starts it doesn't see them;
- the caller that stops it doesn't see them;
- a caller that observes it through `Runtime.runFork` doesn't see them;
- a later application started from the same caller doesn't see them.

That holds before the run, during it and after it.

v0.9 is **API compatible** and changes **behavior**. The two are listed separately below.

- **Design:** [`superpowers/specs/2026-09-28-nexus-v0.9-outline.md`](../superpowers/specs/2026-09-28-nexus-v0.9-outline.md), invariants I44–I49 (Revision 1) and contracts C29–C32.
- **Evidence:**

  - [`architecture/2026-09-28-j1-application-fiber-boundary.md`](../architecture/2026-09-28-j1-application-fiber-boundary.md), finding J1.

## What was wrong

- **P1: building in the caller's fiber.** `Application.start` (and `Runtime.make`) built the platform and the application layer in the caller's fiber. A FiberRef layer such as `Layer.setClock` therefore changed the caller while the application ran.
  - With `Layer.merge` (the shape of a typical platform), the change **survived the application**: it stayed after `shutdown`, and a later application started without a platform ran on the earlier platform's Clock.
  - With `Layer.provideMerge`, it survived when the start scope was closed, or when start failed.
- **J1: `runFork` handed out the application's own fiber.** `Runtime.runFork` returned the application's own fiber. `Fiber.join` on it (the usual way to get its result) copied the application's FiberRefs into the caller, where they stayed.
  - The Chromium tracer bullet found J1 after P1 was fixed.

## Behavioral contract (new in v0.9)

**Isolation covers the execution boundaries NEXUS creates and controls:**
- **B1:** `Application.start` / `Runtime.make`, including a failed or interrupted start;
- **B2:** termination, by `Application.shutdown` or by closing the start scope;
- **B3:** `Runtime.run`;
- **B4:** the handle `Runtime.runFork` returns.

**The guarantees:**
- **I44, caller isolation.** Across B1–B4, the caller's FiberRefs are unchanged: before start, during the run, after the stop, and after any operation on a `runFork` handle. A change the caller makes itself is kept.
- **I45, the view inside the application, unchanged.** Inside the application, the precedence is still the caller's value at start, then the platform, then the application layer.
- **I46, lifecycle.** Nothing the platform, the layer or the application's execution wrote, in acquisition or release, is visible through B1–B4 after termination.
- **I47, across applications.** One application's FiberRefs never reach another through B1–B4, whether they run concurrently or in sequence.
- **I48, finalizers, unchanged.** A finalizer sees what its acquisition saw.
- **I49, start, unchanged.** `start` keeps the same type, errors, status transitions and interruptibility, and still works under `Effect.runSync`.

**The `runFork` handle** is an execution handle NEXUS controls, not the fiber the effect runs in.

It guarantees:
- **completion:** `await`, `poll` and `status` observe the effect's completion;
- **results:** `join` and `Effect.fromFiber` give the effect's own result, typed failure or defect, unchanged;
- **interruption:** `interrupt` stops the effect and runs its finalizers before it returns, even when called at once;
- **isolation:** `join`, `fromFiber`, `inheritAll` or any other operation imports none of the application's FiberRefs;
- **refusal:** after termination has begun, the handle ends as a defect and the effect never runs, as before.

It doesn't guarantee:
- that its `id()` identifies the fiber the effect runs in;
- that `status` describes that fiber rather than the handle;
- that it is the same fiber NEXUS uses internally.

**What isolation doesn't cover (O19, deferred).** A value that an application's own effect returns is the application's data. If an effect deliberately returns execution state, such as a fiber it forked, its `FiberRefs` or its Effect `Runtime`, using that value is outside these guarantees. `A` is unconstrained, and NEXUS doesn't inspect results.

**Still unresolved (O15).** A MESH host's `render` and `renders` aren't admitted work. They run where their caller (a composer) runs them, outside the application's lifecycle. That is unchanged, and documented as an open question, not a guarantee.

## API compatibility

- **No exported name, type or module changed.** `Runtime.runFork` still returns `Fiber.RuntimeFiber<A, E>`. `tests/exports.test.ts` is unchanged.
- **Internal change:** `src/runtime/` only. The mechanism is one internal helper: run work in a child fiber, observe it with `Fiber.await` (never `Fiber.join`), and forward interruption. It is used for the build (C29), for closing the scope (C30), and behind `runFork`'s handle (C32). There is no FiberRef snapshot and restore, and no list of FiberRefs.

## Behavior changes you may notice

- Code **outside** an application that read a Clock (or another FiberRef) the platform or application layer set now reads its own. That was never documented, and it was the defect.
- Joining a `runFork` fiber no longer changes the joiner's FiberRefs.
- A `runFork` fiber's `id()` and `Fiber.status` are the handle's own.
- Each `start`, termination and `runFork` uses one extra fiber.

## Evidence

- **NEXUS tests.** All 391 existing tests pass **unmodified**. `tests/platform-isolation.test.ts` adds 92 tests. They were written before each fix: 41 of the P1 tests failed on v0.8.1, and 24 of the J1a tests failed on the P1 fix.
- **The P1 matrix:** Clock, Random, ConfigProvider and the minimum log level × `merge`/`provideMerge` × platform/application layer × both stop routes. It also covers a raw scope finalizer, precedence, concurrent and sequential applications, failed and interrupted starts, finalizers, the caller's own changes, `runSync` and a standalone `Runtime.make`.
- **The J1a matrix:** `await`, `join`, `fromFiber` and `inheritAll` across the same compositions and routes, plus results, typed failures, defects, interruption (including immediate interruption), `poll`/`status`, and refusal after termination.
- **Tripwires.** Each of these fails named tests:
  - reverting the build isolation;
  - reverting the close isolation;
  - using `join` instead of `await`, in either mechanism;
  - dropping the interruption forwarding;
  - returning the application's own fiber from `runFork`.
- **A real composition (PORT's private integration workspace, `integration/browser/`).** The chain is MPRX, the MESH compiler (Node), the MESH runtime (WebAssembly, `init` in the page), NEXUS (state, commands, and `users.refresh` requiring one capability), a test platform in the `Layer.merge` shape providing that capability and Clock 42, the existing composer, PORT Web, and Chromium with real clicks.
  - The positive path passes: reviewed MESH intents, capability resolution, and an in-place DOM update. Application code sees Clock 42 and the caller never does, even though the test gets its events with the ordinary `Fiber.join`.
  - The negative path passes: with the capability absent, the analysis says incompatible, the application still starts, Refresh fails with `CapabilityUnavailableError`, and nothing else changes.
  - The existing jsdom integration and port-web pass unchanged. There is one `effect` and one `@valancex/mesh-runtime`.
  - No MESH or `@valancex/port-web` source changed.

## Compatibility

- **Effect:** `^3.10.0`, unchanged. The mechanism was established against effect 3.22.2's source.
- **MESH:** v0.6 (`@valancex/mesh-runtime` `^0.6.0`), unchanged.
- **PORT:** v0.2. PORT's integration workspace moves to `@valancex/nexus` `^0.9.0` once this release is published.
