# NEXUS v0.7.0 release notes

*Released 2026-09-27.*

v0.7 establishes the **platform capability model**:
- how an application states what it requires from its execution environment;
- how a platform states what it provides;
- how NEXUS relates the two, before anything runs, without embedding any environment in NEXUS.

It is a **non-breaking** release with **no public API change**. It adds exact meanings for existing pieces, tests that pin them, and documentation.

## Highlights

- **What a semantic "target" means is decided (L6).** A `TargetProfile` states the provisions of the one provider an analysis context is evaluated against. `Semantic` defines the relation (required × provided → supported / opaque / incompatible), not a vocabulary and not a kind of environment. A **binding** fixes what the identifiers mean. The released names (`TargetProfile`, `TargetRequirements`, `target-requirements`, `target-compatibility`) and the three `nexus-*` diagnostic codes are unchanged.
- **The platform binding.** A semantic capability identifier is a `Capability`'s `id`, verbatim. `Capability.define("acme.storage")` is the semantic identifier `"acme.storage"`. There is no mapping table, prefix or registry.
- **A requirement means necessity.** An application states a requirement as a semantic declaration naming `Capability` ids. Code that uses a capability with a fallback doesn't require it.
- **A provision is a platform-authored claim.** A platform publishes a plain-data `TargetProfile` alongside its `Layer`:

  | Entry | Meaning |
  |---|---|
  | `provided` | every start resolves the id `Available` |
  | `notProvided` | the id is never `Available` through this platform |
  | neither | undecided (permissions, optional hardware, remote state, configuration) |

  NEXUS never derives a statement from a `Layer` or an `Environment`, and it never passes one to `Application.start`.
- **A claim is not a fact, and analysis is not enforcement.** An *incompatible* verdict doesn't stop an application from starting, and a *supported* one doesn't make a capability `Available`. At runtime, `resolve` and `require` return exactly what the platform's `Layer` supplies. Tests pin both directions.
- **I15 is revised.** "Analysis is independent of resolution" stays. "Separate identifier spaces" becomes "identifiers belong to the context's binding". The v0.4 DoD 12 tests pass unmodified.
- **Five distinct things.** A capability contract, a requirement, a platform statement, a runtime `Environment` and a PORT target capability are different things. The shared `id` is the identity of the contract, not a merger of the abstractions.
- **Platform conformance is test tooling.** Platforms prove that their statement agrees with their `Layer` in their own tests. NEXUS's `tests/platform/conformance.ts` shows how. It reports `provided` ids that aren't `Available` and `notProvided` ids that are, and never reports undecided ids. It isn't part of the package.

## Decided, and documented

- **NEXUS doesn't compose platforms.** `start` takes one `Platform`. Beware `Layer.merge` of two `Environment` layers: the later one replaces the earlier, with no error. A characterization test pins this Effect behavior.
- **Capability identity is the exact `id` string.** Two contracts with the same `id` share an implementation and share verdicts. Qualify ids by their owner.
- **Unchanged decisions.** There is no typed per-capability identity in Effect's `R`. `Application.Platform` stays `Layer<EnvironmentShape, unknown, never>`. There is no capability provenance.

## Compatibility and migration

**Nothing to migrate.** No public type, value, diagnostic code, message, rejection or behavior changes:
- the 11 entry namespaces, the primitive export pin, and `Semantic`'s 35 exports and 2 runtime values are unchanged;
- `src/` is unchanged from v0.6.0;
- no existing test was modified.

The documentation changes where earlier text called application and target capabilities "unrelated", and where examples read a target as a named environment (`"browser"`).

## Tests

34 new tests in three new files and one test helper. The total is 366 tests, up from 332.
- `tests/capability-model.test.ts` (20):
  - the platform binding: supported, incompatible (one error with its exact related spans), and opaque (target-undetermined);
  - necessity versus use;
  - exact identity;
  - independence: every verdict against a matching and a contradicting `Layer`, where the application starts and resolves exactly what the `Layer` supplies.
- `tests/platform-conformance.test.ts` (8), with `tests/platform/conformance.ts`: the test-only conformance helper.
- `tests/capability-characterization.test.ts` (6): `Environment` merge behavior, and identity collision.

Seven deliberate breaks were each caught by a named test and then reverted. The implementation plan's "As built" section lists them.

## Not in v0.7

- Any `src/` change.
- A capability vocabulary, shipped ids or profiles, or a registry.
- Platform packages, detection or discovery.
- Profiles derived from `Layer`s or `Environment`s.
- A second supply point, or a new `StartOptions` field.
- Start-time enforcement or gating.
- Platform composition helpers, or capability provenance.
- A domain tag in `Semantic`.
- Modeling optional use.
- Attaching declarations to primitives (v0.8).
- A PORT binding or PORT dependency (L1).
- MESH changes.
- SSR, HMR, hydration or request scope.
